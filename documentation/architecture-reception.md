# Rota Generator — Reception Rota Architecture

Covers the reception rota only. Shared infrastructure — auth, the app shell, the HTTP client, tech stack, CI, deployment — is documented once in `documentation/architecture.md`; read that first if you haven't already. The clinical rota (generation engine, doctors/rooms/clinics, staging, leave) is a fully separate system documented in `documentation/architecture-clinical.md` and is not needed to work on reception.

## Domain: Reception Rota

A second, independent rota type, backend and frontend both, living under its own `/reception` API prefix and its own `ReceptionShell` in `App.tsx` (see "Shared Frontend Infrastructure" in `documentation/architecture.md`). Nothing is shared with the clinical rota except auth, the app shell, the HTTP client, and the deployment — no doctor, room, clinic type, counter, leave, closure, duty, staging, or `engine/` code is touched or reused anywhere in it. What follows records only what reading the code will not tell a future reader on its own — the reasons a shape was chosen over the obvious alternative.

**Why `reception_staff` is not `doctors`.** A reception staff member is `id`/`code`/`active` and nothing else — no employment window, no `sessions_per_week`, no preferred rooms, no supervision, no signature, no counters. Every one of those fields on `Doctor` exists to serve the generation engine (eligibility, weighted counter scoring, room preference, employment-window gating); reception has no engine, no eligibility, and no counters, so none of it has anywhere to attach. Reusing `Doctor` would mean either padding it with columns reception never reads or special-casing the engine against rows that must never reach it — a new table is the cheaper and safer shape.

**One identifier, called `code` in the code and "Name" in the UI.** A reception staff member had both a `code` and a `name` until the column was dropped in migration 008. Nothing structural separated them — every relation joins on `staff_id`, so neither was ever a foreign key — while `code` carried the unique constraint and was what the grid row headers, sort orders, delete confirmation and leave columns all rendered; `name` reached three render sites and was duplicated onto the wire as `staff_name` on three schemas. `code` therefore survives as the single identifier, matching `doctors`, which has only a code. The staff page labels the field **Name** and nothing else in the UI says "code": the value is whatever the practice wants to read on a rota — initials, a first name, or "Emily M"/"Emily S" where two people would otherwise collide, which is also how the uniqueness constraint gets satisfied. Wire and column names are unchanged (`code`, `staff_code`), so a reader will see the two names for one thing; the alternative — renaming the column and every `staff_code` join to `name` — was rejected as a much wider diff for a label change. The only place the mismatch surfaces to a user is the duplicate-value 409, whose message says "name" deliberately, since the form field it is displayed under is labelled Name.

**Deleting a reception staff member is permanent, and deactivating them is a different verb.** `DELETE /reception/staff/{id}` purges: the staff row, their master template rows, their rows on every already-generated day, and their leave entries all go. A day rota printed months ago will no longer match what the app shows, and the counters window loses that person entirely. That is accepted rather than overlooked — `reception_rota_sessions.staff_id` is non-nullable, so the alternative to purging is an orphan row with no name attached, and the other alternative considered (refusing to delete anyone with generated-day rows) would make anyone who has actually worked a day undeletable, which is precisely the retiring-staff case the feature exists for. Informed consent in the UI and the audit log — which records who deleted which staff id even after the rows are gone — are the mitigations. Two guards narrow it: the endpoint is manager-only (deactivate stays open to admins, because an irreversible action should be the narrower permission — and this is the first manager-only non-GET route outside `/users`), and it 409s unless the member is already inactive, making deletion a deliberate two-step that also removes the "deleted someone who is on today's rota" case. Unlike a has-history guard, requiring deactivation first never makes anyone permanently undeletable: deactivate is always available, so the guard costs one extra click and nothing else. Consequently `DELETE` and deactivate are genuinely different calls here, where on the clinical side `DELETE /doctors/{id}` is itself a soft delete — the divergence is deliberate and the reception router's docstring states it, so a reader moving between the two is not misled. The purge does not remove `reception_rotas` headers it happens to empty: an empty header already means "generated, then every row deleted" as distinct from "never generated" (see the header section below), and deleting it would destroy that distinction and change what the day page offers.

**Deactivating a staff member hides them from the master template but keeps their pattern.** `ReceptionMasterPage` fetches `useReceptionStaff(false)` (active only), so an inactive member has no row on the template grid at all — there is nothing to schedule for someone who is not working, and the previous "(inactive)" flagged row was noise on every day tab. Their `reception_master_sessions` rows are deliberately **not** deleted (deactivation is only `PATCH {"active": false}`, and generation already filters to active staff, so the retained rows can never leak onto a generated day): reactivating brings the whole working pattern straight back rather than making someone reassign every slot. Permanent `DELETE` is still what purges the rows. The **day rota** page keeps `useReceptionStaff(true)`, because a day generated before someone was deactivated has real sessions on it that must stay visible — that is what `pivotReception`'s `inactiveWithSessions` row flag and `ReceptionGrid`'s non-interactive absent cells now exist for.

**Hour model.** A reception day is twenty-two half-hourly slots, 7:30am–6:30pm (`hour=7.5` is the 7:30–8:00 slot, `hour=18` is 6:00–6:30pm), check-constrained rather than modelled as a Postgres enum, which would be a `CREATE TYPE` carrying no semantics the float lacks. The range is defined once — `RECEPTION_FIRST_HOUR`/`RECEPTION_LAST_HOUR`/`RECEPTION_HOURS` in `backend/app/models/reception.py` — and mirrored in the frontend's `lib/receptionHours.ts`. Consequence: **widening the practice's opening hours is a migration** (widening the check constraint), not a configuration change; the range was widened once already, from an original 8:00am–6:00pm. Accepted for v1 over making opening hours runtime-configurable, since that would force every read path to resolve them dynamically for a change that happens approximately never.

**Why a half-hour slot is a float `hour` and not a `slot` index.** `hour` is a float whose legal values are `X.0`/`X.5`, keeping the column's original name and meaning ("the hour of day a slot starts") from when slots were whole hours. Renaming it to something like `slot` would have touched the API contract, every schema/router/frontend reference and every test, for a benefit — a name with no numeric-precision baggage — that `8.5` already reads unambiguously without.

The half-hour step is enforced in **two places on purpose**: the DB check constraint (`HOUR_HALF_STEP_SQL` in `backend/app/models/reception.py`) is the real guarantee, and a Pydantic field validator re-checks the same rule so a bad value comes back as a 422 rather than a constraint violation. Hour labels likewise go through one formatter per side — `format_hour` in the model module, mirrored by `formatHour` in `lib/receptionHours.ts` — so no component or warning message knows the format itself.

**One master template with a `day` column, not five.** `reception_master_sessions` is keyed `(staff_id, day, hour)` — a single table, not five per-weekday templates. Unlike `master_rota_templates`, there is **no header/version table at all**: reception has no active/inactive concept and no staging, so a header would only reproduce `master_rota_templates.is_active`'s documented non-schema-enforced-uniqueness ambiguity (see the Tables section of `documentation/architecture-clinical.md`) for no corresponding benefit. Row existence is itself the data, exactly as on `master_rota_sessions` — a staff member with no row for `(Tuesday, 14)` is not expected at 2pm on Tuesdays, so editing a working pattern means creating and deleting rows, not only updating them.

**Why `reception_rotas` has a header row despite having no lifecycle.** A generated day is a `reception_rotas` header (`id` / unique `date` / `created_at`) plus `reception_rota_sessions` rows cascading from it (ORM `cascade="all, delete-orphan"`). The header's sole job is telling apart "never generated for this date" (no header exists) from "generated, then every row deleted" (header exists, no sessions) — without that distinction the day page has no way to decide between offering "Generate" and rendering an editable-but-currently-empty day. There is no `status` column and nothing to commit or scrap, because no draft/commit concept exists for a day rota at all. Sessions are self-contained snapshots copied from the template at generate time and never re-derived afterwards — the same principle as `RotaSession.template_type` on the clinical side.

**Why regenerate 409s rather than overwriting.** `POST /reception/rota` copies the target date's weekday template rows, active staff only, onto a new header; an existing header for that date is a 409 naming it, never a silent overwrite of hand-edited rows. The only path back to a fresh copy is `DELETE /reception/rota/{id}` (sessions cascade) followed by `POST` again — the frontend's "Regenerate" action on `ReceptionDayPage` is exactly that delete-then-generate pair behind a `window.confirm` stating plainly that edits will be lost; there is no force flag, and the server enforces none of the confirm itself.

**`ReceptionDayPage` is a week-commencing dropdown over five independent day headers, not a week entity.** The backend still has no week concept anywhere — `reception_rotas` stays keyed one header per `date`, exactly as the two sections above describe. The frontend picks a Monday from a `getSurroundingMondays`-backed `<select>` (`lib/date.ts`, the same helper family as the staging week selector, extended with a past window since a generated week stays editable indefinitely) and renders one tab per weekday, each tab an unchanged instance of the old single-day body (`ReceptionDayTab` in `ReceptionDayPage.tsx`) against its own `GET /reception/rota?date=`. "Generate week" is a client-side loop over the existing per-day `POST`, one date at a time, treating a 409 (day already generated) as an expected skip rather than a failure to surface — regenerate, edit, and delete all remain per-day actions on whichever tab is active.

**Coverage minimum varies by hour of day, but by nothing else.** `min_phones_for_hour` (`backend/app/models/reception.py`) returns 0 before the lines open at 8:00 (the 07:30-08:00 slot), 1 from 17:00 onwards (17:00, 17:30 and the closing 18:00-18:30 slot, when calls are light), and `MIN_PHONES_STAFF` = 2 in between; it is checked against every hour of every weekday by `compute_coverage_issues` (`backend/app/api/routers/reception_rota.py`) and by the front desk scorer's `W_PHONES` penalty. There is no `reception_coverage_rules` table, no coverage-rules API, and no editor page: the shape of the phone day is a property of the phone lines, not something the practice configures per weekday. This replaced an earlier per-`(day, hour)` rules table (unique on `day, hour`, editable via `PATCH`) — and then, briefly, a single flat `2` — once it became clear the practice wanted one rule, flat across the week but not across the day; the table, its seed script, and the `/reception/coverage-rules` router and frontend page were removed rather than left in place unused (migration `005`). One consequence of the check running at every hour unconditionally: a day with no phones coverage at all (an empty template slot, or a weekday nobody has set up yet) warns at every hour but 07:30, where the old per-row table could simply have no rule for a slot and stay silent. The frontend has no mirror of the rule — warning messages carry their own "N required" text from the backend.

**`compute_coverage_issues` runs two checks, not one.** Alongside `phones_shortfall` it emits `front_desk_gap`: one warning per *contiguous* uncovered range of 8:00am–6:00pm (`FRONT_DESK_HOURS`, `backend/app/reception_front_desk.py` — deliberately narrower than the rota's own 7:30am–6:30pm), where a slot counts as covered when some session at that hour has `role = front_desk` and its holder is not on leave. Per-range rather than per-hour because up to twenty per-hour lines stacked on the twenty-two possible `phones_shortfall` lines would swamp the panel, and `08:00-13:00: no front desk cover` says the same thing once; the message comes from `format_hour_range`, a multi-slot sibling of `format_hour` with no frontend mirror (nothing renders a range client-side). Both checks share the same leave exclusion and the same already-loaded `rota.sessions` — no extra query. Consequence worth knowing: every day generated before front desk assignment existed now carries an all-day gap warning, and it has a sibling — every day generated before the phones top-up existed keeps whatever `phones_shortfall` warnings it had until the day is re-assigned. A freshly generated day should carry far fewer of them, since the frontend now chains generate → assign (see below).

**`ReceptionRole` has thirteen values; phones coverage stays phones-only.** Beyond `phones`/`other`, `ReceptionRole` (`backend/app/models/enums.py`) also carries `prescriptions`, `registrations`, `front_desk`, `admin`, `online_triage`, `rotas`, `tasks`, `lunch`, `not_working`, `cutteslowe`, `wolvercote` — plain tags on a slot rather than a new table, since a role here is a label with no fields of its own. (Adding a value to a live enum is `ALTER TYPE ... ADD VALUE` — migration `004`, for `cutteslowe`/`wolvercote`; the other nine predate the consolidated baseline and are simply part of it.) `cutteslowe` and `wolvercote` are branch-site tags, not phone-coverage roles — same shape as every other role here, no new minimum-staffing concept. `compute_coverage_issues` deliberately was not extended to the new roles — `min_phones_for_hour` and the `phones_shortfall` check remain phones-specific; the new roles have no minimum-staffing concept. The frontend picks a role from a `<select>` (`RECEPTION_ROLE_ORDER`/`RECEPTION_ROLE_LABELS` in `frontend/src/lib/receptionRoles.ts`), replacing the old two-button toggle, which stopped working once there were more than two roles to choose from. `not_working` is a tag like any other, not a substitute for row deletion or for a leave entry — a `not_working`-tagged row counts toward nothing coverage-wise but is not itself "absent" in either sense that section means; it exists mainly for marking a template slot as a scheduled non-working period (e.g. alongside `lunch`) without deleting the row and losing the note/history that comes with it.

**Coverage now sees whole-day absence (resolved).** `reception_leave_entries` is `(staff_id, date)` and nothing else — no period column, no notes. Reception's day is a run of half-hourly slots, so an AM/PM split would be an arbitrary line through the middle of one, and the finer-grained case ("off from 2pm") was already expressible, more precisely, by deleting those slots or tagging them `not_working`. Leave is therefore a coarser fact layered on top of the per-slot mechanism, not a replacement for it: deleting a row is still how you say "not working this slot", and both remain true at once.

What leave changes is exactly one line of arithmetic. `compute_coverage_issues` loads the date's leave rows and skips those staff when counting `phones` holders; nothing about generation, row creation, or row deletion moves. A day generated before someone was marked off keeps every row it had, and generating a day for a date someone is already off *still copies their template rows* — the absence is expressed by the count and by the greyed row, never by missing data.

That greying is load-bearing, not decoration. Because the rows stay, a coverage warning reading "2 staff on phones, 3 required" would sit next to three visible `phones` chips in that column and read as broken arithmetic. `ReceptionRotaOut` therefore carries `staff_on_leave` (the same ids the count filtered on) alongside `sessions` and `issues`, and `ReceptionGrid` takes an optional `staffOnLeave` prop that dims the row and labels it — dims only: the cells stay clickable, since an admin may still want to retag or delete a slot on a day someone is off. `ReceptionSessionWriteOut` deliberately does *not* carry the field, since a session write cannot change who is on leave; the by-date cache's copy stays correct and there is nothing to re-splice.

**Reception leave is weekday-only on the way in, but not on the way out.** Bulk add skips Saturday and Sunday and reports the count, because reception is Monday–Friday throughout — `Day` has no weekend members and `POST /reception/rota` 422s a weekend date — so a weekend row could never reach a rota or a coverage count, and writing one would only leave inert rows in the entries table. Bulk delete is deliberately *not* weekday-filtered, mirroring the clinical bulk-delete: "clear this range" should also clear anything a single POST (which accepts any date at face value) put on a weekend.

**The two grids duplicate rather than share, deliberately.** `ReceptionGrid`/`ReceptionCellPopover`/`pivotReception.ts` are siblings of `MasterRotaGrid`/`RotaGrid`/`CellEditPopover`/`pivot.ts`, not a generalisation of them, and every one of their docstrings says so explicitly to head off a later "fix". The axes differ (staff × hour here vs doctor × day/period there), reception has no displacement/steal concept at all (several staff can legally share one `(day, hour)`, unlike a room), and there is no draft/committed or leave-derived inert cell state to reconcile. Forcing one abstraction across both would make each harder to read for a saving of very little code; `ReceptionGrid` is reused unchanged between the master template page (Task 7) and the day rota page (Task 8) — that is the only sharing this feature does, and it is sharing within reception, not with the clinical side.

**Shift-click range select is a UI-only batching convenience, not a new write path.** `ReceptionGrid` tracks a `{staffId, anchorHour, focusHour}` selection locally and, on save, composes an ordered array of per-hour payloads that the page writes with `await` in a sequential `for` loop — never `Promise.all` — against the same unchanged single-hour create/patch endpoints. Sequencing is deliberate rather than an easy default: on the day rota, every write response carries a freshly recomputed full `issues` list, and the cache write overwrites `issues` wholesale, so concurrent requests racing to land last (not necessarily the one computed against the final state) would leave the coverage panel and column warnings silently wrong until the next refetch. On an inactive staff row, a range save writes only the hours that already have a session — the absent-cell add affordance is a frontend gate (`create_master_session`'s docstring notes the backend deliberately performs no active-staff check), and range select must not offer a backdoor around it, so skipped hours are neither highlighted nor written. One cross-component constraint worth knowing before adding any other portalled surface to a cell: the cell's click handler sits on the `<td>` (so it catches both the filled-cell content and the empty-cell `+` button by bubbling), while the edit popover portals into `document.body` — and React bubbles synthetic events along the component tree, not the DOM tree, so clicks inside the popover arrive at the `<td>` as if they were clicks on the cell. `handleCellClick` therefore ignores any event whose target is not physically contained by the cell; without that guard, touching the role dropdown collapses the range to a single cell before Save fires.

**The sequential writes are hidden behind an optimistic overlay, not sped up.** Sequencing being deliberate does not mean the user should watch it happen: with one cache splice per hour, a row-wide assignment repainted after every write, so the run appeared to merge cell by cell over the couple of seconds the writes took. `ReceptionGrid` therefore holds a `PendingReceptionWrite` (`{staffId, hours, write}`, `write: null` for a removal) from the moment Save/Remove is pressed until the page's loop resolves, and renders `withPendingReceptionWrite(grid, pending)` (`lib/pivotReception.ts`) — the pivoted grid with the whole range already flipped — so the merge is one transition. Only the display is overlaid: `handleSave`/`handleDelete` compose their payloads from the un-overlaid `grid`, so the placeholder cell a pending create draws (`session_id: -1`, no `staff_code`/`day`) can never reach the API. On success the overlay is dropped once the real cells match it and nothing moves; on failure it is dropped too, snapping back to whatever actually landed, under the page's error banner. This is a repaint fix and nothing more — the range still takes as many round trips as it has hours, and the grid stays disabled (`saving`) for all of them. A bulk write endpoint is the fix for the wait itself, and would make this overlay redundant rather than conflict with it.

**Adjacent same-role slots merge visually only, never in the DOM.** `ReceptionGrid` renders one `<td>` per half-hour slot and always will; when a slot's `(role, note)` pair matches the immediately preceding slot's, `receptionRunContinuations` (`lib/receptionRuns.ts`) flags it as a continuation, the run's internal divider is dropped, and the repeated chip is hidden. `colSpan` was considered and rejected: a merged `<td>` is one click target for a run of arbitrary length — a whole day, at the limit — which would destroy per-slot editing and the ability for a shift-click range to start or end mid-run, and would force the hour-keyed `{staffId, anchorHour, focusHour}` selection model above to be re-derived entirely. The repeat is hidden with `visibility: hidden` on the chip content *inside* the popover trigger, never on the trigger `<div>` itself — `visibility: hidden` also disables pointer events, and putting it on the trigger would make continuation slots unclickable, losing exactly the per-slot editing this approach exists to preserve. Absent cells deliberately never merge, with each other or with anything else: an absent cell is data ("not expected this slot" — see the master-template section above), a genuinely different state from a `not_working` session, and each one owns its own per-slot `+` affordance. The merge key includes `note`, not just `role`, so a run's slots never differ in a way that would hide user-entered text. **Only a lone slot sizes its column to its label.** The grid's `table-fixed` class is inert — `table-layout: fixed` applies only when the table's own width is not `auto`, and `min-w-full` sets a min-width — so the automatic algorithm runs and every cell's content widens its column. Wanted for a lone slot, which has to hold "Prescriptions" by itself; wasteful for a run, which spreads one label across `runLength` columns, so a whole-row run used to stretch all 22 columns to fit text drawn once. Inside a run the invisible in-flow copy is therefore `w-0 overflow-hidden whitespace-nowrap`: still there to set the row height and the popover trigger's hit box, contributing no width. Fixing this by giving the table a real width instead would engage fixed layout and equalise every column, which is the opposite of what lone slots need.

**A run is drawn as one bar, and that decides the grid's paint order.** The role colour lives on an absolutely positioned bar inside each `<td>`, not on the cell background: with the cell's own padding box as the bar's extent and rounded corners plus left/right borders drawn only at the run's ends (top and bottom on every segment), a run of slots reads as one capsule on a timeline instead of a row of filled spreadsheet cells. It also retired the near-black 2px `ink/40` rules the grid used to be built from, which drew on each cell's bottom and right only and gave every block a pseudo-3D bevel. Two consequences are worth knowing before touching the cell markup. Every `<td>` is now `position: relative` (it is the bar's containing block), where previously only a run's first cell was, for the centred label; and because a run's label overhangs its own cell into the run's later cells — whose bars are *later siblings* in the tree and therefore paint on top — the label needs an explicit z-index or all but its first cell's slice disappears behind them. The grid's layering is documented next to the constants in `ReceptionGrid.tsx` and runs: header corner (40) > sticky staff column (30) > sticky header row and the shift-click selection outline (20) > run label (10) > bars (auto). The staff column has to outrank the label for the same overhang reason. The selection outline is drawn the same way as a bar, one capsule around the whole range, for the same reason: a per-cell ring on each selected slot read as a row of separate boxes rather than one selection.

**The hours counter was a client-side derivation; the counters page is not.** The old `ReceptionHoursPage` computed each staff member's weekly working hours entirely in the browser from the already-fetched template, and this file argued against backend aggregation for it: the template list is at most a few hundred rows and reception had no counters concept to extend, so a route and a schema would have bought arithmetic the frontend could already do. That argument no longer holds and the page has been replaced by `ReceptionCountersPage` (`/reception/counters`). Two things broke it. The window figure — what a staff member *actually* worked over the last few weeks — cannot be derived from the recurring template at all; it lives in `reception_rota_sessions`, which the frontend does not hold and should not fetch a month of. And a future front-desk-rotation generator needs the same numbers server-side as its fairness input, so a browser-only derivation would guarantee the two eventually disagree. The template-derived weekly figure survives as one column on the new page, because "what is Sam contracted for" and "what did Sam actually work" are different questions worth reading side by side; its derivation (all template rows minus those tagged `not_working`, × 0.5, absent slots already excluded because only rows exist in the data) is unchanged and still lives only in `computeWeeklyHours` on that page.

**Reception counters are derived at read time and never stored.** This is the deliberate divergence from the clinical side's `clinic_counters` / `counter_snapshots` tables, and the reason is the window. A rolling window cannot be kept as a running total: a stored counter can be incremented and decremented but has no way to *forget* a day that ages out, so it would have to be rebuilt from `reception_rota_sessions` anyway — making the table a cache of a derived number rather than a source of truth. Nothing is lost by omitting it, because the persistence a generator needs is the assignment history and `reception_rota_sessions` already *is* that history. The clinical tables exist for reasons reception does not share: the engine reads counters mid-run as a tie-break, and the values are cumulative forever, which is what makes the snapshot lifecycle and the reset endpoints necessary. Reception has no draft/commit lifecycle to hang a snapshot off — "Regenerate" is `DELETE` then `POST` (see above) — so a stored reception counter would need correct decrements on every session delete, day delete and cascade, with no snapshot to restore from when one was missed. One consequence to know rather than to fix: deleting or regenerating a past day moves the counters, because that day's sessions *were* the counter's contribution. That is the correct reading — a regenerated day's old assignments did not happen — but it does mean a number on this page can change without anyone touching the current week.

**The counter window is anchored to a Monday, so it is 29–33 days long, not 28.** The default is the four complete preceding weeks plus the current week to date: `from_date = monday_of(today) − 4 weeks`, `to_date = today`. Its length therefore moves through the week and resets each Monday, and today's own rota counts even though the day is not over. Both are accepted rather than overlooked: every staff member is measured over the *same* window, which is all a fairness comparison needs, and the absolute counts are never meant to be read as a stable metric over time. Future-dated generated days are excluded, so generating a week ahead does not pollute the picture with assignments that have not happened. `days_counted` — the number of distinct *generated* dates in range, not the number of days the range spans — is returned and rendered above the table for exactly this reason: a window with sparse generation contributes fewer days rather than reaching further back, and four weeks containing six generated days is a fact the page should show rather than leave indistinguishable from a quiet one.

**Leave is excluded from both numerator and denominator.** A staff member's rows on a date they have a `ReceptionLeaveEntry` count toward neither their role counts, nor their hours worked, nor their days present. Their rows stay on the day exactly as generated — this is a reading of the data, not a change to it, consistent with the whole-day absence section above — and because the value is computed at read time, leave entered *after* a day was generated is picked up automatically with no leave-router change needed. Hours worked excludes `not_working` and nothing else, matching the old hours page's rule exactly so the page's two hours figures cannot disagree about what "working" means; `lunch` therefore counts as working time, a deliberate choice with a known cost (it inflates the denominator and dilutes every role's proportion by a few percent, uniformly for everyone).

**Why `Off` (`not_working`) shows an em dash in the page's "% of time" mode.** The weighted counter is `role_hours / hours_worked`, a proportion of working time. `not_working` is the one role whose hours are counted in the numerator's reach but excluded from the denominator by the rule above, so its ratio is not a proportion of anything and can exceed 100% — two `phones` slots against ten `not_working` slots would read as 500%. "What proportion of Sam's working time was spent not working" is not a question with an answer, and inventing one would be worse than an empty cell, so that single cell renders an em dash. This is a display rule and lives only with the display (`lib/receptionWeightedScore.ts`): the backend returns raw slot counts for all thirteen roles plus the hours figure, and computes no ratios at all. That file is a sibling of the clinical `lib/weightedScore.ts`, not a reuse of it — it drops the clinical function's cosmetic ×10 (a proportion is already readable) and maps a zero denominator to "no data" rather than to infinity, because infinity there is a real answer to "who is least loaded" for a sort key the engine consumes, while here it would claim a fairness fact that does not exist.

## Assignment

A second, separately-invoked step over an already-generated day (`POST /reception/rota/{id}/assign`, `backend/app/reception_front_desk.py` and `backend/app/reception_phones.py`): partition 8:00am–6:00pm into two or three contiguous blocks at half-hour boundaries and give each to one staff member who is in the building for every slot of it, then move `online_triage` staff onto `phones` in contiguous chunks wherever the day is still below `min_phones_for_hour`. Generation itself stays a pure template copy. The module and router docstrings carry the mechanics; what follows is only the reasoning that no single file shows.

**Exhaustive enumeration, and why there is no engine here.** Fifty legal partitions (five two-block, forty-five three-block) × at most a few hundred staff assignments each is small enough to generate and score in full, so it is — no greedy pass, no heuristic, and emphatically none of the clinical side's phase pipeline. Fixed changeover times and greedy longest-available-first were both considered and are worse answers at this size *and* no simpler to write. Lunch is what makes the space this small rather than what breaks it: a 1pm lunch slot bars its holder from any block spanning 12:30–13:30, which pushes changeovers onto the lunch boundaries on its own.

**Everything that could leave the desk unmanned is a score, not a rule.** The 3–5 hour ideal length, displacing a specialist role, and pushing an hour below its phones minimum are all penalties. This is the same convention as the rest of reception, where coverage produces warnings and nothing blocks — an unmanned desk is a worse outcome than a warning that already has a UI, and with `MIN_PHONES_STAFF` = 2 on a thin day a hard phones rule could make the day infeasible outright. Only wrongness is hard: blocks tile the window exactly, a holder is present for every slot they hold, and nobody holds two *adjacent* blocks (that is one long block wearing a hat — two *non-adjacent* blocks, a morning and a late afternoon with someone else in the middle, is a normal outcome and merely penalised). No legal solution at all means assign nothing and let `front_desk_gap` say so.

**The length penalty fires on most days; that is arithmetic, not a bug.** Ten hours over three blocks forces a 3h20 average, and inside the 3–5h band there are only six legal three-block shapes (3+3+4, 3+4+3, 4+3+3, 3+3.5+3.5, 3.5+3+3.5, 3.5+3.5+3) and exactly one two-block shape (5+5). So `W_LEN` is a routine term in the total rather than the rare tie-break it looks like. Anyone retuning the weights should also keep `W_PHONES` dominating `W_ROLE`: the two criteria overlap deliberately on the phones case, which is both the cheapest displacement and the only one that creates a shortfall.

**Assignments overwrite `role` in place and record what they overwrote.** The alternative — a `reception_front_desk_blocks` overlay table — was rejected: it would make "what is Sam doing at 2pm" have two sources of truth, force overlay rendering into `ReceptionGrid`, and need a counters change. Overwriting needs none of that, because three things already existed: `front_desk` is already a `ReceptionRole`, `receptionRunContinuations` already merges a contiguous same-role run into one chip so a three-hour block *displays* as one block despite being six rows, and `compute_role_counters` already returns `front_desk` counts and `hours_worked`.

What overwriting does need is a way back, and that is `reception_rota_sessions.displaced_role` (nullable, migration `006`), whose invariant is **non-null ⇔ this generator wrote this slot**. It is set on every slot the generator writes, *including* when the previous role was already `front_desk` (a no-op restore), so the invariant is total and reset is a flat "restore every row with a non-null `displaced_role`". Re-running is therefore reset-then-assign, and idempotent. A manual `PATCH` of a slot nulls the column: the user has taken ownership, and a later reset must not resurrect a role the day no longer has.

The obvious cheaper alternative — recovering the displaced role by re-reading the weekday template, with no column at all — was considered and fails three separate ways, all of them silent: `front_desk` is selectable in `RECEPTION_ROLE_LABELS`, so a hand-tagged slot would be deleted by the next run; a session can exist for a `(staff, hour)` the template has no row for, so there may be nothing to reset *to*; and the template drifts, so resetting a two-week-old day would restore a role that day never had. One nullable column fixes all three exactly.

**The generator uses its own counter window, and the counters page keeps `default_counter_window`.** Both are `monday_of(anchor) − 4 weeks` to `anchor`; the page anchors on `today`, `assignment_counter_window` anchors on the rota's own date. The page's future-date exclusion (documented above, and correct for the page) is what forces the split: generate next week on a Friday and every day in the batch is future-dated, so assigning Tuesday could not see the `front_desk` rows written to Monday moments earlier — every day would read identical counters and pick the same person five days running. Anchoring to the rota's date also makes assignment reproducible, since the window then depends on nothing but the day being assigned. `compute_role_counters` needed no change: it has no notion of "today", and the exclusion lives entirely in `default_counter_window`.

**Fairness is a proportion, not a raw count** — `front_desk_hours / hours_worked`, the same ratio `lib/receptionWeightedScore.ts` renders on the counters page, so the two surfaces agree on what "least front desk" means. Raw counts would structurally favour part-timers, who always have a lower count than someone in five days a week and would win the tie-break every day they are in. A zero denominator scores `0.0` (lowest load, picked first), mirroring that file's no-data rule. Recency and block-position fairness are deliberately absent: the 29–33 day window is already the horizon over which rotation self-corrects, and dropping them keeps this module reading only the counters aggregate and the target day rather than re-deriving historical blocks from past days' role tags — which, with no blocks table, would mean guessing.

**One combined `/assign` endpoint, not two.** `POST /reception/rota/{id}/front-desk` and a hypothetical separate phones step were merged into one `POST /reception/rota/{id}/assign` (reset → front desk → phones top-up, one transaction) rather than kept apart. The two steps are genuinely coupled: the front-desk scorer deliberately displaces phones (`W_PHONES` is a penalty, not a prohibition — see below), so the top-up exists partly to repair the hole the desk just made, and running it against a stale desk assignment would be meaningless. The decisive argument, though, is the reset: two endpoints would each have to reset only *their own* `displaced_role` rows, which needs a discriminator column and therefore a migration, bought purely to enable a re-run mode nobody wants. One endpoint keeps `displaced_role`'s invariant (non-null ⇔ this generator wrote this slot) flat and total across both assigners, with no schema change. Worth correcting a natural assumption: merging the endpoints saves no round trip — the frontend already chained generate + assign as two calls before this change, and still does. What it avoids is adding a *third* call.

**Greedy longest-chunk for phones, exhaustive enumeration for the desk — a contrast, not an inconsistency.** `reception_phones.py` picks chunks greedily and is knowingly suboptimal: it can hand a long run to the only person who could have covered a later gap, leaving that gap unfilled where a split would have covered both. The residual surfaces as an ordinary `phones_shortfall` warning — the recognisable symptom is a shortfall at a late hour with somebody visibly on `phones` earlier in the day who could have covered it, which is this trade-off working as documented, not a bug to chase. The reason greedy is right here and wrong for the desk is the shape of the two problems, not a difference in how carefully each was built. Front desk partitions a *fixed* twenty-hour window into two or three blocks — fifty legal partitions, small enough to enumerate and score exactly. Phones top-up covers a *sparse deficit vector* over twenty-one slots, where a deficit can be 2, deficit hours are not contiguous, and multiple people can each contribute to the same hour (a covering with multiplicity, not a partition) — there is no fixed small enumeration to run. Min-cost flow or a DP over slot states would be optimal and are a large step up in complexity; revisit only if real days produce bad answers.

**Longest chunk first, with a one-slot tolerance band before fairness decides — and why not strict lexicographic order.** Phones-top-up candidates are ranked on deficit slots covered, but a strict `(-deficit_slots, load, staff_id)` order was rejected: it would make fairness vestigial, since someone available 9:00–5:00 always beats someone available 9:00–12:00 for a gap starting at 9:00 regardless of load, so the same full-time triage person would take every top-up every day. Instead the best deficit-slot count defines a shortlist — every candidate within `COVERAGE_TOLERANCE_SLOTS` of it — and the lowest phones load wins from there. Chunk quality still dominates, because it decides the shortlist, but fairness can actually move the answer once inside it. This is the same intent as the front-desk scorer's weighted `W_FAIR` term, expressed in the shape the phones problem has, rather than as a hard-coded tie-break. It is also what makes the fairness argument hold day to day rather than only in theory: on the very first day assigned, every candidate's phones ratio may sit near zero and the shortlist resolves on `staff_id`, but that is not a permanent bias — the top-up writes real `phones` rows, `assignment_counter_window` reads the preceding 29–33 days of generated sessions, so the next day sees the first day's writes and the ratio moves. Under a strict lexicographic order this self-correction would not happen at all.

**Online triage is fully sacrificial, deliberately, with no second minimum-staffing concept.** There is no minimum triage headcount, hard or soft — phones is the only role in reception with a minimum-staffing concept, and introducing a second one for triage would be a new domain rule to justify, document and edit; triage is stripped to zero if that is what the phones minimum needs. The source pool is `online_triage` only, not `other` or `admin` — that is what was asked for and it is the explicit, auditable version; widening the pool later is a constant change, not a redesign. A consequence worth stating so nobody "fixes" it: because availability is filtered to that one role, there is no analogue of `reception_front_desk._UNAVAILABLE_ROLES` here and none is needed — `lunch`, `not_working`, `cutteslowe` and `wolvercote` are excluded by the role filter itself, as is anyone the desk has already taken. And unlike the desk, the top-up has deliberately no `MIN_BLOCK_SLOTS` equivalent: a lone 30-minute phones stint is a worse answer than a two-hour one but a better answer than a shortfall, and the bridging rule exists to make short chunks rare rather than to forbid them outright. This is a decision, not an oversight.

**`W_PHONES` in the front-desk scorer stays as it is.** It is tempting to drop it now that shortfalls get repaired by the top-up, but creating a shortfall that must then be repaired by consuming a triage person is a real cost, not a free one — keep the documented relationship `W_PHONES > W_ROLE`.

**The top-up window is 8:00am–6:30pm, wider than the desk's 8:00am–6:00pm, because it is derived rather than declared.** The desk has its own narrower window because the desk is not manned before opening or after close; phones cover, by contrast, is required for every slot `min_phones_for_hour` returns non-zero for, which includes the closing 6:00–6:30pm slot — twenty-one of the rota's twenty-two slots, only 7:30–8:00 exempt. `reception_phones.py` reads `RECEPTION_HOURS` and `min_phones_for_hour` directly and never `FRONT_DESK_HOURS`, so the window tracks the coverage rule automatically rather than needing its own edit if the rule ever changes.

**One shared `RoleCounters`, computed once, read by both selectors.** The router flushes the reset before calling `compute_role_counters`, so the day's own previous assignments do not pollute its fairness input, and the resulting aggregate is passed to *both* `select_front_desk_blocks` and `select_phones_blocks` rather than recomputed between them. Recomputing after the desk applied its blocks would need a second flush and would fold the just-written `front_desk` slots into the denominator, so the two selectors in one transaction would disagree about what the day looked like going in — the desk's displacement of phones is exactly what the top-up exists to see and repair, and a stale-vs-fresh counters split would blur that.

**Frontend: assignment has no button of its own.** Every path that *creates* a day chains it — "Generate from template", "Regenerate" (delete → generate → assign), and each *successful* generate in the "Generate week" loop — so generating always yields a manned day in one gesture. It is deliberately not run after a 409 in the week loop, since that day already existed and reshuffling someone's existing day is not what the button promises; redoing an existing day's desk therefore means Regenerate, which also discards that day's edits. The two halves report failure separately: a failed assignment leaves the generated day on screen and says so, rather than claiming the generate failed. The endpoint stays separate server-side (POST `""` keeps its 409 semantics; assignment stays independently re-runnable) — only the UI collapsed the two steps. `useAssignReceptionRota` overwrites the cached day outright rather than splicing, because the endpoint rewrites many rows at once and returns the whole day. No `ReceptionGrid` change was needed at all, for the run-merging reason above.

## Router surface

| Router | Responsibility | Key behaviour |
|---|---|---|
| `/reception/staff` | Reception staff CRUD plus a permanent delete | `GET` (`include_inactive` query param, default active-only), `POST`, `PATCH /{id}` (also the deactivate/reactivate verb — `{"active": false}`), `GET /{id}/usage` (what a delete would destroy: master sessions, rota sessions, generated days, leave entries — a separate call because the confirm dialog needs real numbers and folding them into the list would mean N+1 aggregates per page load), `DELETE /{id}` (manager-only permanent purge of the staff row and every row referencing it, returning per-table deleted counts; 409 unless the member is already inactive). See "Domain: Reception Rota" above |
| `/reception/master` | The weekday master template: read and edit | `GET ""` (flat session list, all weekdays), `POST /sessions`, `PATCH /sessions/{id}` (verbatim `(role, note)` pair setter), `DELETE /sessions/{id}`. No displacement rule — several staff can share one `(day, hour)`, unlike a room |
| `/reception/rota` | The generated day: generation, editing, coverage | `POST ""` (copy the weekday template onto a date, active staff only — including staff on leave; weekend 422, existing-date 409), `GET ""` (`?date=`, 404 when ungenerated), `GET /{id}`, `POST`/`PATCH`/`DELETE` on `/{id}/sessions[/{id}]`, `DELETE /{id}` (the whole day, sessions cascade), `POST /{id}/assign` (no body; reset every assigner-written slot, then choose and apply a 2–3 block partition of 8:00am–6:00pm via `app/reception_front_desk.py`, then move `online_triage` staff onto `phones` in contiguous chunks wherever the day is below `min_phones_for_hour` via `app/reception_phones.py` — returns the whole day, 404 only; a day neither step can help is a 200 with `front_desk_gap` and `phones_shortfall` warnings). Reads return `{…, sessions, issues, staff_on_leave}`; every mutating endpoint but the two 204 deletes returns `{session, issues}` with freshly recomputed coverage warnings |
| `/reception/leave` | Whole-day absence for reception staff | `GET` (`staff_id`/`from_date`/`to_date` filters), `POST` (404 unknown staff, 409 duplicate, weekend accepted), `POST /bulk` (range, weekdays only, returns `{created, skipped_existing, skipped_weekend}` counts rather than a per-date skip list), `POST /bulk-delete` (range, weekends included, returns `{deleted_count}`), `DELETE /{id}`. Read in exactly one place — `compute_coverage_issues` — see the whole-day absence section above |
| `/reception/counters` | Per-staff role counters over a rolling window | `GET ""` only, read-only, no stored table — optional `from_date`/`to_date` each default independently to the window above. The window rule and the aggregation live in `app/reception_counters.py`, not the router, because a future front-desk-rotation generator calls them directly and must not be able to disagree with this endpoint |
