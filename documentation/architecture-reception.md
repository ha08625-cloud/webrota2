# Rota Generator — Reception Rota Architecture

Covers the reception rota only. Shared infrastructure — auth, the app shell, the HTTP client, tech stack, CI, deployment — is documented once in `documentation/architecture.md`; read that first if you haven't already. The clinical rota (generation engine, doctors/rooms/clinics, staging, leave) is a fully separate system documented in `documentation/architecture-clinical.md` and is not needed to work on reception.

## Domain: Reception Rota

A second, independent rota type, backend and frontend both, living under its own `/reception` API prefix and its own `ReceptionShell` in `App.tsx` (see "Shared Frontend Infrastructure" in `documentation/architecture.md`). Nothing is shared with the clinical rota except auth, the app shell, the HTTP client, and the deployment — no doctor, room, clinic type, counter, leave, closure, duty, staging, or `engine/` code is touched or reused anywhere in it. The full design-decision record, including the provisional-plan corrections, lives in `documentation/completed/reception_rota.md`; this section records only what reading the code will not tell a future reader on its own.

**Why `reception_staff` is not `doctors`.** A reception staff member is `id`/`code`/`name`/`active` and nothing else — no employment window, no `sessions_per_week`, no preferred rooms, no supervision, no signature, no counters. Every one of those fields on `Doctor` exists to serve the generation engine (eligibility, weighted counter scoring, room preference, employment-window gating); reception has no engine, no eligibility, and no counters, so none of it has anywhere to attach. Reusing `Doctor` would mean either padding it with columns reception never reads or special-casing the engine against rows that must never reach it — a new table is the cheaper and safer shape.

**Hour model (Decision 2).** A reception day is twenty half-hourly slots, 8:00am–6:00pm (`hour=8` is the 8:00–8:30 slot, `hour=17.5` is 5:30–6:00pm), check-constrained rather than modelled as a Postgres enum, which would be a `CREATE TYPE` carrying no semantics the float lacks. The range is defined once — `RECEPTION_FIRST_HOUR`/`RECEPTION_LAST_HOUR`/`RECEPTION_HOURS` in `backend/app/models/reception.py` — and mirrored in the frontend's `lib/receptionHours.ts`. Consequence: **widening the practice's opening hours is a migration** (widening the check constraint) plus inserting new `reception_coverage_rules` rows for the added hours, not a configuration change. Accepted for v1 over making opening hours runtime-configurable, since that would force every read path to resolve them dynamically for a change that happens approximately never.

**Half-hour granularity (Decision 15, supersedes the original hourly model).** `hour` was originally a plain int, one row per whole hour. Switching to half-hourly slots kept the column name and its meaning ("the hour of day a slot starts") and only widened its type to float, with legal values `X.0`/`X.5` — rather than renaming `hour` to something like `slot`, which would have touched the API contract, every schema/router/frontend reference, and every test for a benefit (a name with no numeric-precision baggage) that `8.5` already reads unambiguously without. The DB enforces the half-hour step with `(hour * 2) = CAST(hour * 2 AS INTEGER)` alongside the existing range check (`HOUR_HALF_STEP_SQL` in `backend/app/models/reception.py`); the API schemas re-check the same rule via a Pydantic field validator so a bad value 422s instead of hitting the DB constraint. `backend/app/models/reception.py` also gained `format_hour(hour) -> str` (e.g. `format_hour(8.5) == "08:30-09:00"`), used by `compute_coverage_issues`' warning messages and mirrored by the frontend's `formatHour` in `lib/receptionHours.ts`, which every reception page already routed every hour label through — no frontend component needed to know about the format itself. Migration 024 widened the three `hour` columns from Integer to Float; since the system had no data worth preserving (see CLAUDE.md) and there is no correct automatic mapping from an hourly row to a half-hourly one (an old row for hour=9 meant "all of 9:00–10:00 covered"; keeping it as 9.0 would silently leave 9:30–10:00 uncovered), that migration clears `reception_master_sessions`, `reception_rotas`/`reception_rota_sessions`, and `reception_coverage_rules` rather than reinterpreting old rows. Re-seed coverage rules via `seed/seed_reception_coverage.py` after deploying; the master template has no seed script and was always entered by hand.

**One master template with a `day` column, not five (Decision 3).** `reception_master_sessions` is keyed `(staff_id, day, hour)` — a single table, not five per-weekday templates. Unlike `master_rota_templates`, there is **no header/version table at all**: reception has no active/inactive concept and no staging, so a header would only reproduce `master_rota_templates.is_active`'s documented non-schema-enforced-uniqueness ambiguity (see "Tables (34)" in `documentation/architecture-clinical.md`) for no corresponding benefit. Row existence is itself the data, exactly as on `master_rota_sessions` — a staff member with no row for `(Tuesday, 14)` is not expected at 2pm on Tuesdays, so editing a working pattern means creating and deleting rows, not only updating them.

**Why `reception_rotas` has a header row despite having no lifecycle (Decision 5).** A generated day is a `reception_rotas` header (`id` / unique `date` / `created_at`) plus `reception_rota_sessions` rows cascading from it (ORM `cascade="all, delete-orphan"`). The header's sole job is telling apart "never generated for this date" (no header exists) from "generated, then every row deleted" (header exists, no sessions) — without that distinction the day page has no way to decide between offering "Generate" and rendering an editable-but-currently-empty day. There is no `status` column and nothing to commit or scrap, because no draft/commit concept exists for a day rota at all. Sessions are self-contained snapshots copied from the template at generate time and never re-derived afterwards — the same principle as `RotaSession.template_type` on the clinical side.

**Why regenerate 409s rather than overwriting (Decision 6).** `POST /reception/rota` copies the target date's weekday template rows, active staff only, onto a new header; an existing header for that date is a 409 naming it, never a silent overwrite of hand-edited rows. The only path back to a fresh copy is `DELETE /reception/rota/{id}` (sessions cascade) followed by `POST` again — the frontend's "Regenerate" action on `ReceptionDayPage` is exactly that delete-then-generate pair behind a `window.confirm` stating plainly that edits will be lost; there is no force flag, and the server enforces none of the confirm itself.

**`ReceptionDayPage` is a week-commencing dropdown over five independent day headers, not a week entity (Decision 14).** The backend still has no week concept anywhere — `reception_rotas` stays keyed one header per `date`, exactly as Decisions 5 and 6 describe. The frontend picks a Monday from a `getSurroundingMondays`-backed `<select>` (`lib/date.ts`, the same helper family as the staging week selector, extended with a past window since a generated week stays editable indefinitely) and renders one tab per weekday, each tab an unchanged instance of the old single-day body (`ReceptionDayTab` in `ReceptionDayPage.tsx`) against its own `GET /reception/rota?date=`. "Generate week" is a client-side loop over the existing per-day `POST`, one date at a time, treating a 409 (day already generated) as an expected skip rather than a failure to surface — regenerate, edit, and delete all remain per-day actions on whichever tab is active, unchanged from Decision 6.

**Coverage rule key, and what a missing row means (Decision 8).** `reception_coverage_rules` is unique on `(day, hour)`, not `hour` alone — Monday morning and Friday afternoon are not the same staffing problem, and adding the day dimension after the fact would cost a migration, a seed backfill, and a rules-page rework, against one extra column and forty more seed rows paid up front. **A `(day, hour)` with no rule row reads as no minimum** — no warning is ever possible for that slot — rather than as zero-required-and-therefore-satisfied. Same practical outcome, but a deliberate reading of an empty table rather than an accident of one; `compute_coverage_issues` (`backend/app/api/routers/reception_rota.py`) simply has nothing to compare a count against when the map lookup misses.

**`ReceptionRole` has eleven values; coverage stays phones-only (Decision 13).** Beyond `phones`/`other`, `ReceptionRole` (`backend/app/models/enums.py`) also carries `prescriptions`, `registrations`, `front_desk`, `admin`, `online_triage`, `rotas`, `tasks`, `lunch`, `not_working` — plain tags on a slot, added via `ALTER TYPE ... ADD VALUE` (migrations 019 and 020, following 013's pattern) rather than a new table, since a role here is a label with no fields of its own. `reception_coverage_rules`/`compute_coverage_issues` deliberately were not extended to the new roles — `min_phones_staff` and the `phones_shortfall` check remain phones-specific; the new roles have no minimum-staffing concept. The frontend picks a role from a `<select>` (`RECEPTION_ROLE_ORDER`/`RECEPTION_ROLE_LABELS` in `frontend/src/lib/receptionRoles.ts`), replacing the old two-button toggle, which stopped working once there were more than two roles to choose from. `not_working` is a tag like any other, not a substitute for row deletion or for a leave entry — a `not_working`-tagged row counts toward nothing coverage-wise but is not itself "absent" in either sense Decision 10 means; it exists mainly for marking a template slot as a scheduled non-working period (e.g. alongside `lunch`) without deleting the row and losing the note/history that comes with it.

**Coverage now sees whole-day absence (Decision 10, resolved).** `reception_leave_entries` is `(staff_id, date)` and nothing else — no period column, no notes. Reception's day is twenty half-hourly slots, so an AM/PM split would be an arbitrary line through the middle of one, and the finer-grained case ("off from 2pm") was already expressible, more precisely, by deleting those slots or tagging them `not_working` (Decision 13). Leave is therefore a coarser fact layered on top of the per-slot mechanism, not a replacement for it: deleting a row is still how you say "not working this slot", and both remain true at once.

What leave changes is exactly one line of arithmetic. `compute_coverage_issues` loads the date's leave rows and skips those staff when counting `phones` holders; nothing about generation, row creation, or row deletion moves. A day generated before someone was marked off keeps every row it had, and generating a day for a date someone is already off *still copies their template rows* — the absence is expressed by the count and by the greyed row, never by missing data.

That greying is load-bearing, not decoration. Because the rows stay, a coverage warning reading "2 staff on phones, 3 required" would sit next to three visible `phones` chips in that column and read as broken arithmetic. `ReceptionRotaOut` therefore carries `staff_on_leave` (the same ids the count filtered on) alongside `sessions` and `issues`, and `ReceptionGrid` takes an optional `staffOnLeave` prop that dims the row and labels it — dims only: the cells stay clickable, since an admin may still want to retag or delete a slot on a day someone is off. `ReceptionSessionWriteOut` deliberately does *not* carry the field, since a session write cannot change who is on leave; the by-date cache's copy stays correct and there is nothing to re-splice.

**Reception leave is weekday-only on the way in, but not on the way out.** Bulk add skips Saturday and Sunday and reports the count, because reception is Monday–Friday throughout — `Day` has no weekend members and `POST /reception/rota` 422s a weekend date — so a weekend row could never reach a rota or a coverage count, and writing one would only leave inert rows in the entries table. Bulk delete is deliberately *not* weekday-filtered, mirroring the clinical bulk-delete: "clear this range" should also clear anything a single POST (which accepts any date at face value) put on a weekend.

**The two grids duplicate rather than share, deliberately (Decision 12).** `ReceptionGrid`/`ReceptionCellPopover`/`pivotReception.ts` are siblings of `MasterRotaGrid`/`RotaGrid`/`CellEditPopover`/`pivot.ts`, not a generalisation of them, and every one of their docstrings says so explicitly to head off a later "fix". The axes differ (staff × hour here vs doctor × day/period there), reception has no displacement/steal concept at all (several staff can legally share one `(day, hour)`, unlike a room), and there is no draft/committed or leave-derived inert cell state to reconcile. Forcing one abstraction across both would make each harder to read for a saving of very little code; `ReceptionGrid` is reused unchanged between the master template page (Task 7) and the day rota page (Task 8) — that is the only sharing this feature does, and it is sharing within reception, not with the clinical side.

**Shift-click range select is a UI-only batching convenience, not a new write path.** `ReceptionGrid` tracks a `{staffId, anchorHour, focusHour}` selection locally and, on save, composes an ordered array of per-hour payloads that the page writes with `await` in a sequential `for` loop — never `Promise.all` — against the same unchanged single-hour create/patch endpoints. Sequencing is deliberate rather than an easy default: on the day rota, every write response carries a freshly recomputed full `issues` list, and the cache write overwrites `issues` wholesale, so concurrent requests racing to land last (not necessarily the one computed against the final state) would leave the coverage panel and column warnings silently wrong until the next refetch. On an inactive staff row, a range save writes only the hours that already have a session — the absent-cell add affordance is a frontend gate (`create_master_session`'s docstring notes the backend deliberately performs no active-staff check), and range select must not offer a backdoor around it, so skipped hours are neither highlighted nor written. One cross-component constraint worth knowing before adding any other portalled surface to a cell: the cell's click handler sits on the `<td>` (so it catches both the filled-cell content and the empty-cell `+` button by bubbling), while the edit popover portals into `document.body` — and React bubbles synthetic events along the component tree, not the DOM tree, so clicks inside the popover arrive at the `<td>` as if they were clicks on the cell. `handleCellClick` therefore ignores any event whose target is not physically contained by the cell; without that guard, touching the role dropdown collapses the range to a single cell before Save fires.

**Adjacent same-role slots merge visually only, never in the DOM (Decision 16).** `ReceptionGrid` renders one `<td>` per half-hour slot and always will; when a slot's `(role, note)` pair matches the immediately preceding slot's, `receptionRunContinuations` (`lib/receptionRuns.ts`) flags it as a continuation, the run's internal divider is dropped, and the repeated chip is hidden. `colSpan` was considered and rejected: a merged `<td>` is one click target for up to twenty slots, which would destroy per-slot editing and the ability for a shift-click range to start or end mid-run, and would force the hour-keyed `{staffId, anchorHour, focusHour}` selection model above to be re-derived entirely. The repeat is hidden with `visibility: hidden` on the chip content *inside* the popover trigger, never on the trigger `<div>` itself — `visibility: hidden` also disables pointer events, and putting it on the trigger would make continuation slots unclickable, losing exactly the per-slot editing this approach exists to preserve. Absent cells deliberately never merge, with each other or with anything else: an absent cell is data ("not expected this slot", Decision 3), a genuinely different state from a `not_working` session (Decision 13), and each one owns its own per-slot `+` affordance. The merge key includes `note`, not just `role`, so a run's slots never differ in a way that would hide user-entered text.

**Hours counter is a client-side derivation, not a backend endpoint (Decision 17).** `ReceptionHoursPage` (`frontend/src/routes/ReceptionHoursPage.tsx`) shows each active staff member's weekly working hours, computed entirely in the browser from the already-fetched `useReceptionStaff()` and `useReceptionMasterSessions()` data: every master-template row is a scheduled half-hour slot, so working hours = (that staff member's rows, minus any tagged `not_working`) × 0.5. No new endpoint or stored field exists for this — the template list is at most a few hundred rows (see `list_master_sessions`'s docstring) and reception has no counters concept to extend (see "Why `reception_staff` is not `doctors`" above), so adding backend aggregation would cost a route and a schema for arithmetic the frontend can do over data it already holds. This is a weekly figure derived from the recurring template, not a per-generated-week actual — it does not reflect one-off edits made on a specific `ReceptionDayPage` week. Absent slots (no row at all) are already excluded, since only rows exist in the data — there is nothing to subtract for a slot nobody is scheduled for.

## Router surface

| Router | Responsibility | Key behaviour |
|---|---|---|
| `/reception/staff` | Reception staff CRUD | `GET` (`include_inactive` query param, default active-only), `POST`, `PATCH /{id}`, `DELETE /{id}` (unconditional soft delete — no committed-rota concept to block against). See "Domain: Reception Rota" above |
| `/reception/master` | The weekday master template: read and edit | `GET ""` (flat session list, all weekdays), `POST /sessions`, `PATCH /sessions/{id}` (verbatim `(role, note)` pair setter), `DELETE /sessions/{id}`. No displacement rule — several staff can share one `(day, hour)`, unlike a room |
| `/reception/rota` | The generated day: generation, editing, coverage | `POST ""` (copy the weekday template onto a date, active staff only — including staff on leave; weekend 422, existing-date 409), `GET ""` (`?date=`, 404 when ungenerated), `GET /{id}`, `POST`/`PATCH`/`DELETE` on `/{id}/sessions[/{id}]`, `DELETE /{id}` (the whole day, sessions cascade). Reads return `{…, sessions, issues, staff_on_leave}`; every mutating endpoint but the two 204 deletes returns `{session, issues}` with freshly recomputed coverage warnings |
| `/reception/leave` | Whole-day absence for reception staff | `GET` (`staff_id`/`from_date`/`to_date` filters), `POST` (404 unknown staff, 409 duplicate, weekend accepted), `POST /bulk` (range, weekdays only, returns `{created, skipped_existing, skipped_weekend}` counts rather than a per-date skip list), `POST /bulk-delete` (range, weekends included, returns `{deleted_count}`), `DELETE /{id}`. Read in exactly one place — `compute_coverage_issues` — see Decision 10 above |
| `/reception/coverage-rules` | Minimum phones-staffing rules | `GET` (all rows, ordered `day, hour`) and `PATCH /{id}` (`min_phones_staff` only) — deliberately no `POST`/`DELETE`, the `(day, hour)` row set is fixed by the seed |

`/auth` and `/users` (login, session, user management) are shared with the clinical rota and documented under "Router surface" in `documentation/architecture-clinical.md`.
