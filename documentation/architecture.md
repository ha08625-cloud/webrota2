# Rota Generator — Architecture Hub

Read this file first. It covers what's shared across the whole app; the two rota types each have their own detailed architecture doc, and you should only read the one relevant to what you're working on.

## Domains

The app is two independent rota systems plus a small third section, sharing one deployment, one login, and one landing page:

- **`documentation/architecture-clinical.md`** — the clinical rota: the generation engine (`backend/app/engine/`), doctors/rooms/clinic types, leave, duty, closures, staging, master rota, and the whole `RotaGrid`/`MasterRotaGrid`/`StagingGrid` frontend. This is almost all of the app's complexity, and reception doesn't touch any of it. It also documents **Signatures**, which is admin-staff document tooling rather than a rota: it has its own top-level route and shell, but it is small enough not to warrant a third architecture doc.
- **`documentation/architecture-reception.md`** — the reception rota: reception staff, the weekday master template, generated day rotas, and phone-coverage rules. Small, self-contained schema and API (`/reception/*`), its own `ReceptionShell` and grids. Shares nothing with the clinical rota except what's described below.

## Overview

A rota generator for a medical practice: generates a working rota from a master template over a configurable 1–4 week period, applying annual leave, duty assignments, clinic assignments, and room allocations, with interactive editing (drag-and-drop, cell edit menus, WFH, undo) in a web UI. Ported from a Google Apps Script project attached to a Google Spreadsheet, which it replaces; the port removed GAS's 6-minute execution limit. The reception rota is a later, independent addition covering front-desk phone-coverage scheduling — see "Domains" above.

**Status:** feature-complete and deployed to production (Railway, PostgreSQL), seeded, and verified end to end — a non-technical admin can generate, edit, and validate a rota without touching the API, including one-off holiday-cover changes via the staging step (see "Staging" and "Frontend: Staging" in `documentation/architecture-clinical.md`) without editing the master template. Access control is real per-user email/password login with DB-backed sessions. Outstanding work is listed below.

## Shared Frontend Infrastructure

The parts of the React app used by both rota types: routing shell, login/session handling, and the base HTTP client. Reference data pages, grids, and per-resource hooks are domain-specific and documented in each domain's own architecture doc.

### Application Shell & Providers

- **main.tsx** — the composition root. Creates the `QueryClient` (custom retry policy: no retries on any 4xx, since they will not succeed on retry; 5xx/network capped at 2 — so a 401 surfaces the login form immediately) and renders `QueryClientProvider > LoginGate > App`.
- **App.tsx** — routing and layout only, no providers: a top-level `BrowserRouter` (React Router v7, declarative mode — TanStack Query owns all server state, so no router loaders/actions) mounting one route per section. `/` is **LandingPage**, the shared entry point — nothing but a tile per section. Each section below it is a self-contained shell (`ClinicalShell`, `ReceptionShell`, `SignaturesShell`, `AdminShell`) owning its own header, nav and child routes; **no route, component, or nav item is shared between shells**, so a change to one section's navigation cannot affect another. Read the route and nav-item lists off `App.tsx` — they change often and any copy here goes stale.

  The clinical left nav is **not** flat: the five session-planning pages are collapsed into a single **Session Management** entry, which points at the first sub-tab and switches between them with the horizontal tab bar in `components/SessionManagementTabs.tsx`. That module owns the tab list and exports it, because `App.tsx` needs both the first tab's path (where the parent entry links) and the whole path set — `NavLink`'s own `isActive` cannot match sibling paths, so without an explicit `groupPaths` check the parent entry would un-highlight the moment you changed sub-tab. The tab bar is rendered by a **pathless layout route** wrapping the five, not by the five pages themselves, so it exists in one place and cannot drift; those pages consequently render no `<h1>` of their own, the active tab being the heading. The grouping is presentational only — every path is unchanged from when these were five top-level entries, so existing links and bookmarks still resolve. Nav structure is covered by `src/App.test.tsx`, which drives the real `App` via `window.history` (it owns its own `BrowserRouter`, so `renderWithProviders`' `MemoryRouter` cannot reach it).

### Theming & Colour

**The palette picker is currently retired** while the palettes are refined before launch. Nothing sets `data-theme` any more — `main.tsx` forces `default` rather than reading the stored choice, and the `<select>` in `ThemePicker.tsx` is commented out — so every user is on the default palette. The high-contrast toggle beside it is unaffected and still shipping. The machinery below is all still in place and un-retiring it is those two edits.

The app defines five light colour schemes (`default`, `ocean`, `forest`, `plum`, `sand`), listed in `THEMES` in `lib/themeStore.ts`. **Only five semantic tokens are themeable** — `background`, `surface`, `ink`, `border`, `accent`. They are declared in `tailwind.config.js` as `rgb(var(--color-x) / <alpha-value>)`, their channel values live in `index.css` (`:root` for the default, one `[data-theme="..."]` block per alternative), and switching a theme is therefore a variable swap, not a rebuild. The `<alpha-value>` form is not optional: several hundred sites use Tailwind opacity modifiers (`text-ink/70`, `bg-accent/10`, ...), and a plain hex or `rgb()` value would break every one of them. The two `theme("colors.…")` call sites that used to exist in `index.css` were replaced with direct `rgb(var(--color-…))` references for the same reason.

- **Everything outside those five tokens is pinned, deliberately.** The semantic state colours (validation red, warning amber) and the Q13 rota cell colour language (`BACKGROUND_CLASS` / `FONT_CLASS` in `RotaGrid.tsx`, `.closed-hatch`) carry meaning rather than decoration — a red cell must mean the same thing on every screen — so they are hardcoded palette values and must not be "finished off" into theme tokens by a later change. The same goes for the handful of remaining `bg-white` grid cells: they are cell fills, not surfaces.
- **Exports never follow the theme.** `exportStyles.ts` and `exportRotaPdf.ts` stay hex-literal so that two users with different themes produce byte-identical spreadsheets and PDFs. `exportStyles.ts` carries a black that happens to equal the default theme's `ink`; the comment there says explicitly that it does *not* track `--color-ink`, and that decoupling is the point.
- **High contrast is a separate axis, not a sixth palette** — `rota.contrast` in `localStorage`, a `data-contrast="high"` attribute, and CSS that composes with whichever `[data-theme]` block is active. It is an accessibility need rather than a look, which is why it stays exposed while the palettes do not.
- **The choice lives in `localStorage` under `rota.theme`** (`lib/themeStore.ts`), not on the user record. It is a cosmetic preference and does not follow a user between machines or browsers — accepted for now; moving it to `PATCH /users/me` later is purely additive (a nullable column and a field on `UserOut`) and needs no frontend restructuring.
- **The theme is applied in `main.tsx` before `createRoot`**, by setting `data-theme` on `<html>`. Doing it in a React effect instead would flash the default palette on every page load. While the picker is retired this call passes `"default"` explicitly, which also clears a palette a user picked before it was hidden — otherwise they would be stuck on it with no control to change it.
- **Accessibility gate:** a new theme must score no worse than `default` on the measured pairs (ink and its 70/60/50 opacities on both backgrounds, accent, `text-red-700`, and `border` against `surface`). Note that `ink/50` and `ink/40` are already below WCAG AA in the default palette; raising them is a separate piece of work touching ~89 sites and changing the app's look for everyone, and was deliberately kept out of the theming change.
- **Dark mode is deferred, not forgotten.** Every pinned colour above assumes a light surface, so a dark theme is not a fifth variable block — it needs the cell language and state colours re-derived first.

### Authentication Boundary

Enforcement is server-side (`get_current_user()` for authentication, `require_access` / `require_capability` for authorization, all in `deps.py`); the frontend's job is a real login form, attaching the session token, and recovering when it is missing or invalid. Any frontend permission gating is UX only — hidden nav entries and disabled buttons are a courtesy, the 403 is the boundary.

- **client.ts** attaches `Authorization: Bearer <token>` to **every** request (the whole API is gated, reads included), from `tokenStore.ts` (localStorage, so the token survives reloads). On any 401 it invokes the single listener registered via `onUnauthorized()`; `triggerUnauthorized()` lets the logout flow fire that same listener without a real 401 having occurred.
- **auth/LoginGate.tsx** wraps the entire app. No stored token shows the login form immediately with no request fired. A stored token calls `GET /auth/me` to verify it before trusting it — renders nothing while that check is in flight, success renders children, a 401 clears the stale token and falls back to the form. Also listens for the `onUnauthorized` broadcast mid-session, so an expired or revoked session drops back to the login form from anywhere in the app. On successful login it stores the token and calls `queryClient.resetQueries()` explicitly rather than relying on incidental remount behaviour.
- **Logout** lives in `App.tsx`'s nav (not LoginGate): `POST /auth/logout` is best-effort (a network failure must not block getting back to the login form), then the token is cleared, `queryClient.clear()` drops all cached data, and `triggerUnauthorized()` shows the login form immediately.
- **auth/AuthContext.tsx** holds the logged-in `AuthUser` and unwraps its **permission set** — the only thing the UI asks about, `access_level` never being consulted here. `useCanRead()` / `useCanWrite()` take no argument: each shell wraps its subtree in a `<PermissionAreaProvider area="clinical">` (or `reception` / `signatures` / `study_eoi` / `user_admin`), so a page or grid asks "may I write *here*" without knowing which section it is mounted in, and the ~30 existing call sites needed no edit when permissions replaced tiers. `useWriteGate()` spreads onto a control to disable it with an explaining tooltip; `useCanAdminUsers()` is the one area asked for by name, since the Administration shell is the thing being guarded. **Outside a provider the context denies everything** (`DENIED_PERMISSIONS`, the same shape as the backend's `DEFAULT_PERMISSIONS`), so a missing provider is a dead UI rather than a silent hole; `renderWithProviders` supplies the Manager preset by default and takes a `permissions` option, and `authWrapper()` does the same for tests using plain RTL `render()`.
- **Gating in practice**: the landing page renders only the tiles the permission set can enter, and each shell **redirects to `/` when the user cannot read its area** — hiding a nav entry stopped being enough once reads were gated, because a bookmarked `/reception/leave` would otherwise render a page of failed queries. Within a readable section the old behaviour stands: a read-only user sees the whole section with its write controls disabled rather than a truncated one. `RotaGrid` folds `canWrite` into its existing `editable` flag, so a read-only user gets the committed-rota rendering path; the cell popovers (`CellEditPopover`, `MasterCellEditPopover`, `ReceptionCellPopover`) return their children with no editor attached, and `LeavePlanningGrid` starts no selection. Export to Excel/PDF is *not* gated — both are built client-side from data already fetched.
- **One endpoint is deliberately unauthenticated**: the per-doctor `.ics` calendar feed, whose token in the path *is* the credential, because a calendar client cannot present a bearer token. It lives in its own router holding exactly one `GET`, listed in `main.py`'s `_UNGATED` alongside `/auth` and `/users` (which gates itself per-endpoint). Being in `_UNGATED` is load-bearing rather than cosmetic: `require_access` is itself declared `Depends(get_current_user)`, so the gate 401s an unauthenticated request before it ever reaches the permission check — a GET-only router registered in the normal loop would still require a session. `tests/test_api/test_authorization.py` holds the line: its two sweeps run every route in the OpenAPI schema (80 non-GET, 40 GET) against one permission set per preset plus the deny-everything set, asserting exactly 403 where the set does not reach and never 403 where it does — 720 cases, so a write added to the calendar router (which would be both unauthenticated *and* unauthorized) fails on the first run. A separate sweep asserts 401 without a session for every GET, with an explicit allowlist of exactly the feed path, so adding a path to that allowlist is a decision rather than a test fix. The feed itself is documented in `documentation/architecture-clinical.md`.
- **Self-service password reset** (`POST /auth/forgot-password` + `POST /auth/reset-password`, both unauthenticated by necessity). The gap it closes is the **lockout case** — the last remaining user administrator forgets their password and nobody can let them back in; convenience for everyone else is a side benefit, and `PATCH /users/{id}` remains the admin fallback. A request mints a row in `password_reset_tokens`, which mirrors `sessions` exactly: **only the SHA-256 digest is stored**, one hour to live, deleted on redemption, expired rows swept lazily on the next request for that user rather than by a cron job. Redemption deletes every session *and* every other outstanding reset token for that user. So do both password-change paths in `users.py` (`_invalidate_reset_tokens`) — without that, an attacker who requested a reset keeps a live token for up to an hour *after* the admin resets the password, so the very act of locking them out would leave them a way back in.
- **`forgot-password` always answers 204** — unknown address, inactive user, throttled, or a Mailgun failure alike. Anything else hands an unauthenticated caller an oracle for which addresses have accounts, undoing the care `login` takes to make its two failure modes identical. The send is therefore deferred to a `BackgroundTasks` task **for secrecy, not speed**: a synchronous POST to Mailgun on the "exists" path takes hundreds of milliseconds against single-digit ones on every other path, and that gap is measurable with a stopwatch. The task runs after `get_db` has closed the session, so it is handed plain strings and never the `Session` or the `User`. Two rate limits, defending different things: **one token per user per 3 minutes** (protects staff inboxes) and **40 reset emails per hour across all users** (protects the Mailgun quota, which the per-user limit does not — 3 minutes allows ~20/hour *per address*). Both are counts over `password_reset_tokens`, needing no state of their own, and both refuse indistinguishably from success. Matching is exact and case-sensitive **because `login` matches that way**; normalising here alone would let an address request a reset it could never log in with, so the forget view's confirmation has to tell the user to check the address is correct — a typo is otherwise indistinguishable from success. That confirmation also names the **junk folder**, which is not boilerplate: the From address is new and sends rarely, and the first live delivery landed in one. Both clauses are pinned by a test in `LoginGate.test.tsx`, because "shorten the success message" is exactly the tidy-up that would remove them.
- **`reset-password` answers 400, never 401.** This is load-bearing and must not be tidied later: `client.ts` fires the global `onUnauthorized` listener on *any* 401, which would clear the token and swap the reset view for a bare login form at the exact moment the user submitted a stale link, hiding the message telling them what to do. One message for every failure mode (unknown, expired, redeemed, or issued to a user since deactivated) so a guess cannot be graded. The token travels in the **request body, never the path**: `audit.py`'s `_REDACTED_KEYS` already covers `token`, but redaction only reaches the body — a token in the URL would land verbatim on the audit row, in Railway's access logs, and in any outbound `Referer`.
- **The reset page is a view inside LoginGate, not a route.** `main.tsx` renders `QueryClientProvider > LoginGate > App` and `BrowserRouter` lives inside `App`, while `LoginGate` renders the login form *instead of* its children when there is no valid token — so a `<Route path="reset-password/:token">` would never render for the logged-out user it exists for. The gate therefore owns all three views (`login` | `forgot` | `reset`), choosing the initial one by reading `window.location.pathname` on mount. **The reset pathname wins over a stored token**: sessions last 30 days, so the common case is a user still logged in *in this browser* who has forgotten the password they need somewhere else — checking `/auth/me` first would drop them into the app and they would never see the form. A reset pathname skips that check entirely and clears the stored token, which the reset is about to invalidate anyway. Restructuring so the gate sits below the router would be cleaner, but it moves the auth boundary every page depends on for one page's benefit. **This flow depends on `SPAStaticFiles`' `index.html` fallback for unknown non-`/api` paths** (see Deployment) — a cold `GET /reset-password/<token>` from an email client would otherwise 404; do not simplify that fallback away.
- **Accepted risks, recorded so they are not rediscovered as bugs.** (1) Mailgun's suppression list is per-domain and shared with the practice's other project on the same domain, so a staff member who bounced or reported spam there is silently suppressed for rota resets too — check the suppression list first when someone reports never receiving a link. (2) A Mailgun failure is invisible to the caller by construction; it logs at ERROR with the status and body, and the user's route out is the admin fallback. A missing `MAILGUN_*` variable logs at WARNING and no-ops, so local dev and CI need no configuration — WARNING rather than DEBUG because in production the symptom is email silently vanishing and that line is the only thing that says why; `email.is_configured()` doubles as the app's only signal for "this is a real deployment, not a laptop", which is what makes the `APP_BASE_URL` rule above decidable. (3) `forgot-password` writes an audit row per request carrying the submitted address intact, from any unauthenticated caller — the same exposure `login` already has; the global cap bounds the volume of *email*, not of rows.
- **components/ChangePasswordDialog.tsx** sits in every shell's header, open to every login whatever its permission set, and is the only user-management call a login without `user_admin` can make (`PATCH /users/me` — which is why the whole `users` router is `_UNGATED` and gates its three admin endpoints itself). A successful change deletes every session server-side, this one included, so it clears the token and calls `triggerUnauthorized(reason)` — the reason string is shown on the login form, which is why `onUnauthorized` listeners take an optional message.

#### Permissions: what a login may do

Authorization is a **per-user permission set**, not a tier. `backend/app/models/permissions.py` owns its shape, dependency-free, because the ORM model, the Pydantic schemas, the seed script and the Alembic migration all need the same literals:

| Permission | Type | Covers |
|---|---|---|
| `clinical` | `none` / `read` / `write` | the whole `/clinical` section |
| `reception` | `none` / `read` / `write` | the whole `/reception` section |
| `signatures` | bool | upload, delete, apply, and **view** signature images |
| `study_eoi` | bool | the EOI autofill tool |
| `user_admin` | bool | user management and the audit log |

- **Two levels, not six flags.** "Clinical rota, read only" is not a separate permission from "clinical rota"; it is the same permission at a lower level, so modelling it as a level halves the number of controls and makes contradictory states unrepresentable. The three booleans are booleans because there is no meaningful read-only view of a document generator or of user administration — and for `signatures` reading *is* the sensitive part, which is the reason this model exists at all: a scanned signature image is worth more outside this API than in it, so it should reach as few logins as possible, independently of who may edit a rota.
- **Stored as a `MutableDict.as_mutable(JSON)` column on `users`.** Portable `sqlalchemy.JSON`, not `JSONB`, because the tests build SQLite from the models via `create_all` while CI and production run Postgres. `MutableDict` is not decoration: a plain `JSON` column is not change-tracked, so `user.permissions["clinical"] = "write"` would silently fail to persist. A JSON column rather than five columns or an association table because the set is small, always read whole, and a sixth permission should not be a migration.
- **The default is deny-everything**, for the same reason `access_level` server-defaults to `nurse`: an accidental viewer is recoverable, an accidental administrator is a silent hole. It is not a *legal* saved state, though — an empty set is refused by a `model_validator` on the schema (422 on both `POST /users` and `PATCH /users/{id}`) and by a mirrored Zod refinement in the form, because a login that can reach nothing but its own password form is indistinguishable from a bug. Deactivating the user is how you say "no access".
- **Gating is centralised at router-registration time and is default-DENY. This is the property to preserve.** `main.py` registers every router bar three with `dependencies=[Depends(require_access(_AREA[module]))]`, so a new endpoint on an existing router is gated the moment it is written, and a new *router* is a `KeyError` at import until somebody classifies it in `_AREA` (a direct subscript, never `.get()`; two module-level assertions catch the reverse, a stale entry for a router that no longer exists). Per-endpoint gating was rejected on the numbers: with ~40 GET paths and ~80 non-GET operations, decorating each one is default-OPEN — the next endpoint anyone adds is unguarded until somebody remembers the call, and no test catches it. Same argument, same shape as `AuditMiddleware`.
- **`require_access` is a dependency *factory*, and has to be.** The area is resolved at registration time by closing over it, because it cannot be resolved per request: FastAPI 0.139 wraps each `include_router` call in an opaque `_IncludedRouter`, so a running request cannot ask which router served it. Router-level `dependencies=` alone would not do either — the levelled areas mix reads and writes in one router, so the read/write discrimination happens inside the dependency, off `request.method`. Safe methods (`GET`/`HEAD`/`OPTIONS`) pass at `read` or `write`; everything else needs `write`. The boolean areas admit every method when the flag is true and nothing when it is false, GETs included. Denials are 403 with a message naming the area, and a distinct one for "you can read this section but not write it" — a different problem for whoever reads the toast.
- **`_SHARED_READ` is the one hole, and it holds exactly two entries.** `GET /doctors` and `GET /reception/staff` are readable by any authenticated login whatever its permission set, because both populate a picker in *another* section: the Signatures page's Partner/Salaried picker, and `UserFormDialog`'s two linked-staff pickers — without which a `user_admin`-only login, the tightly scoped login this feature exists to make possible, could not create or edit a user. It is checked per `(method, route.path)` rather than per router because `GET /doctors/{id}/calendar-feed` must stay clinical while `GET /doctors` does not. Both payloads are innocuous (id/code/type/sessions/active/dates, and id/code/active — no token, no personal data). This is a permanent exception to default-deny, so a third entry needs justification as specific as these two, and `test_authorization.py` pins the set's contents rather than sweeping past it.
- **Four per-endpoint gates, `require_capability(name)`, and no more.** `users` is `_UNGATED` and gates its three admin endpoints itself, because `PATCH /users/me` must stay open to every login. The other three are **conjunctions** layered on top of their router's area gate: `POST /doctors/{id}/calendar-feed/rotate` and `DELETE /doctors/{id}` need `clinical: write` **and** `user_admin`, `DELETE /reception/staff/{id}` needs `reception: write` **and** `user_admin`. Each is kept that way deliberately — both staff deletes are irreversible, history-destroying purges, and rotating a feed token silently breaks someone's live calendar subscription. Mapping any of them to plain `area: write` would widen it to every rota editor.
- **`/admin/*` is its own section for a permission-shaped reason.** Users and Audit Log used to be routes inside `ClinicalShell`; once each shell redirects on `cannot read this area`, that would have locked a `user_admin`-only login out of the two pages its permission grants. They now live in `AdminShell` under `/admin/users` and `/admin/audit`, with `/clinical/users` and `/clinical/audit` kept as redirects.
- **`_active_user_admin_count` replaces the old last-manager guard.** `PATCH /users/{id}` 409s with "cannot remove the last active user administrator" rather than counting managers, which under a decorative `access_level` would have protected nothing. It is the one query that reads this column across users, on two PATCH paths only.
- **The presets are frontend starting points, not roles.** Manager / Rota admin / Reception admin / Documents / Read-only fill the form's controls and are then forgotten; nothing consults a preset at request time. They live in `models/permissions.py` anyway, because the seed script and the 010 migration's backfill both need to translate a tier they did not choose. Two are worth knowing: Reception admin grants `clinical: read`, since the reception rota is built against the clinical one; and **Rota admin does *not* grant signatures**, which the old `admin` tier did — that narrowing is the feature, but it means an existing admin login loses signature access the moment its permissions are set.
- **`access_level` survives as a decorative label and nothing else.** No gate consults it. It is kept because it is a native Postgres enum (dropping or adding a value costs an `ALTER TYPE` for no functional gain), because "Manager" is still a useful word on the Users page, and because the audit log snapshots it. Exactly three things read it: the display label, `PRESET_FOR_ACCESS_LEVEL` (seeding and the backfill), and that snapshot. Do not re-derive authorization from it.

#### Staff Identity: linking a login to a rota staff member

`users` and the two staff tables were entirely unrelated until this link existed — the app knew a request came from Charlie, but not that Charlie is `CH` on the clinical rota, which blocked every per-person feature.

- **Two nullable FK columns on `users`, each uniquely indexed.** `users.doctor_id` and `users.reception_staff_id`, added by migration `009_user_staff_links`. They live on `users` rather than on the staff tables because linking is a *privilege* grant — it decides whose rota is "yours", and in any future ticket what you may act on. The Users page needs `user_admin`; the Doctors and Reception Staff pages are writable by anyone with `clinical: write` / `reception: write`, so a column there would let a rota editor grant themselves a clinical identity. Two typed columns rather than a polymorphic `(kind, ref_id)` pair, because the schema has exactly two staff types and giving up referential integrity to save one column is a bad trade. The unique indexes give 0..1 : 0..1 semantics for free: both SQLite and Postgres treat NULLs as distinct in a unique index, so any number of users may be unlinked while no two users can claim the same staff row. Both columns may be set on the same user — a nurse who also covers reception is real, and allowing it costs nothing.
- **The link is manual, chosen by a manager on the Users page. There is no name matching, not even a suggested match.** `Doctor.code` is initials-style, `ReceptionStaff.code` is a human-typed display name ("Emily M"), and `User.name` is free text. Matching two free-text fields where a false positive shows someone a colleague's rota as their own is a bad trade for saving a one-off set of dropdown clicks at a practice with a few dozen staff, and a "suggestion" is what gets clicked through.
- **The link is orthogonal to the permission set; neither derives the other.** A partner who runs the rota needs write permissions *and* a doctor link; a practice manager needs no link at all; a locum may have a `Doctor` row and no login. So linking neither requires nor implies any particular permission, changing someone's permissions never touches the link, and vice versa. `AccessLevel.DOCTOR` stays exactly what its docstring says — a label, and since this change every `AccessLevel` value is one. This is the property most likely to get quietly fudged, so it is pinned from both directions by tests in `tests/test_api/test_users.py`, `frontend/src/components/UserFormDialog.test.tsx` and `frontend/src/auth/AuthContext.test.tsx`, the last two deliberately using a read-only user *with* a doctor link.
- **Deactivation and deletion never destroy a login.** A link to an *inactive* doctor or staff member is a supported state and is *shown* as such ("AB (inactive)") rather than silently cleared, since clearing it would lose the record of whose login that is — which is why `StaffLinkOut` carries `active` alongside `id` and `code`. Both staff `DELETE`s are hard purges (`/doctors/{id}`, `/reception/staff/{id}`) and both null the link column — `users.doctor_id`, `users.reception_staff_id` — instead of touching the user row (see the two domain documents). Deactivating a *user* leaves the link intact: they cannot log in, so it is dormant, and reactivating them restores what they had.
- **It reaches the frontend on `UserOut`, and there is no `/me`-style endpoint anywhere.** `UserOut` gained `linked_doctor` and `linked_reception_staff`, each nullable `StaffLinkOut`. `UserOut` is already the response model for `GET /auth/me`, `POST /auth/login`, `GET /users`, `POST /users` and both PATCHes, so one schema change serves both consumers — the logged-in user's own link, and the user administrator's view of who is already claimed (the Users page picker offers every staff row not claimed by *another* user, plus always this user's own current link). No endpoint was added by this feature. In particular the calendar feed needed none: `GET /doctors/{doctor_id}/calendar-feed` is already readable at every tier, so `CalendarFeedPage` simply **defaults its picker to the linked doctor and labels it as you**, which removes the page's one real failure mode (putting a colleague's rota in your calendar) while keeping the picker so a rota administrator can still fetch anyone's URL. `RotaGrid`, `LeavePage` and `LeavePlanningPage` seed "which row is me" the same way.
- **`AuthContext` is where the link is unwrapped.** It derives `linkedDoctorId` / `linkedReceptionStaffId` alongside the permission set, exposed as `useLinkedDoctorId()` / `useLinkedReceptionStaffId()`. Components call the hook rather than reading `user.linked_doctor?.id`, for the same reason they call `useCanWrite()` — the wire shape of the link lives in one file — and they read it directly rather than being handed a prop, so no page prop-drills identity into `RotaGrid`. (`useLinkedReceptionStaffId` currently has no consumer outside its own tests; it exists because the reception half of the link does, and the asymmetry is in the *defaults* built so far, not in the model.)
- **Everything built on the link only reads, and the link itself grants nothing.** Nothing here lets a user *write* on behalf of their linked staff member. Reads are no longer open to everyone — the permission set decides which sections a login may see at all — but that is the permission set's doing, not the link's: the link says who you are, not what you may see, and a doctor with `clinical: none` sees no clinical rota to be defaulted into. That was reviewed rather than defaulted into. Scoping a doctor tier to only their own data would touch nearly every `GET` in the app and change what the grids can render, so it is a large separate ticket, not an omission here.

### Audit Log

Shared infrastructure across both rota types and signatures, sat behind the same `user_admin` permission as user management (its router is registered under that area, so the boolean gates its GETs too). One row in `audit_log` per **non-GET** request that reaches the app: timestamp, acting user, method, templated route, real path, path params, the JSON request body, status code, the reason for a 4xx, duration and client IP. `backend/app/api/audit.py` holds the capture machinery, `backend/app/api/routers/audit.py` the single read endpoint, `backend/app/api/audit_descriptions.py` the plain-English translation of a row, `frontend/src/lib/auditDetails.ts` the humanising of a request body, and `frontend/src/routes/AuditLogPage.tsx` the page at `/admin/audit`.

Its purpose is **debugging** — reconstructing "the rota looks wrong, what happened to it?" — not compliance, and most of what follows falls out of that. Reads are not audited at all: this app holds staff scheduling data, not patient data, so a read log would be noise. Nor are there field-level before/after diffs; the SQLAlchemy `before_flush` approach that would produce them has no notion of user intent, so one rota generation would emit thousands of rows for a single click.

- **Capture is middleware, so coverage cannot drift.** Instrumenting ~81 non-GET endpoints by hand would be default-OPEN — the next `POST` anyone adds goes unaudited until somebody remembers the call, and no test catches it. `AuditMiddleware` makes a new router, or a new endpoint on an existing router, audited by default, exactly as `require_access` at `include_router` time makes it permission-gated by default. Same argument, same shape. The cost is that entries are HTTP-shaped, not domain-shaped: the log says `PATCH /rota/{rota_id}/sessions/{session_id} → 200` with the JSON that was sent, not "moved Dr AB from room 3 to room 5".
- **It is pure ASGI, not `BaseHTTPMiddleware`**, which would run the downstream app in a spawned anyio task and complicate both contextvar propagation and body handling. The status code is read off the `http.response.start` message via a wrapped `send`; `scope["route"]` and `scope["path_params"]` are read *after* awaiting downstream, because routing mutates the same scope dict. `scope["route"]` is populated by FastAPI's `APIRoute.matches`, not by Starlette, so the upgrade risk there is a FastAPI risk — it is read defensively so an upgrade degrades the log rather than breaking requests. `route.path` is router-local (no `/api/v1`, no `include_router` prefix) and `path_params` values are strings, pre-coercion.
- **Enrichment mutates a context object; it never calls `ContextVar.set()`.** This is the single most important rule in the module. Every router here is `def`, not `async def`, so FastAPI runs endpoints in a threadpool, and anyio executes them via `context.run(func)` on a **copy** of the context — a `.set()` performed inside an endpoint or a threadpooled dependency is invisible to the middleware afterwards. So the middleware `.set()`s once, to a mutable `AuditContext`, before calling downstream; `get_current_user`, the exception handlers and the login endpoint reach it with `current_audit_context()` and mutate fields in place. Getting this backwards produces a log that silently records nothing extra, with tests that pass.
- **The acting user comes from `get_current_user`**, which already holds the `User` row, rather than from a second token lookup — zero extra queries. A 401 records no user, which is correct. Three identity fields are frozen snapshots, copied in as plain values: `user_email`, `user_access_level` (the decorative label) and `user_permissions`, the acting set rendered as sorted-key JSON in a nullable `String`. The last is what makes "why was this allowed?" — or denied — answerable after the fact, since permissions are edited in place and the current row will not tell you what they were at the time. It is a `String` rather than JSON for the same reason the other two are: a snapshot is a value, not a live reference. An empty set stores NULL rather than `{}`, because that is a data problem worth seeing. Note for tests: `get_current_user` is dependency-overridden by every API fixture except `client_no_auth`, so any test asserting user capture must go through a real seeded user and a real login, or it asserts nothing while appearing to pass.
- **A 500 is captured only because the middleware catches it.** `app.add_middleware` places this inside Starlette's `ServerErrorMiddleware` but outside its `ExceptionMiddleware`, so an unhandled endpoint exception arrives here as an exception — `http.response.start` is never sent and the wrapped `send` never fires. The downstream await is therefore wrapped in `try/except BaseException`, which records status 500 and the exception repr, writes the row, and re-raises. Without that branch a 500 would produce no row at all.
- **Request bodies are stored, redacted.** Knowing someone sent `PATCH /rota/12/sessions/45` and got a 200 does not say what the cell was set *to*, which is the next question after almost every lookup, so the middleware drains `receive`, keeps the bytes and replays them downstream. Four rules keep it cheap: JSON only (anything else — notably the two multipart signature uploads — is passed through unbuffered and never lands in memory); a 16 KiB cap, above which the body is replaced by a `{"_audit": "body too large"}` marker; unparseable JSON stored as `{"_audit": "unparsed body"}`; and recursive redaction by key name through dicts and lists, replacing `password`, `new_password`, `current_password`, `token` and `password_hash` with `"[redacted]"`. That list is one module constant, which is where a new secret-bearing schema registers itself. Two honest caveats: this is *what was sent*, not *what changed*, so a no-op PATCH and a real one look identical; and a user who types their password into the login form's email box puts it in `email`, which is not redacted.
- **Audit failures never fail a request.** The row is written in its own session and transaction, in a worker thread, after the endpoint has committed and the response has been flushed — so it costs the client no latency — and any exception during the write is logged and swallowed. The log is therefore **best-effort**: a database problem loses entries silently. That is the right trade, since the alternative is an audit outage taking down rota generation.
- **Nothing is pruned, and `total` degrades before storage does.** This is the only table in the schema that grows without bound, but at this practice's scale that is tens of thousands of rows a year, and pruning a debugging log is self-defeating the first time you need last quarter. What gets slow first is the exact `COUNT(*)` behind each page view. The cheap fix when it arrives is to stop returning an exact total, not to start deleting rows.
- **The row is HTTP-shaped; the page is not. Translation happens at read time, in one table.** Capture-by-middleware buys drift-proof coverage at the cost of rows that read as `PATCH /rota/12/sessions/45 → 200`, which is unusable by the practice manager the page exists for. `audit_descriptions.py` closes that gap: `(method, route)` is a stable key — `route` is the *templated*, router-local path — so a dict maps it to a sentence ("Changed a session in rota 12"), and `status_code` collapses into five buckets ("Done", "Rejected", "Not allowed", "Not found", "System error"). Both reach the wire as Pydantic `computed_field`s on `AuditLogEntryOut`, so they cannot be forgotten at a call site. Three decisions hold this together. (1) **Derived at read time, never stored** — the wording is presentation, so rewording a sentence improves every historical row rather than only the ones written after the deploy. (2) **The table lives backend-side purely so a test can walk the route tree.** `test_audit_descriptions.py` recurses `app.routes` through FastAPI's `_IncludedRouter.original_router` (the same wrapper that makes `scope["route"]` router-local in the first place) and fails, with the missing keys formatted as paste-ready dict entries, if any non-GET route has no description — plus the reverse, an entry naming a route the app no longer serves. A frontend-side table would rot silently, which is the exact failure mode middleware capture exists to prevent, reintroduced one layer up. (3) **Sentences describe the attempt, in the UI's own vocabulary** ("Committed", "Scrapped", "Force-deleted" are the buttons on `RotaDetailPage`); whether it worked is the outcome column's job, so no sentence has to be keyed on status as well.

- **Ids inside the request body are resolved in the frontend, and only where a lookup exists.** `auditDetails.ts` turns `{"doctor_id":34,"room_id":7}` into "Doctor: AB, Room: 7" — keys de-underscored and stripped of a trailing `_id`, booleans as Yes/No, primitive lists joined, anything structured left as JSON. Resolution is a live lookup against `useDoctors()`/`useUsers()`, not a join, with two consequences worth stating: a name reflects how things stand *now*, not at write time, and a record deleted since falls back to `#34`. Neither lookup is required — a `user_admin`-only login gets a 403 from `/doctors` and the ids simply stay ids. Both name lookups are cosmetic by design; the frozen `user_email` on the row remains the authoritative record of who acted.

- **What this deliberately cannot show.** Rows record what was *sent*, never what was there before, so a deletion can only ever read "Deleted a leave entry" — by the time anyone looks, the row naming whose leave it was is gone — and bulk endpoints stay coarse. Fixing either means capturing a domain summary at write time in every endpoint, which is a much larger change and one that can silently rot. The description table cannot. Accept the coarseness unless somebody actually asks the "whose?" question.

- **`path` is deliberately unindexed.** The key debugging question is "show me everything that touched rota 12", answered by a `path` substring filter — portable across the SQLite the tests run on and the Postgres production runs on, unlike filtering the `path_params` JSON, which would need `->>` on one and `json_extract` on the other. A leading-wildcard `LIKE` cannot use a B-tree index, so an index there would cost a write on every audited request and serve no read, and making it genuinely fast would need `pg_trgm` and break that SQLite parity. The sequential scan is accepted. Only `at` and `user_id` are indexed. Two wrinkles live in the page's UI copy rather than being engineered around: the match has no word boundaries, so `/rota/12` also matches `/rota/120`, and the value goes through `.contains(..., autoescape=True)` so a typed `%` or `_` is literal rather than a silent wildcard.

### API Communication

- **client.ts** — centralised HTTP client over `/api/v1` (relative base by default: Vite proxy in dev, same-origin static mount in production; `VITE_API_BASE_URL` overrides). Non-2xx responses throw a plain `ApiError` object (`{status, detail}`), never an `Error` instance; 204 resolves to `undefined`.
- **types.ts** — hand-written mirrors of the wire contract (the Pydantic schemas' JSON shapes, with `Out` suffixes dropped: `ValidationIssue`, `Doctor`, `RotaSession`, ...). Enum types mirror `enums.py` by *value* (`"draft"`, not `"DRAFT"`). Also carries the TanStack Query `Register` augmentation setting `defaultError: ApiError`, so every `useQuery`/`useMutation` error is typed correctly with no per-hook generics. These mirrors drift silently until a `tsc` failure forces a fix — the known cost of not generating them from the OpenAPI spec.
- **Per-resource hook modules** — one file per resource under `src/api/`, each exporting TanStack Query hooks with hierarchical query keys. The convention: mutations invalidate their resource's key root rather than splicing caches, because reference data is cheap to refetch. The rota and master-rota grids are the deliberate exceptions and splice instead, to keep large grids from flashing — see `documentation/architecture-clinical.md`.
- **Pagination** — every resource except the audit log is fetched wholesale, because reference data is small enough that paging it would be pure ceremony. `api/audit.ts` is the one server-paginated list and the precedent to copy if a second one is ever needed: the whole filter object (offset included) goes into the query key, so each page is its own cache entry, and `placeholderData: keepPreviousData` keeps the previous page on screen instead of flashing an empty table while the next one loads. The pair matters together — without the placeholder, every page change drops back through `data === undefined`. `AuditLogPage` dims the table and disables the pager off `isPlaceholderData`, since otherwise a slow page change gives no feedback at all. The query string is assembled with `URLSearchParams` rather than template concatenation, which is where the single-parameter cases elsewhere (`?year=${year}`) stop scaling at nine optional filters.

## CI (`ci.yml`)

Three independent jobs on every push and pull request:

1. **Backend test suite** — `uv sync --extra dev`, then the full pytest suite (engine + API) on in-memory SQLite. API tests run `TestClient` with `get_db` dependency-overridden to a fresh SQLite engine per test, and with authentication stubbed out by default so most tests can exercise a route without logging in. The trap worth knowing before writing an API test: every client fixture writes to the one `app.dependency_overrides` dict on the one shared `app`, so a test may use **exactly one** client. `backend/tests/test_api/conftest.py`'s module docstring lists the fixtures and which tier each one authenticates as.

   **pytest is pinned `<9.1`** (`backend/pyproject.toml`). 9.1.0 regressed conftest collection when the command line interleaves directories — `pytest tests/test_api/a.py tests/b.py tests/test_api/c.py` silently loses `tests/test_api/conftest.py` for the *second* `test_api` file, so every test in it errors with "fixture 'client' not found". 8.3, 8.4 and 9.0 are all fine; the repro is three test files and two conftests with no project code in it. CI passes whole directories and never trips this, so it looks like a local-only oddity — but running exactly the files you touched is the normal way to work here, which is what makes it worth a pin rather than a note. Lift the ceiling once 9.1.x fixes it.
2. **Postgres migration validation** — upgrade/downgrade/upgrade round trip against a `postgres:16` service container, proving both migration directions and native enum type cleanup against a real Postgres before Railway ever runs a migration.
3. **Frontend gate** — Node 24, `npm ci` (requires `frontend/package-lock.json` committed), then typecheck / vitest / build, in that order so a fast typecheck failure doesn't wait on the slower build.

## Deployment

Single Railway service deployed from the GitHub repo, Root Directory `/` (repo root — both `backend/` and `frontend/` must be inside one build context, since FastAPI serves the built frontend same-origin).

**Build (`nixpacks.toml`, repo root).** Drives the Nixpacks build plan explicitly rather than relying on provider auto-detection, since neither `backend/pyproject.toml` nor `frontend/package.json` sits at the scanned root — `providers = ["python", "node"]` only puts the runtimes on PATH; every install/build command is written out with an explicit `cd`. Python installs into a manually created venv at `/opt/venv` (the nixpkgs `python3` has no bundled pip; `python3 -m venv` bootstraps one), which persists into the runtime image but is not on PATH at runtime. `frontend/dist` is built here. Node is pinned by overriding the whole `node:setup` phase (`nixPkgs = ["nodejs_24"]` plus a `nixpkgsArchive` on the nixos-25.05 revision) rather than by `NIXPACKS_NODE_VERSION`: that variable only changes the attribute name requested, and nixpacks v1.41's own node archive is a Nov 2024 snapshot with no `nodejs_24` in it and nothing else new enough for vite 8. Bump the archive, not just the package name, to move Node later. Deliberately no `[start]` section — the start command lives in exactly one place.

**Run (`railway.toml`, repo root).** `[deploy] startCommand` runs migrate-then-serve: `cd backend && /opt/venv/bin/alembic upgrade head && /opt/venv/bin/uvicorn app.api.main:app` — idempotent, so repeat deploys are safe. Health check on `/health`. The `/opt/venv/bin/*` prefixes are required, not stylistic: the venv persists into the runtime image but is not on PATH there.

**Serving.** FastAPI mounts `frontend/dist` at `/` (`mount_frontend()`; path overridable via `FRONTEND_DIST`) only if the directory and its `index.html` both exist, so a half-built dist never mounts. Registered routes always beat the mount; `SPAStaticFiles` serves `index.html` as the fallback for unknown non-API paths so client-side routes survive a hard refresh, while `/api/*` misses stay real JSON 404s **for every method**. That takes two guards, not one: `get_response` withholds the fallback from `/api/*`, but it only runs for GET and HEAD, because `StaticFiles` answers every other method 405 before consulting the path — right for a static file, wrong for an unmatched API path, which should answer exactly as it does with no frontend mounted. So `__call__` declines `/api/*` outright, ahead of the method check, and lets the 404 propagate to the app's exception handlers, audit row included. **The mount is a catch-all and is registered last, so anything added to `app.routes` afterwards sits behind it and never matches** — a real route registered the normal way is always ahead of it, which is why `test_audit.py`'s `boom_route` fixture moves its runtime route to the front of the list. Both of these are invisible in CI, which never builds `frontend/dist`; `tests/test_api/test_static.py` provokes them deliberately against a temp dist. No cache-control headers are set — if stale-frontend-after-deploy ever appears, that is where to look.

**Environment variables** (Railway dashboard):

- `DATABASE_URL` — the Railway Postgres service; must use the `postgresql://` scheme, not `postgres://`.
- `CORS_ORIGINS` — the production origin. Same-origin serving means the SPA never makes a cross-origin request, so this is hardening only; a correct value can only be verified via a cross-origin `curl`, not by watching the app work.
- `APP_BASE_URL` — the origin the emailed password-reset link is built from, no trailing slash. **Never derived from the request's `Host` header**: that would be host-header injection — an attacker sends `Host: attacker.example` with a `forgot-password` request for a victim's address, and the victim gets a genuine-looking email whose link posts their new password, and the token, to the attacker. One Railway variable closes it outright. It falls back to `http://localhost:5173` (the Vite dev server) **only where Mailgun is unconfigured** — a local run or CI, which delivers to nobody and reads the link out of a test or a log. Anywhere that *can* send, a missing `APP_BASE_URL` makes `forgot-password` **refuse to send and log at ERROR**, rather than posting a localhost link into a real person's inbox: a dead end they cannot diagnose, arriving from a system that looks like it worked. No token row is written on that path either, since an unusable token would still throttle the user and still count against the global cap. `routers/auth.py`'s `check_config()`, called from `main.py` at import time, logs the same misconfiguration once at **startup**, so a deploy that forgot a variable says so in its own log instead of looking healthy until the day somebody is locked out. It logs rather than raises — email is one feature, and a half-set variable must not take the whole rota offline while `PATCH /users/{id}` still resets a password by hand.
- `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_FROM` — outbound email for password resets (`backend/app/email.py`). Mailgun's **EU** HTTP API (`api.eu.mailgun.net`; posting an EU domain to the US endpoint returns a 401 that reads like a bad key and sends you looking in the wrong place), overridable via `MAILGUN_API_BASE` for tests. HTTP rather than SMTP: one authenticated POST, no connection handling and no outbound SMTP ports to be blocked on Railway. Domain and From are separate variables because the sending domain listed under Sending → Domains is not necessarily the From address's domain part; the reset mail uses a distinct local-part (`rota@…`) so the practice's two projects stay separable in Mailgun's logs. Reuses the already-verified domain rather than a new `rota.` subdomain, which would need fresh DNS and restart the deliverability question from zero — at the cost of the shared suppression list noted above.

Auth itself has no env var of its own. Every router endpoint bar the calendar feed requires a valid session and there is no fail-open mode, so a fresh environment has no way in until at least one user exists — see Seeding below.

**Seeding.** `seed/run_all.py` (rooms, doctors, system counters, master template — the four seeders in dependency order) is run manually from a local machine against Railway's public Postgres URL (`DATABASE_PUBLIC_URL`). There is deliberately no clinic-type seed — clinic types are entered via the frontend.

`seed/seed_users.py` bootstraps the first login and is deliberately separate from `run_all.py` — a one-off, run manually the same way, reading `SEED_USER_EMAIL`/`SEED_USER_NAME`/`SEED_USER_PASSWORD` from the environment with no hardcoded fallback, plus optional `SEED_USER_ACCESS_LEVEL` (defaults to `manager`). The seeded user's **permission set is derived from that tier** via `PRESET_FOR_ACCESS_LEVEL` — the default gives the Manager preset, i.e. everything — rather than read from a second env var, because a permissions-shaped env var would be a JSON blob nobody can type correctly under pressure; fine-grained editing is the Users page's job. Idempotent: re-running it against an email that already exists is a safe no-op. This is also the recovery path if every user is somehow deactivated, and — since `users.permissions` server-defaults to deny-everything — the only way a database ends up with a user administrator in it at all; every other user is managed from the Users page instead once at least one active login exists.
