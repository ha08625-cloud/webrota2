# Rota Generator — Architecture Hub

## Overview

A rota generator for a medical practice. Automates the creation of a working rota from a master template, applying annual leave, assigning duty doctors, school/college/care-home clinics, duty helpers, trainee supervision, and room allocations across a configurable 1–4 week period.

Originally a Google Apps Script (GAS) project attached to a Google Spreadsheet. The Python web app rewrite removes the 6-minute GAS execution limit, adds interactive editing (drag-and-drop, WFH status), and improves long-term maintainability.

**Status:** M1 (data layer), M2 (generation engine), M3 (REST API), M3.5 (backend additions for the frontend), M3.6 (persisted `RotaSession.template_type`), M3.7 (duty/slot compatibility checks), and **M4 (frontend, all 8 tasks)** are complete. The backend is deployed to Railway on PostgreSQL, seeded (rooms, doctors, system counters, master template), gated by the shared-token shim (`API_TOKEN` set in production and verified: 401 without the header), and verified end to end against production including the M3.5 surface. **M4 Task 8 (deployment) closed out the milestone:** the frontend now builds and serves from the same Railway service (`nixpacks.toml`, repo root, both `backend/` and `frontend/` in one build context), `CORS_ORIGINS` is set to the production origin (wildcard removed — same-origin serving makes CORS unnecessary), and a full production verification pass is confirmed: static SPA serving incl. client-side-route refresh and the `/api/*` 404 boundary, the token gate end to end, migrations, a real generate/edit/commit cycle, and the Q13 colour conventions eyeballed against the old spreadsheet. A non-technical user can now generate, edit, and validate a rota without touching the API — the M4 done-criterion is met. **A read-only Master Rota tab was added as a small post-M4 follow-up** (`GET /api/v1/master-rota/active`, not a numbered milestone) — see the REST API and Frontend sections below. **M4.1 (cell edit menu, Tasks 0–2) is complete**: Task 0 wired the undo/toast model into `RotaDetailPage` (correcting a gap the M4.1 review surfaced — the model and its library pieces were built at M4 Task 4, but nothing actually consumed them; see the Task 4 note below), Task 1 added the `set-room`/`set-role` endpoints (an additive amendment to the M3.5 contract), and Task 2 expanded the cell popover into the full edit menu with undo replay for the new entry kinds — see the M4.1 section below. **M4.2 (unified leave range form) is also complete**: the Leave page's three entry forms are collapsed into one Timetastic-style range form with edge half-day options, an Add/Remove mode toggle, and a read-only calendar preview — frontend-only, composing the existing bulk endpoints; see the M4.2 section below. Supervision (Phase 9C + Check 4) and master rota template *editing* remain deferred until after the project is otherwise complete; M5 (real auth) is also still outstanding.

## Data Layer (M1)

SQLAlchemy 2.0 models under `backend/app/models/`, one Alembic migration (`001_initial_schema.py`). The models and the migration are the authoritative schema record.

**Design decision made after M1's initial build:** `ClinicCounter` is shared-only — one row per `(doctor_id, clinic_type_id)`, regardless of how many schedule slots the clinic type has. An earlier design considered separate per-slot counters (`ClinicCounterMode`, nullable `day`/`period` on `ClinicCounter`); this was reversed and removed from the schema before M2 began, since no persistent database existed yet.

**Migration baseline is now frozen.** Through M1–M3, `001_initial_schema.py` was regenerated rather than incrementally migrated. Its final regeneration at M3 folded in the two counter-snapshot tables (18 tables total) and was deployed to Railway, making it the permanent baseline. All schema changes from here are additive migrations; `002_rota_session_template_type.py` (M3.6) is the first of these. M3.5 required no schema change.

**Postgres enum handling (resolved at M3).** `enum_col()` originally created a fresh named `Enum` type per column, which breaks on Postgres when the same enum appears in multiple tables (duplicate `CREATE TYPE`). Two-part fix: `enum_col()` now caches one shared SQLAlchemy `Enum` instance per Python enum (so `Base.metadata` deduplicates correctly), and the migration creates every native type explicitly once with `checkfirst` at the top of `upgrade()`, with columns referencing the types without re-creating them (`postgresql.ENUM(create_type=False)` on Postgres, plain `sa.Enum` on SQLite). Validated in CI by an upgrade/downgrade/upgrade round trip against a real Postgres 16 service container.

**M3.6 — `RotaSession.template_type` persisted (additive migration `002`).** Found during M4 Task 2/3 review: `NO_SURGERY`/`ADMIN_TIME` slots and a normal-but-currently-unassigned slot are byte-identical in `rota_sessions` (`room_id`/`clinic_type_id`/`role` all null), but the frontend's Q13 cell-colour rules and Q2 drop-target rules both need to tell them apart. `RotaSession` originally had no session-type column at all — the model docstring claimed it was "re-derivable from `MasterRotaSession` via (doctor, template_week, day, period)" at read time, but nothing actually implemented that re-derivation, and `RotaSessionOut` never exposed it. Resolved by persisting `template_type` directly on the row at generation time (`generate.py` already had it on hand via `SessionSlot.template_type`) rather than re-deriving it at read time — sessions are meant to be self-contained snapshots, and read-time re-derivation would silently rewrite the appearance of historical committed rotas once master-template editing (a deferred milestone) exists. Nullable, no backfill (system is pre-production); null renders as a normal session in both the API and the frontend. **As of M4.1 the invariant is deliberately weaker:** picking No surgery / Admin time in the cell edit menu overwrites the persisted value, so `template_type` now means "generation-time snapshot, possibly manually overridden" — an accepted, draft-only-in-spirit trade-off recorded in the M4.1 section below. This is an additive amendment to the M3.5 "frozen" contract, not a new milestone in its own right — see `docs/M3.6_implementation_plan.md`.

**M3.7 — duty/slot compatibility checks.** Found during M4 Task 3 review, tracing through Phase 4: it applies a pre-planned duty role to any slot with a template row, with no check on `template_type` at all — so a `NO_SURGERY`/`ADMIN_TIME` slot can legitimately end up with `role=duty_primary`, a state the frontend then has to render *something* for. Resolved two ways rather than one: (1) Phase 0 now hard-blocks generation if a duty doctor is pre-planned onto a `NO_SURGERY`/`ADMIN_TIME` template slot (`duty_on_incompatible_slot`, same severity tier as the existing duty-on-leave check) — WFH is deliberately excluded from this block, since a WFH template slot is realistically overridable (the doctor comes in for duty); (2) Phase 12 gained a new `role_on_incompatible_slot` warning covering *any* role (duty or clinic) on a `NO_SURGERY`/`ADMIN_TIME`/on-leave/WFH slot, which — because swap, move, and the session PATCH all re-run Phase 12 via `grid_utils.py` with no eligibility checks of their own — catches the same class of problem introduced post-generation by an edit, not just at generation time. This is also why `grid_utils.py`'s reconstruction was changed to trust the persisted `template_type` (M3.6) over re-deriving from the current active template: without that, a template edited after generation could silently change which past edits register as `role_on_incompatible_slot` warnings today. Resolves the M4 Task 3 rendering question the same review raised: when `template_type` is `NO_SURGERY`/`ADMIN_TIME` **and** a role is present, role colouring wins visually (the cell stays normal/interactive) — the Phase 12 warning, not the cell's own appearance, is what surfaces the conflict. WFH's background is unconditionally blank/white regardless of any role present, badge on top. Additive amendment to the M3.5 contract — see `docs/M3.7_implementation_plan.md`.

## Generation Engine (M2)

`backend/app/engine/` — pure Python, no FastAPI dependency. Structure:

```
engine/
  datatypes.py    SessionSlot, RotaGrid, CounterState, GenerationContext, ValidationIssue, GenerationResult
  week_map.py     generation-week <-> template-week <-> calendar-date mapping
  context.py      load_context(): one read-only snapshot of all reference data per run
  grid_utils.py   rebuild_rota_grid() / run_phase12_for_rota(): reconstruct a grid from persisted RotaSession rows (added at M3 for /issues and swaps)
  phases/
    phase0.py       pre-flight validation (hard errors abort; everything else is a warning)
    phase2.py       build the grid from the active template; load counters
    phase4.py       apply pre-planned duty roles
    phase5.py       clinic assignment (priority tier -> weighted counter -> alphabetical) + room resolution
    phase7_9a.py    Trainee/AHP room displacement (full-day, then single-session) + Partner/Salaried fallback
    phase9b.py      room swap elimination
    phase12.py      validation checks (warnings only)
  generate.py     orchestrator: runs all phases in order, writes the result in one transaction; also owns the draft lifecycle (get_active_draft, commit_rota, scrap_rota)
```

**Data flow:** `generate(db, config_id)` loads a `GenerationContext` once, builds a `RotaGrid` + `CounterState` in Phase 2, mutates both in place through Phases 4/5/7-9A/9B, runs Phase 12 as a read-only check, then persists everything via `_write_to_db()`. A Phase 0 error short-circuits before any grid is built or anything is written; every other finding is a collected warning that doesn't stop the pipeline.

**Design decisions locked in during the M2 build** (beyond what `M2_implementation_plan.md` and `algorithms.md` already specify — recorded here because several of these resolved real ambiguities or contradictions between those two documents, or between the plan and the M1 schema):

- **Clinic counters are shared** (see M1 section above) — `CounterState.clinic` is keyed `(doctor_id, clinic_type_id)`, no day/period dimension.
- **`RotaGrid.get_room_occupant()`** was added beyond the original datatypes sketch — Phase 5 and Phase 7-9A's displacement logic need to know *who* occupies a room, not just whether it's free.
- **`GenerationContext.preferred_rooms_by_doctor`** was added beyond the original context sketch — flattened, ordered `doctor_id -> room_ids`, with `room_type` preference rows expanded to concrete rooms at load time. Needed by Phase 5 and Phase 7-9A displacement.
- **`ClinicTypeInfo.schedules` is sorted deterministically** (weekday, then period) at load time — the original context sketch didn't specify an order, but Phase 5's counter fairness depends on processing order being deterministic.
- **Phase 5 room resolution** (a clinic's own `room_required` displacement) uses preference-list-only, no fallback — confirmed against `algorithms.md`'s "Room Preference Assignment" section, which explicitly scopes its C/W/SR fallback step to Phases 7-9A and 9B, not Phase 5.
- **Phase 7-9A room resolution** (Trainee/AHP displacing a Partner/Salaried) *does* get the C/W/SR fallback from `algorithms.md`, since it's in scope there. Pass 3 (Partner/Salaried's own fallback, no displacement) does not — it only ever tries the doctor's own preference list, per the plan's explicit wording.
- **Phase 9B priority table, row 5 was dropped.** Under strict top-to-bottom "first matching row wins" evaluation of rows 1-4, row 5's own scenario ("both prefer the same room; Partner wins") is unreachable — whenever one doctor prefers their own room and the other prefers the swap room, row 1 or row 2 already fires first, since those rows only look at each doctor's *own*-room preference in isolation. Confirmed with the user: row 5 collapses to the same default outcome as rows 6/7.
- **Phase 9B "preference match"** means the room appears anywhere in the doctor's `DoctorPreferredRoom` list, not restricted to their top preference or to a currently-free room.
- **Phase 12 Check 1 (duty coverage) was corrected mid-build.** The plan's original wording ("2 primary Monday, 1 Tue-Fri") contradicted `DutyAssignment`'s own unique constraint on `(date, period, duty_type)`, which allows at most one primary row per session on any day — caught by CI hitting the constraint directly. Corrected per `domain-model.md` and user confirmation: 1 primary expected every session; 1 secondary expected Monday AM/PM only, 0 elsewhere.
- **Phase 12 Check 3 (unresolved rooms) excludes on-leave slots and, since M3.5, WFH slots.** A doctor on leave still gets a `REQUIRES_ROOM` `SessionSlot` from Phase 2 (the template doesn't know they're on leave), and Phases 7-9A correctly never give them a room. Without this exclusion every leave day would register as a spurious validation failure. The WFH exclusion was added at M3.5: the session PATCH can set WFH on a `REQUIRES_ROOM` slot (clearing its room), and a doctor working from home needs no room — the warning must be silent while WFH is on and re-surface when it is toggled off.
- **`run_phase2()` takes a `db` parameter**, even though the M2 plan's `generate()` pseudocode sketch omitted it — Phase 2's own description requires DB access to load `ClinicCounter`/`SystemCounter` rows, so the sketch was treated as simplified rather than authoritative.

## REST API (M3)

`backend/app/api/` — FastAPI over the M1 models and M2 engine. All routers under `/api/v1`; `GET /health` at the root for Railway's health check. Structure:

```
api/
  main.py       app factory: CORS (CORS_ORIGINS env var, default *), router registration, /health, frontend static mount (M3.5)
  deps.py       get_db() session dependency; get_current_user() shared-token auth shim (M3.5)
  routers/      rota, clinic_types, doctors, leave, duty, rooms, counters, master_rota
  schemas/      Pydantic models, one module per resource + common (ValidationIssueOut)
```

**Rota lifecycle (the core M3 design).** A `GeneratedRota` is `draft` or `committed`, and **one draft exists globally** — generate returns 409 while any draft exists. When generation persists, it first snapshots every existing `ClinicCounter`/`SystemCounter` row's value into `rota_clinic_counter_snapshots` / `rota_system_counter_snapshots` (before `_write_counters()` runs, so values are exactly pre-generation), then writes counters and sessions in the same transaction. **Commit** deletes the snapshots; the live counter values become the baseline for future generations. **Scrap** (DELETE, draft-only) restores every snapshotted value, deletes counter rows created after the snapshot, and deletes the rota, sessions, and snapshots — all in one transaction. This means scrap also undoes counter edits made by swaps and moves during the draft period, and scrap-then-regenerate is equivalent to generating once from the original baseline.

**Swaps and moves** are session-level manual edits on a draft (409 on committed rotas); no regeneration. `swap-roles` swaps `(role, clinic_type_id)` between two sessions and adjusts `ClinicCounter` rows (get-or-create upsert, floored at 0 on decrement; a same-clinic-type swap is a counter no-op). `swap-rooms` swaps `room_id` only, no counter change. Since M3.5, **one side of either swap may be empty, making it a move** — this fell out of the counter guards naturally and is now documented contract with tests (`tests/test_api/test_swap_moves.py`) rather than accident; both sides empty is a 422 (previously a silent no-op). A room move deliberately leaves the source with an `unresolved_room` warning if its slot is `REQUIRES_ROOM` — the signal to reassign. Both endpoints re-run Phase 12 and return fresh issues, so a force-swap to an ineligible doctor is *allowed* — the API returns the warnings and the frontend owns the "are you sure" flow (apply-then-warn with undo, per the M4 plan). **Duty swaps do not write back to `DutyAssignment`** — that table is a generation input, not an audit trail; Phase 12 reads roles from the rebuilt grid, so re-validation stays correct.

**Cell-edit endpoints (M4.1).** `POST /rota/{rota_id}/sessions/{session_id}/set-room` and `.../set-role`, alongside the swap endpoints — deliberately **not** folded into the session PATCH, whose documented "safe partial update, no side effects on other rows" contract stays intact. Both are draft-only (409 on committed), re-run Phase 12, and return `{session, displaced_session, issues}`. `set-room` is a one-sided assign/clear with displacement: `room_id: null` clears the target's room with no displacement lookup and no `is_wfh` change; a set `room_id` displaces any same-slot holder (its `room_id` cleared to blank — **not reverse-swapped**; the resulting blank/`unresolved_room` state plus Phase 12 warnings are the honest signal) and clears the target's `is_wfh` if set (the PATCH `is_wfh=true` room-clear rule in reverse). Unknown rooms 404 via an explicit lookup, not FK errors — which surface as 500s on Postgres at flush. `set-role` is a **verbatim `(role, clinic_type_id, template_type)` triple setter**: it does not distinguish menu shapes from undo-restoration calls, it always writes the given triple exactly. Displacement applies only to steal-class assignments (duty roles; `role=clinic` with a specific `clinic_type_id`) — the displaced side is cleared to `None`/`None`, one-sided, not exchanged. If the written triple ends as `role=None` with `template_type` in `no_surgery`/`admin_time`, the target's room is also cleared (a no-surgery session silently holding a room would block it with no warning). Counter adjustments mirror `swap-roles` (get-or-create upsert, floored at 0), with a same-clinic-type reassignment guarded to a counter no-op. The nullable/clear shapes on both endpoints are what make every undo expressible — see the M4.1 frontend section.

**Grid rebuild (`engine/grid_utils.py`).** `/issues`, both swap endpoints, the session PATCH, and (since M4.1) `set-room`/`set-role` rebuild a `RotaGrid` from persisted `RotaSession` rows with a fresh `GenerationContext` per request (no caching). The persisted `template_type` (M3.6) is trusted when present — including a manually overridden one (M4.1) — per the M3.7 decision above; re-derivation from the active template is only the fallback for a null (pre-M3.6 legacy) value, and if the template entry no longer exists either, the slot falls back to `NO_SURGERY` — duty/clinic checks (which read roles) stay accurate, and the slot opts out of the unresolved-room check rather than warning against a template entry that no longer exists. (This paragraph previously described re-derivation as the primary path — stale wording from before M3.7, corrected at the M4.2 documentation pass; the M3.7 section above was already right.) `/issues` works on both draft and committed rotas.

**Master Rota (read-only) tab — small post-M4 follow-up, not a numbered milestone.** `GET /master-rota/active` returns the single active `MasterRotaTemplate` with its flat session list, joined to doctor/room codes the same way `_session_outs` does for `RotaSession`. `MasterRotaTemplate.is_active` is not schema-enforced unique (no partial unique constraint — see the model docstring), so the endpoint orders by `id` and takes the first match rather than `.scalar_one()`: a second active row must resolve deterministically, not 500 the page. `MasterRotaTemplateOut`/`MasterRotaSessionOut` use `template_id`/`session_id`, matching `RotaOut`/`RotaSessionOut`'s convention for objects embedded in a list alongside other `_id` fields (`doctor_id`, `room_id`) — not the plain `id` used by standalone CRUD entity schemas (`DoctorOut`, `RoomOut`, etc.). Template *editing* remains the deferred milestone in Outstanding Tasks below; this endpoint is read-only end to end, with no write path.

**Other API design decisions:**

- **ClinicType writes are single nested requests** (parent + schedules + doctor eligibilities + room eligibilities in one payload, one transaction). PUT uses the replace-children pattern — delete all child rows, insert the new set — safe for counter history because `ClinicCounter` is keyed on values, never on child-row FKs.
- **Doctor DELETE is a soft delete** (`active=False`), returning 409 if the doctor has sessions on a *committed* rota; draft-only history means scrap the draft first.
- **Transaction boundaries:** each mutating endpoint commits explicitly on success; any raised `HTTPException` leaves the session uncommitted, so partial work is discarded — including the `RotaConfig` row when generation fails Phase 0 (returned as 422 with the issues).
- **Duplicate detection** is via catching `IntegrityError` on commit (race-free) rather than pre-checking, mapped to 409.
- **Rooms are read-only** (seeded, 14 rooms). **Counters are read-only views** (joined with doctor/clinic names) of live values — committed baseline plus any in-progress draft's edits. Room types needed by the frontend's colour rules are mapped client-side from the one-time `/rooms` fetch — deliberately not duplicated onto the rota payload.
- The room_id/room_type XOR on room eligibilities and preferred rooms is enforced at the API boundary (Pydantic validators, 422) as well as by the DB check constraints.

**Decisions inherited from or reversed against the retired roadmap:**

- **Counter updates after manual edits — REVERSED at M3.** The roadmap specified "recalculate from scratch" after any manual edit, to avoid counter drift. What was actually built is incremental: swap-roles applies targeted increments/decrements to the affected `ClinicCounter` rows. Drift is prevented by the snapshot lifecycle instead — any accumulated error on a draft is wiped by scrap's wholesale restore, and commit turns the live values into the new baseline, so there is no long-lived incremental chain to drift. Full recalculation would also have required re-deriving counters from all historical rotas, which the schema never stored.
- **WFH handling — implemented at M3.5, one deliberate deviation from the roadmap.** The session PATCH sets `is_wfh` and, when toggling on, **clears `room_id`** (the roadmap's "separate boolean so toggling never destroys the room assignment" was superseded by the Q3 product decision: WFH frees the room for others immediately, which requires actually nulling it since room freeness is derived from session rows). Toggling WFH off does *not* restore a room — the slot warns `unresolved_room` until a room is manually assigned. The freed room is not auto-reassigned (carried forward unchanged).
- **Auth (M3.5 shim now; real auth remains M5):** enforcement lives entirely in `get_current_user()` at the router layer; real auth must require zero changes to route handlers or business logic. M5 done when the app rejects unauthenticated requests and the 2-3 admin users can log in (simple username/password first).

## API Additions for the Frontend (M3.5)

Small additive milestone done between M3 and M4 so the frontend starts against a stable, deployed, tested contract. No schema changes. Plan and rationale in `docs/M3.5_implementation_plan.md`; the durable design decisions:

- **`GET /rota`** — list of all rotas newest first (`created_at DESC, id DESC` — the id tiebreak matters for same-second creation), metadata only via `RotaSummaryOut` joined from `RotaConfig`. The frontend derives the active draft (at most one by design) and the committed history from it. No pagination (tens per year).
- **`PATCH /rota/{id}/sessions/{session_id}`** — draft-only partial update of `is_wfh` and/or `notes`. Field presence is detected via Pydantic's `model_fields_set`, so `notes: null` clears while an absent `notes` is untouched; an empty body is 422. Re-runs Phase 12 and returns `{session, issues}` (same pattern as the swap endpoints). WFH semantics as described in the roadmap-decisions section above; the matching Phase 12 WFH exclusion is described in the M2 section.
- **Null-side swap moves** — documented and 422-guarded as described in the Swaps and moves section above.
- **Auth shim** — `get_current_user()` compares an `X-API-Token` request header against the `API_TOKEN` env var (`secrets.compare_digest`). **Fail-open by design:** if the env var is unset, the API is open — this keeps local dev, the test suite, and CI working with zero fixture changes, and makes enabling auth a Railway env-var change with no deploy. The env var is read per-request (tests monkeypatch it; production can rotate without redeploy). `/health` and `/docs` stay open. The operational consequence: forgetting to set `API_TOKEN` in production silently leaves the API open — a 401-without-header check is part of the deployment checklist and was verified. This is deliberately not real auth (no users, no sessions); real auth is M5.
- **Frontend static mount** — `mount_frontend()` in `main.py` mounts `frontend/dist` at `/` (overridable via `FRONTEND_DIST`; default resolved from `__file__`, so working-directory independent) only if the directory *and its `index.html`* exist — the second check prevents a half-built dist from mounting. `SPAStaticFiles` serves `index.html` as the fallback for unknown non-API paths (client-side routes survive refresh) while `/api/*` 404s stay real JSON 404s; registered routes always beat the mount. Until M4 produces a build, the backend runs exactly as before. No cache-control headers are set — if stale-frontend-after-deploy ever appears, that is where to look.

## Frontend (M4)

`frontend/` — React 18 + Vite + TypeScript + Tailwind, built out task by task per `docs/M4_implementation_plan.md`.

**Task 1 (scaffold and API layer) — complete.** Decisions made in the course of this task that aren't otherwise visible from the code:

- **Node 24** (Active LTS), pinned via `engines` in `package.json` and matched in the CI `frontend` job's `setup-node` step — the two are meant to stay in lockstep; a future Node bump should update both together.
- **Tailwind v3.4**, not v4 — deliberately, to avoid introducing v4's CSS-first config model as a second new variable alongside the rest of the stack. Revisit if there's ever a reason to.
- **React Router v7 in declarative mode** (`BrowserRouter`/`Routes`/`Route`), not the data-router API — TanStack Query owns all server state per the M4 plan, so router-level loaders/actions would just create a second, competing place for server state to live.
- **API client (`src/api/client.ts`) defaults to a relative base URL** (`/api/v1`, overridable via `VITE_API_BASE_URL`). This is what makes the same client code work in both dev and production: in dev, `vite.config.ts`'s `server.proxy` forwards relative `/api/...` calls to a locally running backend on `:8000`; in production, FastAPI serves the built SPA same-origin (the M3.5 static mount), so relative calls need no base at all. Developing against the deployed Railway backend instead is a `.env.local` override, not a code change.
- **Auth recovery is explicit, not structural.** `TokenGate` wraps the app and switches to a full-screen token prompt on any 401 (via a listener registered with `client.ts`). On submit it calls `queryClient.resetQueries()` directly rather than relying on unmount/remount of children to trigger a refetch — the latter would have worked given the current component structure, but only incidentally. The `QueryClient`'s default `retry` also explicitly skips all 4xx (they won't succeed on retry) and caps 5xx/network retries at 2, so a 401 surfaces the prompt immediately rather than after three silent retries.

**Task 3 (grid, read-only) — complete.** Decisions:

**Task 4 (grid editing) — complete.** Decisions:

- **`@dnd-kit/core`, deliberately the older of two active dnd-kit generations.** `@dnd-kit/react` (built on `@dnd-kit/dom`) is the newer rewrite but pre-1.0 with a different API and far fewer dependents; `@dnd-kit/core` hasn't shipped a release in two years but has no deprecation notice and a much larger install base. - **Drag eligibility must check day *and* period explicitly** (`dragRules.ts`) — it is **not** guaranteed by which cells are mounted. Only one week's cells are ever in the DOM at once (so a cross-week drag is structurally impossible), but all ten day/period columns of the *active* week are mounted simultaneously, so a Monday-AM chip dropping on a Thursday-PM cell is a real, constructible case the API would happily apply (no server-side eligibility check) if the client didn't reject it first.

Undo still restores `is_wfh`/`notes` correctly; when the room can't come back too, the undo toast says so explicitly (`"Undone - room could not be restored, reassign it manually"`) rather than reporting a plain "Undone" that overstates what happened. Accepted for M4 — the issues panel itself always reflects the true current state regardless of what the toast says. A composite key of `check`+`week`+`day`+`period`+`message` would give a workable diff without backend changes if this ever needs tightening.
- **Toast is a small custom component, not a library** — a single slot, not a queue, since exactly one admin edits one draft rota at a time.

**Task 5 (clinic types) — complete.** Decisions:

- **The M4 plan's "room_required XOR wfh-allowed" rule does not exist anywhere in the real API.** Checked directly against the model, the Pydantic schema, and the router: `room_required` is a plain boolean with no counterpart field, no validator, no check constraint. The only XOR that actually exists is per-row on `RoomEligIn` (exactly one of `room_id`/`room_type`), which is a different, narrower rule about which rooms are eligible, not a clinic-type-level toggle. The plan text was simply wrong by the time this task was reached; the form matches the real contract, not the earlier plan wording.
- **Clinic types are now seeded via the frontend, not left permanently empty** — this task is what the earlier "clinic types not seeded" status note was waiting on. Production still had zero at the time this task shipped; nothing meaningful generates until an admin adds some.
- **Zod validates form state, not the wire shape directly.** Room-eligibility rows carry a client-only `kind: "room" | "roomType"` discriminant (matching the form's two separate "Add specific room" / "Add room type" controls), collapsed to the wire's `room_id`/`room_type` pair only at submit. This makes the XOR structurally unrepresentable in the form rather than merely validated — there's no state where both or neither are set to catch.
- **`mapValidationErrors` only maps top-level scalar fields** (`name`, `clinic_priority`) from a 422 onto form fields. Nested/row-level errors (e.g. the `RoomEligIn` XOR validator firing) fall back to a generic top-of-form banner rather than a guessed field mapping — the client-side schema and the form's own structure already prevent constructing the payloads that would trigger those server-side, so if one appears anyway, guessing which row it belongs to would risk misattributing a real problem rather than surfacing it honestly.
- **Editing preserves eligibility rows for since-deactivated doctors untouched.** `PUT` uses the replace-children pattern (delete all child rows, insert the new set), so anything the form drops on submit is permanently gone, not just hidden from that session. The add-doctor `<select>` is filtered to active doctors only; existing rows for an inactive doctor still round-trip through the form unchanged, with an `(inactive)` label, the same treatment Task 3's grid gives inactive doctors.
- **`@radix-ui/react-dialog`**, a separate package from Task 4's `react-popover` — Radix primitives are installed individually, not via the newer unified `radix-ui` package, for consistency with the Task 4 precedent. The dialog is conditionally mounted only while open (not always-mounted with just its `open` prop toggling) — an earlier version leaked form state across a Cancel-then-reopen-the-same-record cycle, since only the `key` changing (a different record) forced a remount; caught by review before this shipped.

**Task 6 (doctors, leave, duty) — complete.** Decisions:

- **The soft-delete 409's own suggested remedy was a dead end in the first drafted version — caught before shipping, not after.** `DELETE /doctors/{id}` 409s when the doctor has committed sessions and names `PATCH active=false` as the fix, but a first pass removed `active` from the form entirely with no other path to fire that PATCH — for exactly the doctors the 409 fires on (every real doctor, once the system is live), the displayed remedy was unreachable in the UI. Fixed: the 409 banner has a "Deactivate instead" action that fires the PATCH directly.
- **The doctors list is active-only with no reactivate path, by deliberate scope decision, not oversight — and this is a real, stated limitation.** A doctor deactivated (via the soft-delete flow above) drops out of the list and is not recoverable from the UI. `DoctorPatch` already supports `active: true`, so reactivation is a small addition when needed; a "show inactive" toggle is the natural next step.
- **Preferred rooms are structurally never desynced from `preference_order`.** The form's row type carries no `preference_order` field of its own; it's derived at submit time as array index + 1 (`toWireRows`), so "always contiguous 1..n, never duplicated" — required by the PUT endpoint's `ge=1` constraint and its duplicate-order 409 — holds for any array of rows rather than being an invariant a reducer has to maintain by hand across reorder/add/remove.
- **Reordering uses `@dnd-kit/sortable`**, a new dependency layered on the `@dnd-kit/core` generation Task 4 already chose (not a departure from that decision) — the purpose-built companion package for list reordering, rather than hand-rolling drag-to-reorder on bare `core`.
- **Preferred rooms are only editable once a doctor already exists.** The PUT route needs a real `doctor_id`; a newly created doctor is saved via plain POST first, and preferred rooms are added on a follow-up Edit. Editing itself is PATCH (scalar fields) then PUT (preferred rooms), sequential and **deliberately not rolled back on a PUT failure after a successful PATCH** — faking atomicity client-side would misrepresent what the server actually holds; a partial failure is reported honestly ("Doctor details saved. Preferred rooms could not be saved: ...").
- **Leave's add-row doctor select is active-only; the doctor *filter* select is not.** The API will happily create leave for an inactive doctor (it only 404s on an unknown id), but there's no legitimate reason to add new leave for someone no longer working here — while historical leave for a since-deactivated doctor must still be findable via the filter. Duty's add-row select follows the same active-only rule by analogy (not separately requested, but the same reasoning applies: no reason to assign new duty to someone inactive).
- **"Both AM+PM" leave entry is two independent POSTs (`Promise.allSettled`), not a combined endpoint** — there isn't one. A partial failure (e.g. the PM slot already exists) is reported per-period, not as one opaque error.

**Task 7 (counters panel) — complete.** Decisions:

- **Two flat, read-only tables** (clinic, system), not a pivoted doctor-rows x counter-type-columns matrix — matches the row-per-record pattern every other management screen in M4 uses, and the API already returns both lists pre-sorted by doctor code.
- **Weighted score (`raw_count / sessions_per_week`) is computed client-side — it isn't in either `ClinicCounterOut`/`SystemCounterOut`, despite `counter.py`'s docstring describing it as "computed at query time."** The computation actually lives only in the engine (`datatypes.py`'s `weighted_clinic_score`/`weighted_system_score`), never surfaced via the API. Replicated faithfully rather than approximated: `sessions_per_week == 0` renders as `∞` (checked directly against the engine functions, which return `math.inf` for exactly this case — a zero-session doctor scores as maximally loaded and is never preferred for allocation), not as missing data. A counter row whose `doctor_id` has no matching doctor (a failed join — shouldn't happen with `active_only=false`, but shouldn't crash the row either) is kept as a distinct "unknown" result rendered as `-`, so the two situations are never conflated in the UI.
- **`sessions_per_week` is parsed via `Number()` before dividing** — same Decimal-serialised wire string (`"10.0"`) as everywhere else it appears; a caught-before-shipping category of bug, not a real one that reached users.

- **Root Directory is `/` (repo root) in the Railway dashboard, not `backend/`.** It briefly lived at `backend/` (end of M3) to work around Nixpacks failing to generate a build plan when `backend/pyproject.toml` wasn't at the scanned root — correct for a backend-only deploy, but `Root Directory = backend` excludes `frontend/` from the build context entirely (not just "unbuilt" — genuinely absent from what Railway copies in), which would silently break `mount_frontend()`'s `FRONTEND_DIST` default once the frontend needed serving. - **`CORS_ORIGINS` set to the production origin; the wildcard is gone.** Same-origin serving means this doesn't change any in-app behaviour (the SPA never made a cross-origin request in production to begin with) — it's a hardening step, verified by a genuine cross-origin `curl` request rather than by observing the app work, since same-origin traffic can't distinguish a correct value from a still-wildcarded one.
- **Production verification confirmed** (full checklist, not spot-checked): static SPA serving including a hard-refresh on a client-side route (`FRONTEND_DIST` resolution against the real build, not just the path arithmetic on paper), the `/api/*` 404 boundary (a bad API path must stay a real 404, not fall through to the SPA's `index.html` fallback), `CORS_ORIGINS` via cross-origin `curl`, the token gate end to end (missing/wrong/correct token, persistence across reload), migrations ran clean, a real generate/edit/commit cycle with the committed state surviving a reload, and the Q13 colour conventions eyeballed against the old spreadsheet.

- **Task 0 shipped the page-level undo/toast wiring** described in the Task 4 correction bullet above, including replay for the pre-existing entry kinds. On replay failure the consumed entry is re-pushed (so undo is retryable) with an "Undo failed" toast; the Undo button is always rendered for drafts, disabled when the stack is empty (no layout shift, feature stays discoverable), and absent for committed rotas.

**M4.2 — unified leave range form — complete.** Frontend-only; **zero backend changes** (verified against `routers_leave.py`/`schemas_leave.py` at planning time — the bulk endpoints already had everything needed). The Leave page's three entry forms (single add, range add, range delete) are replaced by one form; the table, filter, and per-row delete are unchanged. Decisions:

- **The Timetastic pattern:** one date range with optional half-day options at the edges (First day: Full / PM only; Last day: Full / AM only), plus an Add/Remove mode toggle sharing the same fields. The rationale: a lone AM/PM session is a degenerate range (start = end), and real half-day leave overwhelmingly occurs at range *edges* ("off Wednesday lunchtime, back Thursday morning"). When `start === end` the two edge selects are replaced by a single "Day" select (Full / AM only / PM only), making the contradictory first-day-PM + last-day-AM state on one day **structurally unrepresentable** rather than validated away — `expandLeaveRange` still throws on it as a guard against future programmatic callers.
- **`expandLeaveRange.ts` (pure lib)** expands range + edges into 1–3 **disjoint** chronological segments — PM edge, interior `BOTH`, AM edge; a 2-day range with both half edges legitimately has no interior segment. Disjointness is what makes firing the segments concurrently safe, and is asserted as a property in its tests, not assumed. **Both modes share the same expansion**: Add maps segments onto `POST /leave/bulk`, Remove onto `POST /leave/bulk-delete`. All weekend logic is deliberately left to the server (bulk add skips weekends and reports them as skipped; bulk delete does not weekday-filter, so stray weekend entries are still cleared) — the client does none of its own.
- **Segments fire via `Promise.allSettled`**; created/duplicate/weekend counts (or `deleted_count`) are summed across fulfilled results into one summary line, and a failed segment is reported per segment alongside what did succeed — no rollback, no faked atomicity (the Task 6 PATCH-then-PUT precedent). Client-side validation mirrors the server's `MAX_BULK_RANGE_DAYS = 366` so its 422 is never the first line of defence.
- **The form's doctor select is active-only in *both* modes** — a deliberate semantics change from the old range-delete form, which allowed inactive doctors for historical cleanup. One doctor list keeps the unified form coherent; an inactive doctor's rows remain deletable per-row from the table, and the filter select still lists inactive doctors to find them.
- **Any date change resets the half-day selects to Full** — a deliberate superset of the minimum requirement (resetting only when crossing the single-day/multi-day boundary, where the two control shapes don't map onto each other): a half-day choice refers to a specific day and should not silently survive that day changing. On full success the dates clear but doctor and mode persist — entering several ranges for one doctor in a row is the common batch pattern. Remove mode keeps the `window.confirm` guard, its message extended to name any half-day edges.
- **`LeaveRangePreview.tsx`** is a read-only calendar rendered under the form once a doctor and valid dates are set: one mini month grid per calendar month the range touches, capped at 4 months with a plain-text fallback (so a typo'd year can't render dozens of grids), **Mon–Fri columns only**, each day cell split into AM/PM halves coloured by what the pending submission will do (add / already-booked-skip / remove / existing), with a mode-specific legend. Existing leave arrives via `useLeave(formDoctorId)` — the hook's cache key is already doctor-parameterised, so it coexists with the table's own filter query. **One documented blind spot:** a legacy weekend entry (created via the old single-add form or the raw API) doesn't render in the preview, though Remove mode still deletes it and the summary count includes it.
- **`useCreateLeave` stays exported from `api/leave.ts`** even though the page no longer calls it (the single `POST /leave` endpoint is untouched); removing it was explicitly out of scope.
