# M4 Implementation Plan — Frontend (PROVISIONAL)
 
**Status: draft for discussion. Not approved for coding.** The open questions
at the end must be resolved first; several will materially change the task
breakdown.
 
**Scope:** a React single-page app consuming the deployed `/api/v1` REST API:
rota generation and lifecycle controls, an interactive rota grid with
drag-based swaps, and management screens for clinic types (manual entry
happens here), doctors, leave, and duty. Plus a small set of backend
additions the frontend needs (identified below).
 
**Out of scope (deferred post-project, confirmed):** supervision (Phase 9C +
Check 4), master rota template editing. Auth remains a stub unless Q6 changes
that.
 
---
 
## Stack (from the roadmap, to confirm)
 
| Concern | Choice |
|---|---|
| Framework | React 18 + Vite + TypeScript |
| Styling | Tailwind CSS |
| Server state | TanStack Query (all API reads/writes; no separate client-state store to start) |

## Backend additions required (small, but blocking)
 
These are API gaps found by walking the frontend's needs against the M3
surface. Each is a half-day-or-less change plus tests, done as M4 Task 0
before frontend work consumes them:
 
1. **`GET /rota` (list).** There is currently no way to discover rotas —
   only `GET /rota/{id}`. The frontend needs the active draft (if any) and
   the committed history to render anything. Proposed: returns all rotas
   (id, status, created_at, start_date, num_weeks), newest first.
2. **`PATCH /rota/{id}/sessions/{session_id}`.** The architecture doc lists
   WFH drag-and-drop editing as an M4 feature, but no endpoint can set
   `is_wfh` on a session. Proposed: draft-only PATCH accepting `is_wfh` and
   `notes`, re-running Phase 12 and returning the session + issues (same
   shape as SwapOut's halves). No counter implications.
3. **Bulk leave creation (probably).** A week's holiday is 10 LeaveEntry
   rows; entering them one POST at a time from a calendar UI is clumsy.
   Proposed: `POST /leave/bulk` taking doctor_id + date range + periods,
   returning created entries, skipping duplicates rather than 409ing the
   whole batch. Depends on Q11 — if the leave UI is grid-click-per-session
   rather than range-based, this may not be needed.

## Proposed structure
 
```
frontend/
  index.html, vite.config.ts, tailwind.config.js, tsconfig.json
  src/
    api/
      client.ts          fetch wrapper (base URL from env), error normalisation
      types.ts           TS types mirroring the Pydantic schemas
      hooks/             one module per resource: useRota, useDoctors, ...
                         (TanStack Query queries + mutations, invalidation rules)
    components/
      layout/            app shell, nav, toasts
      grid/              RotaGrid, SessionCell, DragLayer, IssueBadge
      issues/            IssuesPanel (grouped by check, linked to grid cells)
      forms/             ClinicTypeForm (nested children), DoctorForm, ...
    pages/
      RotaPage           the main screen: grid + lifecycle controls + issues
      ClinicTypesPage    list + nested create/edit form
      DoctorsPage        list, edit, preferred rooms, soft delete
      LeavePage          calendar or table entry (Q11)
      DutyPage           duty assignment table
      CountersPage       read-only clinic/system counter tables
    App.tsx, main.tsx
  tests/                 Vitest + RTL; MSW handlers mirroring the API
```

## Open questions (resolve before approval)
 
**Q1 — Grid layout.** Doctors as rows and day/period as columns, like the
spreadsheet the practice already knows? One week visible at a time with week
tabs, or all weeks stacked? Is there also a room-centric view (the GAS
Room_Rota_V1 equivalent: rooms as rows), and is it needed in M4 or later?
 
**Q2 — Drag semantics.** A drag between two cells could mean swap-roles or
swap-rooms. How does the user choose — two explicit modes (a toolbar
toggle), or a chooser dialog on drop? A modifier key is not discoverable
enough for non-technical users, in my view. Also: is drag-to-empty-cell
(move rather than swap) expected? The API only supports pairwise swaps, so a
"move" would need either a backend addition or frontend restriction.
 
**Q3 — WFH editing.** Confirm the interaction: a toggle on the session cell
(click/context menu) rather than drag? The architecture doc says
"drag-and-drop, WFH status" but a toggle seems more natural. Either way
Task 0's PATCH endpoint covers it.
 
**Q4 — Notes.** `RotaSession.notes` exists. Should the frontend display and
edit notes in M4, or display-only, or ignore?
 
**Q5 — Force-swap flow.** The API applies a swap immediately and returns
warnings. So "are you sure" can only be implemented as either (a) warn
*after* applying, with an undo button that swaps back, or (b) a client-side
pre-check (eligibility data is all fetchable) shown *before* calling the
API, or (c) a new dry-run mode on the backend. (a) is simplest and honest
about what the API does; (b) duplicates engine logic in the frontend and
will drift; (c) is more backend work. My recommendation is (a). Decide.
 
**Q6 — Auth reality check.** The API is publicly reachable and fully
mutable by anyone with the URL, and M4 will make that URL more visible.
Deferring real auth is fine, but consider a minimal shim in M4: a shared
password checked by `get_current_user()` against an env var, sent as a
header by the frontend. Half a day of work. Are you comfortable deferring
even that, given patient-adjacent (though not clinical) data — doctor names,
leave dates?
 
**Q7 — Deployment topology.** Two options: (a) FastAPI serves the built
frontend as static files — one Railway service, no CORS, one URL;
(b) separate Railway static service — independent deploys, but CORS config
and two services to manage. I recommend (a) for this project's scale: add a
StaticFiles mount + catch-all to main.py and a build step to the Railway
config. Confirm.
 
**Q8 — Devices.** Desktop-only, or does anyone need to check the rota on a
phone/tablet? Drag-and-drop on touch works with dnd-kit but needs explicit
testing effort; read-only mobile is much cheaper than editable mobile.
 
**Q9 — Print/export.** The GAS system's output was inherently
printable/shareable (a spreadsheet). Does M4 need a print stylesheet or
xlsx/PDF export of a committed rota, or is on-screen viewing sufficient
until post-project?
 
**Q10 — Committed history depth.** Is viewing old committed rotas
read-only in the same grid enough, or is any comparison/reporting needed?
(Assume read-only view unless told otherwise.)
 
**Q11 — Leave entry UX.** Calendar-style (pick doctor, click/drag a date
range, choose AM/PM/both) or a simple table with add-row? Range entry
implies the bulk endpoint in Task 0.
 
**Q12 — Counter adjustment.** Counters are currently read-only via the API.
In the GAS system you could edit the sheet directly to correct a counter.
Is manual counter adjustment needed in M4 (a small PATCH endpoint + audit
consideration), or is read-only acceptable?
 
**Q13 — Look and feel.** Any constraints — NHS-adjacent styling, practice
branding, colour-coding conventions from the existing spreadsheet that
users expect (e.g. specific colours for duty/clinic/leave/WFH)? The
spreadsheet's colour language is worth preserving if users have years of
habit reading it.

The practice admin can, from a browser against production: generate a
