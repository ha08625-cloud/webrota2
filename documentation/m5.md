# Provisional plan - Data Model Cleanup: fold no_surgery/admin_time into SessionRole

## Motivation

`RotaSession.template_type` was added at M3.6 purely to distinguish two
states that were byte-identical under the old model: a `no_surgery`/
`admin_time` slot vs. a genuinely unassigned normal slot, since `role`
alone couldn't tell them apart. If `SessionRole` can express
`no_surgery`/`admin_time` directly, that ambiguity disappears and the
persisted `template_type` column has no remaining job at the generated
(`RotaSession`) layer.

This is **not** the master-template layer (`MasterRotaSession.session_type`)
— that table has its own reasons for the five-value enum and stays untouched. 

"Normal" (no other role) is
`role = None`, not `role = clinic` with `clinic_type_id = None`.
`phase5.py` only ever sets `role = SessionRole.CLINIC` when a doctor is
actually matched to a real clinic schedule slot (`slot.clinic_type_id =
clinic.id` and `slot.role = SessionRole.CLINIC` together, same line). A
plain working slot that isn't duty and isn't matched to any clinic
schedule simply stays `role = None` — the engine never produces
`role = clinic` with a null `clinic_type_id`. The M4.1 role menu's
"Normal clinic" entry should map to clearing `role` to `None`, not to
`clinic` + null type. Flagging this now since M4.2 changes `SetRoleIn`'s
shape anyway — worth fixing both at once rather than building the wrong
mapping first.

## Target end state

1. **`SessionRole` gains two members**: `NO_SURGERY = "no_surgery"`,
   `ADMIN_TIME = "admin_time"` (matching the existing `MasterSessionType`
   string values, so the wire representation doesn't change shape, just
   which field it lives on).

2. **Phase 2** (`phase2.py`, slot construction during real generation)
   additionally sets `slot.role = SessionRole.NO_SURGERY` /
   `ADMIN_TIME` when the master template's `session_type` is one of
   those two — alongside `slot.template_type`, which it keeps setting
   exactly as today. `SessionSlot.template_type` is untouched as an
   **engine-internal, generation-time field**: Phases 2, 5, 7-9A, and 9B
   still need to know `REQUIRES_ROOM` vs `PRE_ASSIGNED` to decide how to
   resolve rooms, and that's a real generation-time distinction, not
   redundant — only the *persisted, post-generation copy* of it is being
   retired (see point 6).

3. **Phase 4 and Phase 5's existing "skip if `slot.role is not None`"
   guards** (already there to avoid double-assigning duty/clinic onto an
   already-assigned slot) now also naturally skip `no_surgery`/
   `admin_time` slots, for free, once Phase 2 seeds those roles first —
   **needs verification during implementation**, not assumed; I haven't
   traced every guard in `phase5.py`/`phase9b.py` closely enough to
   promise this is a zero-line change there.

4. **Phase 12, `_check_role_on_incompatible_slot`**: the
   `no_surgery`/`admin_time` branch is deleted outright — it's now
   structurally impossible for a session to simultaneously be
   `no_surgery` and have a duty/clinic role, since they're the same
   single-valued field. The `is_on_leave`/`is_wfh` branches are
   unchanged (those remain genuinely independent booleans that can
   coexist with any role).

5. **Phase 12, `_check_unresolved_rooms`**: rewritten to warn whenever a
   "working" slot (`role` is `None`, `duty_primary`, `duty_secondary`,
   or `clinic` — i.e. **not** `no_surgery`/`admin_time`) has no
   `assigned_room_id`, isn't on leave, and isn't WFH. This drops the
   `template_type == REQUIRES_ROOM` gate entirely.

   **Behavior change to confirm, not just a rename:** today this check
   only fires for slots templated `REQUIRES_ROOM`; a `PRE_ASSIGNED`
   slot whose room later gets cleared by an edit (e.g. a room swap/move,
   or room-steal) does **not** currently warn — under the simplified rule
   it *would* warn, which I think is the more correct behavior

6. **`RotaSession.template_type` is
   dropped.** New additive migration, `007_drop_rota_session_template_type.py`.
   No backfill needed.

7. **`grid_utils.py`**: the `row.template_type` / `context.template_sessions`
   fallback-reconstruction block is deleted — it existed only to
   populate `SessionSlot.template_type` for Phase 12's old checks, both
   of which no longer need it (point 4 doesn't need `template_type` at
   all; point 5 doesn't need the persisted value once the check is
   role-based). This is a real simplification of that module, worth
   noting since architecture.md currently has a fairly detailed comment
   block there that will need rewriting, not just deleting.

8. **API/schema**: `RotaSessionOut.template_type` field removed.
   `RotaSessionOut.role` (already `SessionRole`) now carries the full
   picture. `MasterSessionType` import drops out of `schemas_rota.py`
   and `routers_rota.py` where it was only used for this.

9. **Frontend**: `types.ts`'s `RotaSession.template_type` field removed.
   `cellStyle.ts`'s no-surgery/admin-time branch reads `session.role`
   instead of `session.template_type` (and simplifies — no longer needs
   the "only reached when no role is present" comment, since that's now
   structurally guaranteed rather than an ordering assumption).
   `RotaGrid.tsx`'s `CellContent` "No surgery"/"Admin" badge conditions
   switch from `session.template_type === "no_surgery"` to
   `session.role === "no_surgery"` (same for admin_time).

10. **M4.1's `set-role` endpoint**: `SetRoleIn` no longer needs a
    separate `template_type` field — `role` alone now covers all six
    menu options (duty x2, clinic + specific type, clear-to-normal,
    no_surgery, admin_time). 

## What stays out of scope

- `MasterRotaSession.session_type` / the master template table and its
  five-value `MasterSessionType` enum — unaffected. `seed_master_rota.py`,
  `phase2.py`'s reading of the template, and the Master Rota
  tab all keep working exactly as they do today.

## Testing

Existing tests referencing `template_type` need updating, not just
extending — a broader set than typical additive work:

- `test_phase12.py` — both checks under test here change shape
  (`_check_role_on_incompatible_slot`'s no-surgery/admin-time cases,
  `_check_unresolved_rooms`'s PRE_ASSIGNED-exemption case, assuming
  point 5 is confirmed).
- `test_phase4.py`, `test_phase5.py`, `test_phase9b.py` — need cases
  confirming no_surgery/admin_time slots are correctly skipped once
  seeded as a role rather than only a template_type.
- `test_generate.py`, `test_grid_utils.py` — end-to-end generation and
  rebuild-from-persisted-rows coverage.
- `test_api_test_swap_moves.py`, `test_api_test_session_patch.py` — any
  fixture or assertion touching `RotaSessionOut.template_type` needs
  updating to drop the field.
- `test_models.py` / migration round-trip test — the new `003` migration
  needs the same upgrade/downgrade/upgrade CI coverage `002` got.
- Frontend: `frontend_src_lib_cellStyle_test.ts`, `RotaGrid_test.tsx`,
  `frontend_src_api_rota_test.tsx`-equivalent, and any fixture in
  `fixtures_masterRota.ts` / `frontend_test_fixtures_rota.ts` carrying a
  `template_type` field.

   Points to raise before you approve it:
1. The plan misses the edit-layer consequences of no_surgery/admin_time becoming roles. Everything downstream that gates on role now includes them: role chips presumably become draggable for those cells, and canDropRole in dragRules.ts only excludes leave/WFH targets — so dragging duty onto a no_surgery cell, which today produces a move-plus-warning, becomes a clean two-way swap where the dragger's own cell turns into no_surgery. Also, swapping two no_surgery sessions goes from a 422 ("nothing to swap") to a valid operation. None of this is necessarily wrong — a no_surgery slot being swappable between doctors is arguably a feature — but it's unexamined behavior change, and the plan needs an explicit decision: are no_surgery/admin_time chips drag sources, drop targets, both, or badge-only? Whichever you pick needs dragRules and RotaGrid tests.
2. There's a second silent behavior change in the unresolved_rooms rewrite beyond the PRE_ASSIGNED one the plan flags: WFH-templated slots. Today, toggling is_wfh off on a WFH-template session never warns (its template isn't REQUIRES_ROOM); under the role-based rule it will (role None, no room, not WFH). I'd call that a fix — a doctor now in the building with no room should warn — and the existing comment in _check_unresolved_rooms ("toggling WFH off re-surfaces it") becomes true for all slots rather than just REQUIRES_ROOM ones. But it should be in the plan and tests with the same explicitness as the PRE_ASSIGNED change, not discovered later.
3. Drop the PRE_ASSIGNED exemption. It was a generation-time proxy; post-edit, a roomless pre-assigned doctor is genuinely unresolved, and it also surfaces master-data errors (a PRE_ASSIGNED row with no room) instead of hiding them.
4. Smaller additions for the plan: point 7 should include a repo-wide grep for slot.template_type / template_sessions as a verification step, since after reconstruction every SessionSlot.template_type will be None on the Phase 12 re-run path and any remaining reader is a latent bug; the 003 downgrade should state that it re-adds the column but can't restore data (same pre-production reasoning as 002); and a one-line note on why is_wfh stays a boolean while no_surgery becomes a role would preempt the obvious "why not role = wfh too" question later (WFH is a modifier that coexists with leave and interacts with rooms; no_surgery is the session's state).
