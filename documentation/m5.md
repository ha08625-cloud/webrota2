# Plan

Add a derived per-doctor duty session count, exposed via `GET /api/v1/duty/counts` and displayed as two fixed-width columns (raw count, weighted score) beside each doctor chip in DutyGrid's left palette.

# Scope

**In scope**
- `GET /api/v1/duty/counts` — combined (primary + secondary) count per active doctor, derived live from `duty_assignments`, with optional `from_date` / `to_date` query params.
- New `DutyCountOut` schema and its export.
- Backend API tests.
- Frontend `DutyCount` type, `useDutyCounts()` hook, `counts` query key.
- DutyGrid palette layout change: widen panel, add `n` / `wtd` columns, en-dash fallback while loading.
- Default MSW handler for the new endpoint and updates to existing DutyGrid tests.

**Out of scope**
- No migration, no new `SystemCounterType`, no stored counter.
- No change to the Counters page, the generation engine, snapshot/scrap logic, the duty add-form, or the flat assignment table.
- The UI does not use the date-range params yet; they exist for future scoping (e.g. current-year fairness) so the wire contract does not need a v2.

# Design Decisions

1. **Derived, not stored.** The count is always exactly derivable from `duty_assignments` via LEFT OUTER JOIN + GROUP BY. A stored counter would need a `SystemCounterType` extension, a migration, snapshot/scrap semantics, and reset plumbing — none warranted.
2. **Combined count.** Primary/secondary is an artefact of the generation calculation, not a real-world workload distinction (user-confirmed). One `raw_count` sums both duty types.
3. **Date-range params on the API, unused by the UI for now.** `from_date` / `to_date` mirror `list_duty`'s existing filters and provide the future "reset" lever a derived count otherwise lacks (scope to a window rather than zeroing a stored row). Critically, the date filters must live in the JOIN's ON clause, not the WHERE clause — a WHERE filter on the outer table would collapse the LEFT JOIN into an inner join and drop zero-count doctors from the response.
4. **Rota-edit blind spot is a conscious decision.** Session-level duty swaps on a generated rota deliberately do not write back to `duty_assignments` (duty router docstring), so the count reflects the planned duty board, not post-generation edits. Accepted: the count is an aid for manual board assignment.
5. **All active doctors returned; typing filter stays client-side.** The endpoint returns every active doctor (zero counts included). DutyGrid's palette already filters to Partner/Salaried; the count lookup is a Map keyed by `doctor_id`, so the mismatch is invisible to both layers.
6. **Weighted score computed client-side.** DutyGrid already holds `doctorsById: Map<number, Doctor>` with `sessions_per_week`; `computeWeightedScore` / `formatWeightedScore` from `lib/weightedScore.ts` are reused directly. Consequently `DutyCountOut` does **not** carry `sessions_per_week` — that would create a second wire source for spw that could diverge from the doctors query, and it matches the existing `SystemCounterOut` pattern (carries `doctor_code`, not spw).
7. **Invalidation is free.** `useCreateDuty` / `useDeleteDuty` already invalidate `dutyKeys.all = ["duty"]`; keying the new query `["duty", "counts"]` means every add/remove (including the delete-then-create replace flow) refreshes the counts automatically. No mutation changes.
8. **No route conflict.** The duty router has no `GET /{duty_id}` (only `DELETE /{duty_id}`), so `GET /counts` cannot be shadowed by a parameterised route.

# Task 1: Backend — `DutyCountOut` schema and `GET /duty/counts` endpoint

**A — State of the world.** Nothing for this feature exists yet. The duty router currently has `GET ""` (list), `POST ""` (create, with M5 closure checks), and `DELETE /{duty_id}`. This task adds the counts endpoint, its schema, and tests. Nothing has been completed yet.

**B — Files and deliverables**

| File | Deliverable |
|---|---|
| `backend/app/api/schemas/duty.py` | Add `DutyCountOut` |
| `backend/app/api/schemas/__init__.py` | Export `DutyCountOut` |
| `backend/app/api/routers/duty.py` | Add `GET /counts` |
| `backend/tests/test_api/test_leave_duty.py` | New `TestDutyCounts` class |

**C — Instructions**

1. **Schema** (`schemas/duty.py`):

```python
class DutyCountOut(BaseModel):
    doctor_id: int
    doctor_code: str
    raw_count: int
```

No `from_attributes` config needed — rows are constructed explicitly in the router, matching the counters router pattern. Add `DutyCountOut` to the schemas package `__init__.py` exports alongside `DutyIn` / `DutyOut`.

2. **Endpoint** (`routers/duty.py`):

```python
@router.get("/counts", response_model=list[DutyCountOut])
def duty_counts(
    from_date: datetime.date | None = None,
    to_date: datetime.date | None = None,
    db: Session = Depends(get_db),
    user: dict = Depends(get_current_user),
) -> list[DutyCountOut]:
```

Query shape:

```python
join_cond = DutyAssignment.doctor_id == Doctor.id
if from_date is not None:
    join_cond = and_(join_cond, DutyAssignment.date >= from_date)
if to_date is not None:
    join_cond = and_(join_cond, DutyAssignment.date <= to_date)

rows = db.execute(
    select(
        Doctor.id,
        Doctor.code,
        func.count(DutyAssignment.id).label("raw_count"),
    )
    .outerjoin(DutyAssignment, join_cond)
    .where(Doctor.active.is_(True))
    .group_by(Doctor.id, Doctor.code)
    .order_by(Doctor.code)
).all()
return [DutyCountOut(doctor_id=i, doctor_code=c, raw_count=n) for i, c, n in rows]
```

Non-negotiable details:
- `func.count(DutyAssignment.id)`, never `count(*)` — with a LEFT JOIN, `count(*)` returns 1 for a doctor with zero assignments.
- Date filters go in the `outerjoin` ON condition (as above), never in `.where()` — see Design Decision 3.
- `.where(Doctor.active.is_(True))` is a filter on the outer (Doctor) side and is therefore safe in WHERE.
- Group by `(Doctor.id, Doctor.code)` — valid on both SQLite (tests) and Postgres (production).
- Verify the `Doctor` model's active flag column name against `backend/app/models/doctor.py` before writing the filter (the doctors router is the reference for the established pattern).

3. **Tests** (`TestDutyCounts` in `test_leave_duty.py`, using the existing `client` / `seeded` / `db_session` fixtures):
- No assignments: every active doctor appears with `raw_count == 0`, ordered by code.
- Assignments across multiple dates for one doctor: all rows counted (each assignment row is one session, not one distinct date).
- One primary plus one secondary for the same doctor: `raw_count == 2` (combined count).
- Inactive doctor excluded from the response even if they hold assignments.
- `from_date`/`to_date` filtering: assignments outside the window are excluded from counts, **and** a doctor whose only assignments fall outside the window still appears with `raw_count == 0` (this is the regression test for the JOIN-vs-WHERE placement).
- Insert assignments via `db_session` directly where the API's closure/secondary-Monday validation would get in the way (the existing legacy-duty test already establishes this pattern).

# Task 2: Frontend — type, hook, MSW handler, DutyGrid layout

**A — State of the world.** Task 1 is complete: `GET /api/v1/duty/counts` returns `[{doctor_id, doctor_code, raw_count}]` for all active doctors, combined across duty types, with optional `from_date`/`to_date` params (unused by the UI). This task consumes it in DutyGrid's palette.

**B — Files and deliverables**

| File | Deliverable |
|---|---|
| `frontend/src/api/types.ts` | Add `DutyCount` interface |
| `frontend/src/api/duty.ts` | Add `counts` key and `useDutyCounts()` |
| `frontend/src/test/msw/handlers.ts` | Default handler for `/api/v1/duty/counts` |
| `frontend/src/components/DutyGrid.tsx` | Palette layout: counts columns |
| `frontend/src/components/DutyGrid_test.tsx` | Updated fixtures + new assertions |

**C — Instructions**

1. **Type** (`api/types.ts`), next to the existing duty types:

```typescript
export interface DutyCount {
  doctor_id: number;
  doctor_code: string;
  raw_count: number;
}
```

No `sessions_per_week` — the weighted score is computed from the doctors query (Design Decision 6).

2. **Hook** (`api/duty.ts`):

```typescript
export const dutyKeys = {
  all: ["duty"] as const,
  list: () => [...dutyKeys.all, "list"] as const,
  counts: () => [...dutyKeys.all, "counts"] as const,
};

export function useDutyCounts() {
  return useQuery({
    queryKey: dutyKeys.counts(),
    queryFn: () => apiClient.get<DutyCount[]>("/duty/counts"),
  });
}
```

No date params in the hook for now; when the UI eventually scopes the window, extend the key to `counts(params)` at that point.

3. **MSW default handler** (`test/msw/handlers.ts`) — this is load-bearing, not optional: the test setup runs `onUnhandledRequest: "error"`, so without it every existing DutyGrid/DutyPage test fails the moment the hook is mounted:

```typescript
http.get("/api/v1/duty/counts", () => HttpResponse.json([])),
```

4. **DutyGrid layout** (`DutyGrid.tsx`):
- Call `useDutyCounts()` alongside the existing queries. Do **not** add it to the `doctorsLoading || dutyLoading` early-return gate — the grid should render while counts resolve, with en-dash placeholders.
- Build `countsById = new Map<number, number>` from the response (memoised on the counts data).
- Widen the left panel `w-40` → `w-56`.
- Add a small header row above the groups, right-aligned to match the columns: `n` (w-8) and `wtd` (w-10), styled like the existing group labels (`text-xs text-ink/50`).
- Each chip row becomes:

```
<div className="flex items-center gap-1">
  [DraggableDoctorChip — wrap in flex-1 container]
  <span className="w-8 text-right text-xs tabular-nums">{raw ?? "–"}</span>
  <span className="w-10 text-right text-xs tabular-nums">{wtd ?? "–"}</span>
</div>
```

- Keep the draggable ref/listeners on the chip itself, not the flex row — the count spans must not become drag handles.
- Weighted score: `formatWeightedScore(computeWeightedScore(raw, doctorsById.get(d.id)))`, only when `raw` is resolved; while the counts query is loading or a doctor id is missing from the map, render `–` (en-dash) in both positions. Note `formatWeightedScore` already renders `∞` for spw 0 and `-` for an unknown doctor; the en-dash is specifically the counts-still-loading state.

5. **Tests** (`DutyGrid_test.tsx`):
- Add a counts fixture to the per-test `server.use(...)` block: `http.get("/api/v1/duty/counts", () => HttpResponse.json(counts))`.
- Assert raw count and weighted score render beside a chip for a doctor with a known count and known `sessions_per_week` (e.g. raw 4, spw "8.0" → "0.50").
- Assert a zero-count doctor renders `0` and `0.00`.
- Assert en-dash placeholders while the counts query is unresolved (use a never-resolving or delayed handler for that one test).
- Confirm existing drag tests still pass — the chip wrapper change must not break the `duty-doctor-chip-{id}` test ids or drag activation.
