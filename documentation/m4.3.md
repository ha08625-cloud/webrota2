# Plan: Rollback of Committed Rotas (Multi-Level Chain)

## Scope

Extend the existing draft-only scrap machinery so that committed rotas can
also be undone, walking backwards through commit history one step at a time.
Each step is destructive: rolling back rota N requires N to currently be the
most recently committed rota, restores counters to their pre-N-generation
values, and hands the rota back into the normal draft lifecycle (editable,
re-committable, or scrappable). Rolling back N-1 then requires N to already
be gone (scrapped) first — the chain cannot be skipped or accessed
out of order.

Explicitly out of scope for this iteration: pruning/archival of old
snapshots, a non-destructive "revert but keep history" mode, and any
frontend work (though `committed_at` is exposed in the API now — see API
changes — so the eventual frontend ticket needs no backend follow-up).

## Why this is tractable here

Two existing invariants make a strict, ordered chain sound rather than
requiring a full counter ledger:

- **Committed rota sessions are immutable** (409 on edit, 409 on swap)
  — so a committed rota's counters cannot drift after commit except
  through the *next* generation run.
- **At most one draft exists globally at a time** — so counter mutation
  is always serialized: generate, commit, generate, commit, ... The
  post-commit baseline of rota N is always exactly the pre-generation
  snapshot of rota N+1. Nothing else touches counters in between.

That means restoring N's snapshot and deleting N always leaves the
counters in exactly the state N-1 left them in — no replay or ledger
needed, provided rollbacks happen in strict reverse order.

Verified against the current codebase: the `/counters` router is
read-only, all edit endpoints are draft-only, clinic-type deletion is
409-blocked while counter rows exist, and doctors are soft-delete only.
One assumption to record: the chain also assumes nobody re-runs
`seed_system_counters` against a live database between commits — an
operational rule, not a code change.

## Design decisions

1. **Snapshots become permanent, not transient.** `commit_rota()` currently
   deletes `RotaClinicCounterSnapshot`/`RotaSystemCounterSnapshot` rows
   immediately (`_delete_snapshots`). That call is removed. A snapshot now
   persists for the life of its rota — it becomes an audit record of "counter
   values immediately before this rota was generated," not a short-lived
   undo buffer for the currently-open draft.

   Consequence for FK lifetimes: a clinic type referenced by a committed
   rota's snapshot is now undeletable via a snapshot FK violation as well
   as the existing live-counter-row block. In practice a snapshot row for
   clinic type X only exists where a live `ClinicCounter` row for X also
   exists, so deletion was already blocked — but the 409 detail in
   `delete_clinic_type` now has a second cause; add a comment there.

2. **Ordering is explicit, not inferred.** Add a nullable
   `GeneratedRota.committed_at` (DateTime, set on commit, cleared on
   rollback). "Most recent committed rota" is `status == COMMITTED` ordered
   by `committed_at desc, id desc` (id tiebreak matching the existing
   `created_at DESC, id DESC` pattern in the list endpoint), queried
   directly — not derived from the single-draft invariant. This keeps the
   ordering check correct even if the single-draft rule is ever relaxed
   later; the two invariants shouldn't be silently load-bearing for each
   other.

3. **`committed_at = NULL` hard-blocks rollback.** Any rota committed
   before this feature shipped has `committed_at = NULL` *and had its
   snapshots deleted at commit*. The restore logic interprets "counter row
   absent from snapshot" as "created after the snapshot, delete it" —
   run against a rota with no snapshot rows, it would delete every counter
   row in the system. So `rollback_commit()` raises `ValueError` (router:
   409, "committed before rollback support existed") when
   `committed_at is None`. This makes deleting the existing test rotas a
   cleanup nicety, not a load-bearing precondition.

   Belt-and-braces second guard: also refuse if the rota has zero snapshot
   rows. In a seeded system, system counters guarantee at least one
   snapshot row per legitimate generation, so an empty snapshot always
   means something is wrong.

4. **No new status.** A rolled-back rota goes `COMMITTED -> DRAFT`, the
   same status a freshly generated rota has. It re-enters the existing
   draft lifecycle wholesale — editable via the same endpoints, scrappable
   via the existing `scrap_rota()`, re-committable via the existing
   `commit_rota()`. No new state machine, no new "which endpoints work on
   which status" rules to document or test.

   Re-commit self-heals the chain ordering: committing a rolled-back rota
   goes through the same `commit_rota()` code path, refreshing
   `committed_at` to now, which correctly re-establishes it as the most
   recent commit.

5. **Rollback and delete are two separate calls.** `rollback_commit()`
   only restores counters and flips status — it does not delete the rota
   or its snapshot. Deleting is `scrap_rota()`'s existing job, called
   afterwards if the user wants the rota gone. This means a user who
   rolls back and changes their mind can simply re-commit instead of
   losing the rota.

6. **The single-draft constraint is what enforces strict order — reuse
   it, don't reimplement it.** Because rolling back a commit produces a
   draft, and only one draft can exist globally, `rollback_commit()` on
   any rota other than the most recent committed one will already be
   blocked by "a draft exists" (if the more recent one hasn't been
   scrapped yet) or by the explicit `committed_at` ordering check (if it
   has). This is a bit implicit, so it needs a clear docstring/comment —
   there is deliberately no separate locking mechanism.

7. **Unbounded storage, accepted for now.** Because snapshots are no
   longer deleted at commit, `rota_clinic_counter_snapshots` /
   `rota_system_counter_snapshots` grow by roughly
   `(doctors x clinic_types) + system rows` for every rota that is ever
   committed and never rolled back. Bounded per-row but unbounded in
   total. No retention/archival policy is proposed here — flagged as a
   known follow-up, not solved in this pass.

## Resolved questions (from review)

1. **Pre-existing committed rotas with `committed_at = NULL`.** They are
   test data (system not live) and will be deleted manually — but the
   code no longer depends on that: NULL hard-blocks rollback (Decision 3),
   closing the empty-snapshot counter-wipe hole.
2. **Rollback endpoint response.** `RotaOut`, mirroring commit; frontend
   routes into the same draft view as a fresh generation.
3. **Does `commit_rota()` need a mid-chain guard?** No. A rollback always
   leaves the system in a valid single-draft state before returning, and
   re-commit refreshing `committed_at` self-heals the ordering. The only
   change commit needs is setting `committed_at` and keeping snapshots.

## Data model changes COMPLETE

- `GeneratedRota`: add `committed_at: Mapped[datetime.datetime | None]`,
  nullable, no default. Set in `commit_rota()`, cleared in
  `rollback_commit()`.
- New Alembic migration, additive-only (matches the pattern of 002/003/004)
  — nullable column, no backfill. Existing committed rotas read as
  `committed_at = NULL`, which per Decision 3 means "not rollbackable".
  The existing test rotas on Railway will be deleted manually (direct SQL;
  the system is not yet live) — but nothing breaks if they aren't.
- No changes to `RotaClinicCounterSnapshot` / `RotaSystemCounterSnapshot`
  schemas — only their lifecycle changes (no longer deleted at commit).

## Engine changes (`generate.py`) COMPLETE

- `commit_rota()`: remove the `_delete_snapshots(db, rota_id)` call; set
  `rota.committed_at = datetime.now(timezone.utc)` alongside the existing
  `status = COMMITTED`.
- New `rollback_commit(db, rota_id) -> GeneratedRota`:
  - Load rota; `ValueError` if not found.
  - `ValueError` if `status != COMMITTED`.
  - `ValueError` if `committed_at is None` (pre-feature commit, no
    snapshot exists — Decision 3).
  - `ValueError` if `get_active_draft(db) is not None` (mirrors the
    generate() 409 rule — rollback produces a draft, so the same
    single-draft constraint applies).
  - Query most-recent committed rota by `committed_at desc, id desc`;
    `ValueError` if it is not this `rota_id`, with a message naming the
    rota that must be rolled back first.
  - `ValueError` if the rota has zero snapshot rows (belt-and-braces,
    Decision 3).
  - Restore counters using the same logic already in `scrap_rota()`
    (load this rota's snapshot rows, apply `value_before` to existing
    counter rows, delete counter rows absent from the snapshot, recreate
    snapshotted rows that no longer exist live). Factor this out of
    `scrap_rota()` into a shared private helper (e.g.
    `_restore_counters_from_snapshot(db, rota_id)`) rather than
    duplicating it — two callers, identical semantics.
  - Set `status = DRAFT`, `committed_at = None`. Flush. Do **not** delete
    the snapshot rows — `scrap_rota()` already deletes them when/if the
    rota is subsequently scrapped.
- `scrap_rota()`: no logic changes needed (beyond the restore-helper
  extraction). It already only operates on `status == DRAFT`, which is
  exactly what a rolled-back rota becomes.
- Docstring updates required by Decision 1 (snapshots now permanent):
  - `counter_snapshot.py` module docstring — currently says "committing
    simply deletes the snapshot" and "at most one rota's snapshots exist
    at a time — bounded". Both false after this change.
  - `_snapshot_counters()` docstring — the "at most one draft exists at a
    time" bounded-storage claim.
  - `commit_rota()` docstring — "delete its snapshots" line.

  One thing beyond what the plan spelled out: the "most recently committed" query orders by committed_at desc, id desc. Postgres's default is NULLS FIRST on DESC — so without an explicit nullslast(), a legacy rota with committed_at = NULL would sort as if it were the most recent commit, not the oldest, which would have broken the ordering check for exactly the legacy rows Decision 3 is trying to hard-block. Added .nullslast() explicitly. 

## API changes (`routers/rota.py`) COMPLETE

- New endpoint: `POST /rota/{rota_id}/rollback-commit`.
- Map `rollback_commit()`'s `ValueError`s to HTTP responses:
  - not found -> 404
  - not committed -> 409
  - `committed_at` NULL / no snapshot -> 409 ("committed before rollback
    support existed and cannot be rolled back")
  - active draft exists -> 409 ("scrap or commit the current draft first")
  - not the most recent commit -> 409, with the blocking rota's id/date
    in the message so the frontend can tell the user which one to roll
    back first.
- Response: `RotaOut` (the same shape `commit` returns — *not*
  `GenerateRotaOut`, which is generate's status+issues envelope). The
  frontend routes into the existing draft-editing view off the rota id.
- Expose `committed_at` on `RotaSummaryOut` and `RotaOut` now. Frontend
  work is out of scope, but the list endpoint is how the frontend will
  determine which committed rota gets the rollback affordance — adding
  the field in this pass avoids a backend follow-up ticket.
- Update the router module docstring's lifecycle summary alongside this
  change, same as the M3 docstring documents commit/scrap today.
- Add a comment to `delete_clinic_type`'s 409 detail noting snapshot rows
  are now a second possible blocking reference (Decision 1).

## Worked example (validates the chain math)

Commit A, then commit B, then commit C, no rollbacks yet:

1. `rollback_commit(C)`: C is most recent committed, no active draft ->
   counters restored to C's pre-generation snapshot (== B's post-commit
   baseline, since nothing touched counters between B's commit and C's
   generation). C -> DRAFT.
2. `scrap_rota(C)`: C and its snapshot deleted. B is once again the most
   recent committed rota.
3. `rollback_commit(B)`: counters restored to B's snapshot (== A's
   post-commit baseline). B -> DRAFT.
4. `scrap_rota(B)`: B deleted. A is most recent committed.
5. `rollback_commit(A)`: counters restored to A's snapshot (== baseline
   before any of A/B/C ever existed). A -> DRAFT. User can now re-edit
   and re-commit A, or scrap it too.

Variant: rollback C -> re-commit C. `commit_rota()` sets a fresh
`committed_at`, so C is again the most recent commit and the chain
ordering is intact.
