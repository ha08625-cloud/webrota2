# Clinic Type PATCH + Inline Toggles (implementation plan)

## Scope

Add a partial-update path for the two clinic type booleans so the frontend can toggle them inline without round-tripping the full nested payload:

1. Backend: `ClinicTypePatch` schema + `PATCH /clinic-types/{id}`, mirroring the `DoctorPatch` pattern (all-optional fields, applied via `exclude_unset`), reusing the existing `_next_priority` / `_close_gap` helpers when `is_enabled` genuinely changes.
2. Frontend: `usePatchClinicType` hook, plus inline checkboxes for **Room required** and **Enabled** in both the Enabled and Disabled tables on `ClinicTypesPage`.

Out of scope: `name` and `category` stay PUT-only (the edit dialog remains the path for everything except the two booleans). No optimistic updates — the page keeps its existing invalidate-and-refetch pattern.

## Frontend design

### Types (`frontend/src/api/types.ts`)

```typescript
export interface ClinicTypePatch {
  is_enabled?: boolean;
  room_required?: boolean;
}
```

### Hook (`frontend/src/api/clinicTypes.ts`)

`usePatchClinicType` (named for what it does — it takes any partial payload, not just a toggle):

```typescript
export interface PatchClinicTypePayload {
  id: number;
  payload: ClinicTypePatch;
}

export function usePatchClinicType() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ id, payload }: PatchClinicTypePayload) =>
      apiClient.patch<ClinicType>(`/clinic-types/${id}`, payload),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: clinicTypeKeys.list() });
    },
  });
}
```

Same invalidate-on-success pattern as the sibling mutations, for the same documented reason (small list, nobody mid-gesture). Confirm `apiClient` exposes a `patch` method (`frontend/src/api/client.ts`); the rota session PATCH already uses one, so it should exist — if not, adding it follows the existing method shapes.

### Page (`frontend/src/routes/ClinicTypesPage.tsx`)

Neither table currently has an Enabled column — both changes are **added columns plus a converted cell**, not a text swap:

- **Room required**: replace the static "Yes"/"No" cell with a checkbox in both tables. `onChange` fires `usePatchClinicType` with `{ room_required: e.target.checked }`.
- **Enabled**: new column in both tables, checkbox, `{ is_enabled: e.target.checked }`. It must appear in both sections to function as a control — toggling it moves the row between the two tables (after refetch), so a one-sided checkbox would be un-checkable-only.
- Keep the Enabled checkbox in its own `<td>`, not the drag handle's cell. The dnd-kit listeners are scoped to the handle button so there is no real event conflict, but a separate column avoids accidental drag-starts on touch devices.
- Give each checkbox an `aria-label` including the clinic type name (e.g. `Enabled for Duty helper`) — the page tests will select by these.

**Pending-state / reorder race.** `enabledOrder` is local state, and the reorder mutation sends the full enabled id set, which the server 409s if it does not exactly match the current enabled set. A disable-toggle in flight followed by a drag can therefore send a stale set. Mitigation, deliberately cheap:

- Disable **all** toggle checkboxes on the page while `patchClinicType.isPending` (not just the clicked one — a second toggle during flight has the same staleness problem, and per-row pending tracking is not worth it for a list this size).
- This also covers the UX gap where a checkbox would otherwise show stale state for the round-trip duration and invite double-clicks.
- The drag/toggle race is narrowed, not eliminated (a drag started before the toggle lands is still possible); the server's existing 409 + the page's existing rollback-and-error-message path is the backstop, and it already handles this correctly. Do not add locking beyond the checkbox disabling.

Surface a patch failure through a page-level error message like the existing `deleteError` / `reorderError` pattern (`toggleError` state, cleared on the next action).

### Frontend tests

`frontend/src/api/clinicTypes.test.ts`:
- `usePatchClinicType` sends PATCH to `/clinic-types/{id}` with exactly the supplied field(s) and invalidates the list on success (mirror the existing `useUpdateClinicType` test shape; add an MSW handler for the PATCH route in the test or shared handlers as the existing tests do).

`frontend/src/routes/ClinicTypesPage.test.tsx`:
- Enabled table renders an Enabled checkbox per row, checked; Disabled table renders one, unchecked.
- Unchecking Room required on a row fires PATCH with `{ room_required: false }` only.
- Unchecking Enabled on an enabled row fires PATCH with `{ is_enabled: false }` only.
- While the PATCH is in flight, all toggle checkboxes are disabled (MSW delayed response).
- A PATCH failure surfaces the error message.
