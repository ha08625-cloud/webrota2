# Server-managed clinic_priority with drag-and-drop reorder — implementation plan

`clinic_priority` becomes a server-computed
ordering position: clients can never set it, the server maintains a contiguous
1..N sequence over enabled clinic types, and reordering happens through a
dedicated drag-and-drop endpoint.

## Data model and migration

- `clinic_priority` stays `NOT NULL Integer`. A **partial unique index** over
  enabled rows only is added to `ClinicType.__table_args__`:
  `Index("uq_clinic_types_priority_enabled", "clinic_priority", unique=True, sqlite_where=text("is_enabled"), postgresql_where=text("is_enabled"))`.
  Both dialect clauses are required — tests run on SQLite, production on
  Postgres.
- **New migration `005`** (`revision="005"`, `down_revision="004"`). migration 003 has already been applied to the Railway database
  and must never be edited. The upgrade does two things, in this order:
  1. **Normalize existing data.** Current priorities are client-supplied with
     no uniqueness guarantee (the old frontend default was 1000), so duplicates
     among enabled rows are likely and would make the index creation fail.
     Renumber enabled rows to 1..N ordered by `(clinic_priority, id)` for
     determinism. Disabled rows are left untouched — their stale value is
     outside the index. Use `op.get_bind()` with plain SQL / SQLAlchemy Core,
     not ORM models.
  2. **Create the partial unique index**, with the correct `WHERE is_enabled`
     clause on both dialects.
  `downgrade()` drops the index. The renumbering is not reversed — the old
  client-supplied values are unrecoverable and a contiguous 1..N is a valid
  state under the old schema anyway.

## Schemas

- `ClinicTypeIn` (the write schema used by POST/PUT) **drops `clinic_priority`
  entirely** — it is no longer something a client can set. Pydantic's default
  behaviour ignores unknown fields, so a stale client that still sends
  `clinic_priority` gets a silent no-op, not a 422. This is deliberate and
  gets an explicit test (see Tests).
- `ClinicTypeOut` keeps `clinic_priority` as a read-only, server-computed
  field.
- New request schema for the reorder endpoint: `{"ordered_ids": [int, ...]}`.

## Backend logic

`_apply()` stops touching `clinic_priority` altogether. Because `_apply()`
overwrites `ct.is_enabled`, the router **must capture the pre-edit
`is_enabled` (and priority) before calling `_apply()`** — transition detection
compares the captured value against the payload.

Small helpers replace manual priority handling. Only the reorder permutation
needs the two-phase placeholder trick:

- **Create, or a disabled-to-enabled transition:** append at the end using
  `clinic_priority = max(enabled priorities) + 1` (1 if none). Use max+1, NOT
  count+1 — max+1 is tolerant of a gap ever existing, whereas count+1 would
  collide with an existing priority and 409 every subsequent create. No other
  row is touched, so this is a single plain update, no placeholder.
- **Delete of an enabled row, or an enabled-to-disabled transition:** gap-close
  by shifting every enabled row with a higher priority down by 1. Two hard
  requirements:
  1. **Same transaction as the delete/edit.** Sequence: capture pre-state,
     delete (or apply edit), `flush()`, gap-close, then one `commit()`. Never
     commit the delete first and gap-close in a second transaction — a failure
     between the two leaves the sequence broken.
  2. **Per-row updates in ascending priority order, flushing between rows —
     NOT a single bulk `UPDATE ... SET clinic_priority = clinic_priority - 1`.**
     Postgres checks a non-deferrable unique index per row in whatever order
     it visits them, so a bulk decrement can spuriously collide. Ascending
     per-row updates always move into a just-vacated value, so no placeholder
     is needed.
- **Drag-and-drop reorder** (new `PUT /clinic-types/reorder`, body
  `{"ordered_ids": [...]}`): the only genuine arbitrary permutation, so the
  only case needing the negative-placeholder two-phase update (phase 1: set
  each affected row to `-(new_priority)`; phase 2: flip signs to final
  values, with a flush between phases). Before applying anything, validate
  that `ordered_ids` is exactly the current set of enabled ids (as a set,
  and with no duplicates) — mismatch is a 409 with a clear detail message.
  **Route registration order matters:** declare `PUT /clinic-types/reorder`
  BEFORE `PUT /{clinic_type_id}` in the router file, otherwise "reorder"
  matches the int path parameter and returns 422.
- **No-op case** (enabled staying enabled, or disabled staying disabled):
  touches nothing — an ordinary edit via the existing PUT never reorders
  anything.

`delete_clinic_type` captures whether the row was enabled and its priority
before `db.delete()`, and runs the gap-close inside the same transaction as
described above.

## Frontend

- **`ClinicTypeFormDialog.tsx`**: the Priority field is removed entirely,
  create and edit. The dialog no longer needs `useClinicTypes()` at all —
  this removes the MSW-mock and default-computation work from the earlier
  round rather than adding to it.
- **`clinicTypeSchema.ts`**: drop `clinicPriority` from the form schema,
  `emptyFormValues()`, the `fromClinicType()` mapping, and the outbound
  payload mapping.
- **`ClinicTypesPage.tsx`**: enabled clinic types become a
  `@dnd-kit/sortable` list with a drag handle (already a dependency —
  `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities` are all in
  `package.json`), modelled on `reorderPreferredRooms.ts`'s pattern: position
  is derived from array index, never stored as separate state. Disabled
  clinic types render in a separate, non-draggable section below, sorted by
  name — their stored priority is stale by definition, so they are never
  interleaved. On drop, call the reorder endpoint with the full ordered id
  list of enabled clinics.
- New API function for the reorder call in `frontend/src/api/clinicTypes.ts`.

## Tests

Backend (`test_api_test_clinic_types.py`):
- `test_put_replaces_children` currently asserts a client-supplied
  `clinic_priority` sticks — rewrite it: the field in the payload is ignored
  and the stored priority is unchanged by an ordinary PUT.
- `test_duplicate_name_409` / `test_room_elig_xor_422` payloads can drop the
  now-ignored `clinic_priority` field.
- New tests:
  - create appends at end (max+1);
  - a POST/PUT payload that still includes `clinic_priority` is silently
    ignored — pins the Pydantic extra-field behaviour explicitly;
  - delete of an enabled row closes the gap and priorities remain contiguous;
  - enable transition appends at end; disable transition removes from the
    sequence and closes the gap;
  - reorder happy path;
  - reorder rejects a payload whose id set does not match the current enabled
    set (missing id, extra id, duplicate id, disabled id included).

Engine tests:
- `factories.py` fix from the earlier round is **still needed** — the default
  is `clinic_priority=10`, engine tests build `ClinicType` rows directly
  through the ORM (bypassing the router), the partial index still applies,
  and `test_two_clinic_types_have_independent_counters` collides. Replace the
  fixed default with an auto-incrementing one.

Migration:
- The existing CI Postgres upgrade/downgrade/upgrade round trip covers
  migration 005 automatically once it exists. Additionally, the normalization
  step should be written so it is a no-op on an empty table (fresh CI
  databases).

Frontend:
- `clinicTypeSchema_test.ts` / `ClinicTypeFormDialog_test.tsx`: remove
  now-obsolete priority cases; no new MSW mocks needed.
- New drag-reorder and disabled-section-split cases for
  `ClinicTypesPage_test.tsx` — review what that file currently covers before
  writing these.

## Task ordering

Start with the migration (005) and model change first — everything else
depends on it. Suggested sequence: (1) migration + model + factories fix,
(2) schema change + router helpers + reorder endpoint + backend tests,
(3) frontend schema/dialog cleanup, (4) ClinicTypesPage drag-and-drop +
frontend tests.
