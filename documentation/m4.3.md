# Plan

Add a generation decision log: every decision the engine makes during a
generation run (clinic assignments, room assignments, displacements, swap
resolutions, supervision assignments, duty applications) is recorded as a
structured entry, persisted per rota in a new `rota_generation_log` table,
exposed via `GET /rota/{rota_id}/log`, and viewable in a new filterable
panel on the rota detail page. This replaces the observability the old GAS
script's built-in log provided and is currently the only practical way to
verify the displacement logic (Phase 5, 7-9A) and the swap-elimination
table (9B) are behaving correctly on real data.

# Scope

**In scope:** decisions made by Phases 4, 5, 7-9A, 9B, and 9C during a
generation run; persistence in the same transaction as the rota; a
read-only API endpoint; a frontend panel with phase and doctor filtering.

**Out of scope:**
- Phase 0 and Phase 12 (validation only — findings already surface as
  `ValidationIssue`s; no decisions are made).
- Phase 2 (mechanical grid/counter initialisation; no decisions).
- Manual edits after generation (swaps, PATCH, set-room/set-role). These go
  through `grid_utils.py` + the routers, a separate code path. Logging them
  is a possible later ticket.
- Crash forensics. The log lives in memory until `_write_to_db()` and is
  written only on a successful pipeline; an uncaught mid-pipeline exception
  rolls back and loses it along with everything else. This is consistent
  with the engine's never-commit transaction model and is accepted: the log
  verifies behaviour, not crashes. Do not add any partial-write or
  out-of-band logging mechanism.

# Design Decisions

1. **New structures, not an extension of `ValidationIssue`.** New frozen
   dataclass `DecisionLogEntry` plus a mutable append-only collector
   `DecisionLog`, both in `backend/app/engine/datatypes.py`. Decisions
   ("this happened") and validation findings ("something is wrong") stay
   separate types with separate persistence and separate frontend surfaces.

2. **Entry shape.** Structured fields for filtering plus a free-text
   message:
   - `sequence: int` — monotonic per run, assigned by `DecisionLog.add()`,
     never by DB row order.
   - `phase: str` — same values as `ValidationIssue.phase` (`"phase4"`,
     `"phase5"`, `"phase7_9a"`, `"phase9b"`, `"phase9c"`).
   - `action: str` — controlled vocabulary, defined per phase in Task 3:
     `assign_duty`, `skip_closed_date`, `assign_clinic`,
     `assign_clinic_room`, `displace_for_clinic`, `assign_room`,
     `displace_room`, `resolve_swap`, `assign_supervisor`.
   - `week: int | None`, `day: Day | None`, `period: Period | None` —
     nullable to match `ValidationIssue` (Phase 7-9A Pass 1 decisions are
     full-day: `period=None`).
   - `doctor_id: int | None` — primary subject.
   - `related_doctor_id: int | None` — the displaced occupant, the swap
     partner. Null elsewhere.
   - `room_id: int | None` — the room assigned/claimed (Phase 9B: doctor
     A's AM room).
   - `related_room_id: int | None` — the room the displaced occupant was
     relocated to (displacements); doctor B's AM room (9B swaps). Null
     elsewhere. This field exists because a displacement is "from room X to
     room Y" and one room field cannot represent it.
   - `clinic_type_id: int | None`.
   - `message: str` — human-readable, same tone as `ValidationIssue`
     messages, uses doctor codes and room/clinic names via the context
     lookup helpers the phases already use.

3. **Mutable collector threaded as a parameter.** Each in-scope phase gains
   a **required** `log: DecisionLog` parameter (keyword or positional —
   match each phase's existing style). This mirrors how `CounterState` is
   threaded and avoids changing every return signature. It is deliberately
   **not** defaulted to `None`: a default would keep existing tests
   compiling but would also make silently forgetting to wire it possible.
   Every direct call site in the engine tests is updated instead
   (mechanical: construct a `DecisionLog()` and pass it).

4. **Verbosity rule (resolves review open question 1).** One entry per
   assignment, not one per candidate considered. For counter-based
   selections (Phase 5 clinic pick, 9C pool pick, 7-9A displacement-victim
   pick) the message states the deciding stage inline, e.g.
   `"...selected on priority tier 1, tie broken on weighted score 0.40 vs
   0.65"` or `"...only eligible doctor"`. Phase 5's closed-date skip **is**
   logged (`skip_closed_date`, one entry per skipped schedule slot) — it is
   the answer to "why is there no clinic on Monday". Do not log
   considered-and-rejected candidates individually.

5. **Persistence — plain integers, no FKs except `rota_id` (resolves
   review open question 2).** New table `rota_generation_log`, model
   `RotaGenerationLogEntry` in a new `backend/app/models/generation_log.py`
   (one-file-per-concern, matching `closure.py` / `counter_snapshot.py`).
   `rota_id` is a real FK to `generated_rotas.id` with
   `cascade="all, delete-orphan"` from a new
   `GeneratedRota.generation_log` relationship — same pattern as
   `RotaClosure`. `doctor_id` / `related_doctor_id` / `room_id` /
   `related_room_id` / `clinic_type_id` are **plain nullable integers with
   no FK constraints**: the log is a diagnostic artifact whose rows already
   carry a self-contained message, an orphaned id in a historical entry is
   harmless, and real FKs would silently expand the delete-blocker surface
   (e.g. `delete_clinic_type`'s 409 currently names "counter or rota rows"
   and would become wrong). Rows are written in `_write_to_db()` in the
   same transaction as everything else, so an exception rolls the log back
   with the run, and scrap deletes it for free via cascade. `commit` and
   `rollback_commit` never touch it — the log is never mutated after
   generation, so no snapshot/restore logic exists.

6. **Migration 007**, revises 006. Uses `enum_col`-backed columns for
   `day`/`period` — these enum types already exist on Postgres from 001, so
   the migration must reuse them, not create them (follow 001/002's
   enum-type-reuse handling, unlike 006 which had no enums). Unique
   constraint on `(rota_id, sequence)`; index on `rota_id`.

7. **API: `GET /rota/{rota_id}/log`.** Reads the persisted rows directly,
   ordered by `sequence`, works for drafts and committed rotas. Note this
   is **unlike** `GET /rota/{rota_id}/issues`, which persists nothing and
   re-runs Phase 12 via a grid rebuild on every request — the log endpoint
   is the first read-persisted-rows endpoint of its kind and is much
   simpler. No grid rebuild, no `run_phase12_for_rota`, no server-side
   filter parameters (a full 4-week run produces several hundred rows;
   returning them all and filtering client-side is fine).

8. **Frontend: a `GenerationLogPanel` on `RotaDetailPage`**, collapsed by
   default, alongside the existing IssuesPanel. Filtering by phase and by
   doctor is a functional requirement (several hundred entries unfiltered
   is unusable), plus visual grouping by week/day. Ids are resolved to
   codes/names client-side from the already-cached reference queries where
   available; the message text is the fallback for anything unresolvable
   (e.g. a since-deleted clinic type).

# Task 3: Per-phase log content

**A.** Tasks 1-2 are complete: `DecisionLog` is threaded through all five
phases and persisted, but no phase emits entries yet. This task adds the
actual `.add()` calls at each decision point. The existing
`ValidationIssue` emissions are untouched — a failure to decide stays a
warning, only successful decisions (and the Phase 5 closed-date skip)
become log entries.

**B.** Files to change:
- `backend/app/engine/phases/phase4.py`
- `backend/app/engine/phases/phase5.py`
- `backend/app/engine/phases/phase7_9a.py`
- `backend/app/engine/phases/phase9b.py`
- `backend/app/engine/phases/phase9c.py`
- Their five test modules, plus `test_generate.py` for one end-to-end
  count/order assertion.

Deliverables: every decision point below emits exactly one entry; per-phase
tests assert the entries (action, subject ids, related ids) for at least
the primary paths; messages use doctor codes and room/clinic names via the
same `context.doctor_by_id` / `context.room_by_id` lookups the phases
already use for warnings (reuse `_code()`-style helpers; add a module-local
room-code helper where needed).

**C.** Instructions — decision points and entry contents per phase. Message
wording below is indicative; keep the tone of existing `ValidationIssue`
messages and always include the doctor code and room/clinic names in the
text so the message is self-contained.

**Phase 4** (`assign_duty`) — one entry per successfully applied duty role
(the `slot.role = ...` line at the end of the loop). Fields: week, day,
period, doctor_id. Message: `"Applied {duty_type} duty to {code} on {date}
{period} (pre-planned)."` The two failure branches already emit warnings;
no entries for them.

**Phase 5** — three actions:
- `skip_closed_date`: at the `date_ in context.closed_dates` branch.
  Fields: week, day, period, clinic_type_id. Message: `"Skipped clinic
  '{name}' on {date} {period}: practice closed."`
- `assign_clinic`: after `doctor_id = eligible[0].doctor_id`. Fields:
  week, day, period, doctor_id, clinic_type_id. The message states the
  deciding stage (Design Decision 4). Determine it from the sorted
  `eligible` list: if `len(eligible) == 1` — "only eligible doctor";
  else compare `eligible[0]` and `eligible[1]` on the same sort key —
  if priority tiers differ, "priority tier {n}"; else if weighted scores
  differ, "priority tier {n}, tie broken on weighted score {a:.2f} vs
  {b:.2f}"; else "..., alphabetical tie-break". Compute the two scores
  **before** `counters.increment_clinic` runs (it runs after room
  resolution, so ordering is already safe — just do the comparison where
  the pick happens).
- Room resolution inside `_resolve_room` (only when `clinic.room_required`):
  - Already in an eligible room (first early return): `assign_clinic_room`,
    room_id = current room, message "...already in eligible room {room}".
  - Free eligible room found (second block): `assign_clinic_room`,
    room_id = room assigned.
  - Displacement (third block): `displace_for_clinic`. Fields: doctor_id =
    the clinic doctor, related_doctor_id = occupant, room_id = the claimed
    room, related_room_id = the occupant's new room, clinic_type_id.
    Message names both doctors, both rooms, and the clinic: `"Displaced
    {occupant_code} from {room} to {new_room} so {code} can run clinic
    '{name}'."`
  - The give-up path already emits `clinic_room_unresolved`; no entry.
  `_resolve_room` will need `log` plus the schedule's week/day/period
  passed through (it already receives gen_week/day/period) and
  `clinic.id`; thread whatever is missing.

**Phases 7-9A** — two actions across the three passes; identify the pass in
the message, not the action name:
- Pass 1, free room found: `assign_room`, period=None (full-day),
  room_id = the D room. Message: `"Assigned D room {room} to {code} for the
  full day (pass 1, room free both sessions)."` One entry, not two, even
  though two `assign_room` grid calls occur.
- Pass 1, displacement: `displace_room`, period=None, doctor_id = the
  Trainee/AHP, related_doctor_id = displaced_id, room_id = d_room_id,
  related_room_id = new_room. Message states full-day, pass 1, and that the
  victim was chosen on lowest weighted room-move score (include the score
  comparison only if there was more than one candidate; the candidate list
  is available at `_find_full_day_displacement`'s call site only as the
  winner — pass the sorted candidate count/scores back, or simply state
  "lowest weighted room-move score" without numbers; the latter is
  acceptable, decide once and apply consistently to Pass 2).
- Pass 2: same two shapes, with period set, messages saying "pass 2".
- Pass 3: `assign_room`, message `"Assigned preferred room {room} to
  {code} (pass 3, first free room on preference list)."`
- All no-room failure paths already emit warnings; no entries.

**Phase 9B** (`resolve_swap`) — one entry per **detected** swap pair,
emitted whether the resolution is CONFIRM or DEFAULT (both are decisions;
this phase currently has no output at all, so the log is its only trace).
Fields: week, day, period=None (the swap spans AM/PM; the mutation is
PM-only — state that in the message), doctor_id = a_id,
related_doctor_id = b_id, room_id = a_am, related_room_id = b_am.
`_should_confirm_swap` must also report **which rule fired**: change its
return to `tuple[bool, str]` (confirm, reason) with reasons like
`"row 1: only {a_code} prefers their own AM room"` /
`"rows 5-7 default: no preference distinguishes the doctors"`, and update
its one call site. Message: `"Detected AM/PM room swap between {a_code}
({a_room}) and {b_code} ({b_room}): {CONFIRMED|DEFAULTED} ({reason})."`

**Phase 9C** (`assign_supervisor`) — one entry per supervised session, from
both selection paths:
- SR-priority path (inside `_assign_sr_priority`, at the assignment):
  doctor_id = occupant_id, room_id = the SR room. Message: `"Assigned
  {code} as supervisor on {day} {period} (SR-room occupant) for {n}
  trainee(s)."` — `n` must be passed into `_assign_sr_priority` (it is
  already computed at the call site).
- Pool path: doctor_id = chosen.doctor_id, room_id =
  chosen.assigned_room_id. Message states pool selection and the deciding
  stage (same single-vs-tie logic as Phase 5's `assign_clinic`, using the
  weighted SUPERVISION score) plus the trainee count.
- `related_doctor_id` stays null — a session can have several trainees, so
  no single trainee is "the" related doctor.
- The no-supervisor path already warns; no entry.

**Tests.** For each phase, extend the existing test module: build the same
fixtures the current tests use, run the phase with a fresh `DecisionLog`,
and assert the expected entries (filter `log.entries` by action; check
subject/related ids and that messages contain the expected codes — do not
assert full message strings verbatim, they will be wordsmithed). Cover at
minimum: phase 4 happy path; phase 5 skip/assign/displace; 7-9A one free
and one displacement per pass shape; 9B one CONFIRM and one DEFAULT with
the right rule reason substring; 9C both selection paths. In
`test_generate.py`, one end-to-end run asserting the persisted rows exist,
are non-empty, and are ordered by `sequence` matching `log.entries` order.

# Task 4: API

**A.** Tasks 1-3 are complete: generation runs now persist populated
`rota_generation_log` rows. This task exposes them read-only.

**B.** Files to change:
- `backend/app/api/schemas/rota.py` — add `GenerationLogEntryOut`.
- `backend/app/api/routers/rota.py` — add `GET /{rota_id}/log`.
- `backend/tests/test_api/test_rota.py` (or a new
  `test_api/test_generation_log.py` if `test_rota.py` is already long —
  implementer's choice, follow whichever the suite's conventions favour).

Deliverables: the schema, the endpoint, tests.

**C.** Instructions:

1. Schema, mirroring the entry fields (from_attributes on, matching the
   other Out models' config):

```python
class GenerationLogEntryOut(BaseModel):
    sequence: int
    phase: str
    action: str
    week: int | None = None
    day: Day | None = None
    period: Period | None = None
    doctor_id: int | None = None
    related_doctor_id: int | None = None
    room_id: int | None = None
    related_room_id: int | None = None
    clinic_type_id: int | None = None
    message: str
```

   Docstring: plain ids by design (no joins in the router — the message is
   self-contained and the frontend resolves ids against cached reference
   data, falling back to the message for anything deleted since).

2. Endpoint, directly below `get_rota_issues` for discoverability, with a
   comment contrasting the two: `/issues` recomputes via Phase 12 because
   issues are never persisted; `/log` reads persisted rows because the log
   is written once at generation time and never re-derived.

```python
@router.get("/{rota_id}/log", response_model=list[GenerationLogEntryOut])
def get_rota_log(rota_id: int, db=Depends(get_db), user=Depends(get_current_user)):
    _get_rota_or_404(db, rota_id)
    rows = db.execute(
        select(RotaGenerationLogEntry)
        .where(RotaGenerationLogEntry.rota_id == rota_id)
        .order_by(RotaGenerationLogEntry.sequence)
    ).scalars().all()
    return [GenerationLogEntryOut.model_validate(r) for r in rows]
```

   No filter query parameters (Design Decision 7).

3. Tests: 404 for unknown rota; empty list for a rota with no log rows
   (e.g. one inserted directly by fixture); a generated rota returns
   non-empty entries ordered by sequence; the endpoint works on a
   **committed** rota (generate, commit, fetch); auth shim applies (it
   does automatically via `get_current_user` — one assertion piggybacking
   on the existing auth test pattern is enough, or skip if the auth suite
   already covers all router endpoints generically).
