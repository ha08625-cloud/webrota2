# Rota Generator — Clinical Rota Architecture

Covers the clinical rota only: the generation engine, its data layer, the `/api/v1` REST surface (excluding `/reception/*`), and the clinical-side React frontend. Shared infrastructure (auth, app shell, tech stack, CI, deployment) lives in `documentation/architecture.md`; the reception rota is documented separately in `documentation/architecture-reception.md`.

## Generation Engine

`backend/app/engine/` — pure Python, no FastAPI dependency. Transforms the active master template plus reference data into a fully assigned draft rota via a strictly sequential pipeline: an immutable context in, a mutable grid through the phases, one write at the end.

```
engine/
  datatypes.py    SessionSlot, RotaGrid, CounterState, GenerationContext, ValidationIssue, GenerationResult
  week_map.py     generation-week <-> template-week <-> calendar-date mapping
  context.py      load_context(): one read-only snapshot of all reference data per run
  grid_utils.py   rebuild_rota_grid() / run_phase12_for_rota(): reconstruct a grid from persisted rows for the edit endpoints
  phases/         phase0, phase2, phase4, phase5, phase7_9a, phase9b, phase9c, phase12
  generate.py     orchestrator + draft lifecycle (get_active_draft, commit_rota, scrap_rota)
```

Phase numbering (0, 2, 4, 5, 7–9A, 9B, 9C, 12) is inherited from the original GAS scripts; the gaps are not missing phases. Phase 9C (trainee supervision) runs between 9B and 12 — see phase-pipeline.md for the full specification, including its three confirmed divergences from the original GAS design.

### Core data structures (`datatypes.py`)

- **`GenerationContext`** — frozen dataclass holding all reference data for one run (doctors, rooms, clinic types, leave set, duty map, week/date mappings, template sessions), built once by `load_context()`. Nothing in it is mutated during generation. Three load-time guarantees the phases depend on: `preferred_rooms_by_doctor` is flattened and ordered, with `room_type` preference rows expanded to concrete rooms at that preference position; `ClinicTypeInfo.schedules` is deterministically sorted (weekday, then period), because Phase 5's counter fairness depends on a deterministic processing order; and `recurring_notes_by_slot` arrives fully resolved — overlapping notes already concatenated, template weeks already mapped against the run's effective start week — so Phase 2's stamp is a plain dict lookup with no concatenation or week logic of its own.
- **`RotaGrid`** — the mutable workspace: a dict of `SessionSlot`s keyed `(doctor_id, week, day, period)`, plus two synchronised occupancy indexes (`_room_occupancy` and `_doctor_room`) giving O(1) answers to both "is this room free" and "what room does this doctor hold" — the displacement logic in Phases 5 and 7–9A needs *who* occupies a room, not just whether it is free. `assign_room()`/`free_room()` keep the indexes and the slot's `assigned_room_id` in lockstep.
- **`CounterState`** — in-memory working copy of clinic and system counters. Clinic counters are **shared**: keyed `(doctor_id, clinic_type_id)` with no day/period dimension (an earlier per-slot design was rejected before M2). The weighted score used for assignment tie-breaking is `raw_count / sessions_per_week`; a doctor with `spw = 0` scores infinity and is therefore never preferred. `CounterState` also tracks which clinic keys are new this run, so the final write knows INSERT from UPDATE without re-querying.
- **`ValidationIssue`** — one finding from a phase. Only Phase 0 ever emits `severity="error"`; everything else is a warning.
- **`DecisionLog`** — an append-only collector of `DecisionLogEntry` records, threaded as a required parameter through the decision-making phases (4, 5, 7–9A, 9B, 9C), mirroring how `CounterState` is threaded. Sibling type to `ValidationIssue`: a `DecisionLogEntry` records the normal path ("this happened" — a clinic assignment, a room displacement, a swap resolution, a supervision assignment), not a finding. Verbosity is one entry per assignment, not one per candidate considered — counter-based selections (Phase 5's clinic pick, 9C's pool pick, 7–9A's displacement-victim pick) state the deciding stage inline in the message (e.g. "selected on priority tier 1, tie broken on weighted score"); Phase 5 additionally logs each closed `(date, period)` slot it skips, since that is the answer to "why is there no clinic on this slot". Persisted verbatim to `rota_generation_log` by `_write_to_db()` on a successful run only — see "Transaction and persistence model" below and the `rota_generation_log` table entry under "Tables".

### Pipeline (`generate.py` orchestrating `phases/`)

`generate(db, config_id)` loads the context, then runs the phases in fixed order. **Only Phase 0 can stop the run**: any Phase 0 error returns `status="failed"` before a grid exists or anything is written. Phases 2–12 cannot fail — every subsequent finding is a collected warning, and the result status is `success` (no warnings) or `partial` (warnings present), both with a persisted draft.

- **Phase 0 — pre-flight validation.** Hard errors (abort) include a duty doctor pre-planned onto a `NO_SURGERY`/`ADMIN_TIME` template slot (`duty_on_incompatible_slot`), duty-on-leave, duty-on-closed-slot (`duty_on_closed_date`, — any `DutyAssignment` whose `(date, period)` is in `context.closed_slots`), and duty-outside-the-doctor's-employment-window (`duty_outside_doctor_dates`). The last three share a rationale: Phase 2 builds no slot in any of those cases, so the duty has nothing to attach to — an error here rather than Phase 4's `duty_no_session_slot` warning, which would let the rota generate with the duty silently dropped. It reads `context.doctor_by_id`, not `context.doctors`, so an inactive doctor carrying a stale duty row is still reachable. WFH template slots are deliberately exempt from the incompatible-slot block: a WFH slot is realistically overridable — the doctor comes in for duty.
- **Phase 2 — grid and counter initialisation.** Builds the grid from the active template (a doctor with no template entry for a slot gets **no** `SessionSlot` — cell absence is data, the part-time-doctor case) and loads `ClinicCounter`/`SystemCounter` rows into `CounterState` (the one phase needing DB access). Also builds no slot for any doctor on a closed `(date, period)`, nor for a `(doctor, date)` outside the doctor's employment window — the same "cell absence is data" mechanism covers closures and the window for free, so no downstream phase needs a per-slot closed or window check. The two compose rather than override: a closed period inside the window and an open one outside it both yield no slot. Also stamps `SessionSlot.notes` from `context.recurring_notes_by_slot`, pre-resolved by `load_context()` — see "Recurring notes" below. This is a default value only: annotation, not eligibility — a duty or clinic role can still land on a slot carrying a note.
- **Phase 4 — pre-planned duty application.** Applies `DutyAssignment` rows as roles on the grid.
- **Phase 5 — clinic assignment and clinic room resolution.** Iterates clinic type (by `clinic_priority`) -> schedule -> generation week; picks the eligible doctor by priority tier, then weighted counter, then alphabetical, and increments the shared counter. Room resolution for `room_required` clinics is **preference-list-only** — no room-type fallback. It may displace a lower-priority occupant, but never one who is on leave, on duty, or running a higher-priority clinic, and only if the occupant can be relocated to a free room from their own preference list (excluding D-type rooms when the room being claimed is D-type). A schedule slot landing on a closed `(date, period)` is skipped outright (before eligibility runs), so a closure produces no `no_eligible_doctor` warning — closed means "not expected", not "uncovered".
- **Phases 7–9A — room resolution.** Three passes: Trainee/AHP full-day displacement, then single-session displacement, then a Partner/Salaried fallback pass. The two displacement passes get the C/W/SR free-room fallback when relocating a displaced doctor; Pass 3 has its own, separate fallback — preference list first, then forced placement by room-type priority SR > D > C > W (D rooms deliberately included, since Pass 3 runs last, after all Trainee/AHP D-room demand is settled) — and only warns if every room in the practice is occupied.
- **Phase 9B — room swap elimination.** Resolves AM/PM room-pair swaps per a priority table. Row 5 of the original table was dropped as unreachable under strict first-match evaluation of rows 1–4 (user-confirmed decision: the scenario falls through to the same default as rows 6/7). "Preference match" means the room appears anywhere in the doctor's preference list, not top-preference-only.
- **Phase 9C — trainee supervision.** Assigns a Partner/Salaried supervisor to every session with at least one trainee requiring supervision, selected from the single D/SR-room eligible pool by lowest weighted `SUPERVISION` score — there is no SR-priority fast path; a doctor already sitting in SR competes on the same footing as one in D. Once selected, if the supervisor is not already in an SR room and an SR room is occupied by someone else, the supervisor is swapped into it and the displaced doctor takes the supervisor's vacated room (no swap if the supervisor is already in SR, or if the SR is unoccupied) — this is the one place Phase 9C itself writes a room assignment, rather than only reading what Phase 9B left behind. Diverges from the original GAS design: no duty-helper fallback pool (a duty helper's `role=CLINIC` already excludes them from the single pool); the trainee count itself is never persisted, only `is_supervising: bool`, since `is_on_leave` is derived at read time and a stored count would go stale. Exposes `count_supervisable_trainees`/`is_eligible_supervisor` as shared predicates so Phase 12 Check 4 cannot drift from the assignment rule. See phase-pipeline.md for the full specification.
- **Phase 12 — validation (warnings only).** Six checks: **duty coverage** (exactly 1 primary per session, 0 on a closed slot; 1 secondary AM/PM only on the generation week's first *fully open* weekday, 0 elsewhere — "Monday only" rule via `context.first_open_weekday_by_week`, which requires **both** AM and PM open rather than either alone, because secondary duty is expected on both periods of that day and a half-open day would expect it into a slot Phase 0 and `POST /duty` both refuse to accept; degrades to plain Monday when nothing is closed and to "no secondary expected" for a week with no fully open weekday), **clinic coverage** (also skips closed-slot schedule entries, mirroring Phase 5), **unresolved rooms** (a `REQUIRES_ROOM` slot with no room — skipping on-leave and WFH slots, since neither needs a room; the warning re-surfaces when WFH is toggled off), **`role_on_incompatible_slot`** (any role, duty or clinic, on a `NO_SURGERY`/`ADMIN_TIME`/on-leave/WFH slot — this is what keeps forced edits honest, since the edit endpoints have no eligibility checks of their own and re-run Phase 12 instead), and two supervision checks reusing Phase 9C's predicates: **`supervision_missing`** (a session has supervisable trainees but no slot is both flagged and currently eligible) and **`supervision_on_incompatible_slot`** (any flagged slot that has since become ineligible, regardless of trainee count). A session edited into a bad state can trigger both supervision checks at once — correct, not a duplicate.

### Staging branch (`context.py`)

`load_context()` prefers a staging copy over the live master template when one exists for the `RotaConfig` being generated (`_load_staging_or_template()`): if a `RotaStaging` row references the config, `template_sessions` is built from its `RotaStagingSession` rows instead of the active template's `MasterRotaSession` rows, and `active_template` is loaded by `RotaStaging.source_template_id` (by id, ignoring `is_active`) rather than re-resolved — so deactivating or adding templates between staging create and generation cannot brick an in-progress staging. The branch does not check `completed_at`: it also fires when `grid_utils.rebuild_rota_grid()` calls `load_context()` for edit endpoints on a staging-born rota after the staging is completed, where the staged sessions remain the correct source. Staging rows are keyed by *generation* week, and a staging's `RotaConfig` always persists `template_start_week=1`, making `template_week()` the identity — this is the invariant that lets Phases 0–12 run against a staged copy completely unchanged; no phase file has any staging-specific code.

This is the only staging-aware code inside the engine itself — now two helpers rather than one: `_load_staging_or_template()` above, plus the smaller `_effective_template_start_week()` read described under "Recurring notes" below, which resolves `RotaStaging.source_template_start_week` for note-week mapping. Everything else — the copy-from-template step, the editable surface, the lifecycle — lives in the API layer (`routers/staging.py`) and is not the engine's concern; see "Staging" under Data Layer and REST API below.

### Recurring notes (`context.py`, `phases/phase2.py`)

A recurring note ("Partners meeting") is defined against a day, a period, a set of *template* weeks (1–4), and an explicit list of doctors — independent of the master template, editable from its own "Recurring Notes" tab. `load_context()` pre-resolves every note into `recurring_notes_by_slot: dict[(doctor_id, gen_week, day, period), str]` so Phase 2 does a single dict lookup per slot rather than the phases knowing anything about the feature. Notes are annotation only: they never affect eligibility, duty, or room resolution, and Phase 2 still creates no slot (and therefore stamps no note) where the doctor has no template row or the `(date, period)` is closed. Overlapping notes on the same slot concatenate (newline-joined, ascending note id) rather than colliding. The stamp is a default value, not a derived one — `grid_utils.rebuild_rota_grid()` reads `notes` straight off the persisted row and never re-derives it, so a note cleared on the draft grid stays cleared.

Week resolution has one subtlety: a staged run always persists `RotaConfig.template_start_week = 1` (see "Staging branch" above), which would make a fortnightly note land on the wrong real-world fortnight if taken at face value. `load_context()` resolves the *effective* start week — `RotaStaging.source_template_start_week` when a staging exists for the config, otherwise `config.template_start_week` — and maps note weeks against that instead. `RotaStaging.source_template_start_week` is written once, at staging create (`routers/staging.py`), from the start week the copy was made against.

### Transaction and persistence model

The engine **never commits** — `_write_to_db()` only flushes; the caller (the rota router) owns the transaction. This is what guarantees an uncaught exception rolls back everything, counter writes included.

`_write_to_db()` runs once, at the end of a successful pipeline, and in this order:

1. Creates the `GeneratedRota` header with `status=DRAFT`.
2. **Snapshots every existing `ClinicCounter`/`SystemCounter` row** into `RotaClinicCounterSnapshot`/`RotaSystemCounterSnapshot` — all rows, not just those this run touches, because draft-period swap edits can change counters the generation never looked at, and scrap must restore those too. The snapshot is taken *before* counters are written, so it holds exact pre-generation values.
3. Writes every `SessionSlot` as a `RotaSession` row, including template-type-only slots (`NO_SURGERY`/`ADMIN_TIME`/WFH with no role). `template_type` is persisted directly on the row — sessions are self-contained snapshots, never re-derived from the master template at read time (which would silently rewrite historical rotas when the template is edited).
4. Upserts counters: INSERT for keys `CounterState` marked new, UPDATE otherwise. System counter updates use `.scalar_one()` deliberately — the seed guarantees a row per active doctor and counter type, and a violated guarantee should raise, not silently create rows.
5. Writes one `RotaClosure` row per closed `(date, period)` slot inside the run's range — `context.closed_slots`, already filtered by `load_context()`. Same self-contained-snapshot reasoning as `template_type` in step 3.
6. Writes the run's `DecisionLog` entries as `rota_generation_log` rows, in `sequence` order.

### Draft lifecycle (also in `generate.py`)

At most **one draft exists globally**; `get_active_draft()` is how the API layer finds it (the 409-on-generate enforcement itself is the router's). **Commit** deletes the snapshots and flips status — the live counter values (generation increments plus any draft-period edits) become the baseline for future generations. **Scrap** restores every snapshotted counter value wholesale, deletes counter rows created after the snapshot, recreates any snapshotted row that was deleted during the draft period, and deletes the rota (sessions cascade) and snapshots — all in the caller's transaction. Scrap therefore also undoes counter drift from manual edits, and scrap-then-regenerate is equivalent to generating once from the original baseline; this snapshot lifecycle is why the edit endpoints can safely use incremental counter updates rather than full recalculation.

### Grid rebuild for edits (`grid_utils.py`)

`rebuild_rota_grid()` reconstructs a `RotaGrid` from persisted `RotaSession` rows with a fresh `GenerationContext` per request (no caching); `run_phase12_for_rota()` re-validates it. Every edit endpoint (swaps, session PATCH, `set-room`/`set-role`) and `/issues` goes through this — `/issues` works on both draft and committed rotas. The `template_type` rule: the **persisted value is trusted when present**, including a manually overridden one; re-derivation from the active template is only the fallback for a null (legacy pre-`template_type`) value, and if the template entry no longer exists either, the slot falls back to `NO_SURGERY` — role-based checks stay accurate and the slot opts out of the unresolved-room check rather than warning against a template entry that no longer exists.

The same snapshot principle applies to closures. `load_context()` populates `closed_slots` from the *current* `PracticeClosure` table, which is correct for a fresh generation run but wrong for reconstruction — a closure added or removed after this rota was generated must not change how it renders or validates. `rebuild_rota_grid()` therefore overrides `closed_slots` on the loaded context with the rota's own `RotaClosure` snapshot via `dataclasses.replace()`, immediately after `load_context()` returns, with `first_open_weekday_by_week` re-derived from that overridden `closed_slots` the same way `load_context()` itself derives it.

# Data Layer and Seeds

SQLAlchemy 2.0 models (`Mapped` / `mapped_column` style) under `backend/app/models/`, fifteen Alembic migrations under `backend/alembic/`, seed scripts under `backend/seed/`. The models and migrations are the authoritative schema record; this section records only what is not obvious from reading them.

## Connectivity

`app/database.py` owns the engine, `SessionLocal` factory, and declarative `Base`. `DATABASE_URL` defaults to a local SQLite file (`./rota.db`); setting the env var (Postgres on Railway) switches the engine with no code change. SQLite gets `check_same_thread=False` so FastAPI can use sessions across threads. Session hand-out to request handlers is the API layer's job (`deps.get_db`).

**SQLite foreign keys are enforced only in the test engines.** Both test conftests attach a connect-event listener issuing `PRAGMA foreign_keys=ON`; the dev engine in `database.py` does not. A local SQLite dev database therefore silently accepts FK violations that Postgres (and the test suite) would reject.

## Enums

All enums are Python `str` enums in `models/enums.py`, stored by **value** (`"Partner"`, `"AM"`, `"no_surgery"`), not member name. `enum_col()` wraps one for column use and **caches one shared SQLAlchemy `Enum` instance per Python enum** — on Postgres each native enum type is a `CREATE TYPE`, and a fresh instance per column would attempt to create the same named type once per table, breaking `create_all` and `alembic upgrade`. One shared instance lets `Base.metadata` deduplicate. SQLite is unaffected (renders VARCHAR + CHECK).

## Tables (34)

Five of the 34 are `reception_staff`, `reception_master_sessions`, `reception_rotas`, `reception_rota_sessions`, and `reception_coverage_rules` — the reception rota's independent schema, covered in full in `documentation/architecture-reception.md` rather than here, since it shares no table, FK, or row with anything described in this section.

**Reference data.** `rooms`: the 14 physical rooms (8 D-rooms at SHC, C1–C3 at Cutteslowe, W1–W2 at Wolvercote, SR at SHC), unique `code`, `room_type` (D/C/W/SR) and `site` — the type letters mirror room codes and carry no further semantics in the data layer. `doctors`: unique `code`, `doctor_type` (Partner/Salaried/Trainee/AHP), soft delete via `active`, `sessions_per_week` (`Numeric(4,1)`, default 10.0) — this is the divisor for weighted counter scores, not a capacity limit enforced anywhere in the schema — and an optional **employment window** (`start_date`/`end_date`, both nullable, migration 017). `doctor_preferred_rooms`: an ordered preference list; each row is exactly one of a concrete `room_id` or a generic `room_type` token, enforced by a check constraint (`ck_dpr_room_xor`), with `(doctor_id, preference_order)` unique.

**The doctor employment window** lets a joiner or leaver be entered ahead of time. Null at either end means unbounded (the state of every pre-017 row, so the migration needs no backfill), and the predicate lives in one place, `app/doctor_window.py`'s `is_within_window` — top-level under `app/` rather than under `app/api/`, since the engine imports it too and `engine/` importing from `api/` would invert the layering. It is deliberately **independent of `active`**: `active` is the soft-delete flag, the window is a real employment fact, and callers combine the two gates as they need. `start_date <= end_date` is validated in `routers/doctors.py` rather than by a check constraint or a schema validator, because PATCH may supply one end of the pair and the check needs the merged post-update values. Enforcement is at four points and no others — `POST /leave` and `POST /extra-sessions` 422 (with `POST /leave/bulk` and `POST /leave-planning/bulk` reporting an `"outside_doctor_dates"` skip rather than failing a long range or a many-cell save), `POST /duty` 422, the `POST /staging` copy loop skips the row, and Phase 2 builds no slot. Phase 2 is the authority; the rest exist so the admin is told at entry time instead of watching cells vanish at generation. The split between 422 and skip is by *request shape*, not by endpoint family: a single-entry POST has nothing to partially succeed at, while one stale cell must not fail the other 199.

**Clinic configuration.** `clinic_types` plus three cascading child tables, all populated via the API/frontend, never seeded. `clinic_type_schedules`: unique `(clinic_type_id, day, period)`. `clinic_type_doctor_eligibilities`: per-doctor `doctor_priority` (default 1000, lower is stronger). `clinic_type_room_eligibilities`: the same room_id/room_type XOR check as preferred rooms (`ck_ctre_room_xor`), plus uniques on `(clinic_type_id, room_id)` and `(clinic_type_id, room_type)`. `ClinicType.category` is free text; the `"duty_helper"` value the frontend colours specially is a data convention, not a constraint. **`clinic_priority` is server-managed, not client-settable** (`ClinicTypeIn` has no such field — a stale client that still sends one is silently ignored by Pydantic's default extra-field handling): a partial unique index (migration 005) enforces a contiguous 1..N sequence over `is_enabled=true` rows only. Three router mechanisms maintain that invariant — `_next_priority` (max+1 append, on create and on a disabled→enabled transition), `_close_gap` (per-row ascending-order decrement with a flush between rows, not a bulk `UPDATE`, since Postgres checks the non-deferrable unique index per row in visitation order — on delete of an enabled row and on an enabled→disabled transition), and `PUT /clinic-types/reorder` (the only genuine arbitrary permutation, via a two-phase negative-placeholder update: every affected row is parked at `-(new_priority)` and flushed before any row gets its real positive value, so no intermediate state can collide). The disabled→enabled transition has one ordering subtlety: the new priority must be assigned *before* the row's `is_enabled` flip is flushed, or the flush briefly persists an enabled row still holding its old, possibly-colliding priority.

**Generation inputs.** `leave_entries`: half-day granularity, unique `(doctor_id, date, period)`; weekday-only is an API rule, not a schema one, so stray weekend rows are representable. `duty_assignments`: unique `(date, period, duty_type)` — at most one primary and one secondary row per session globally. This table is a generation input only; manual duty edits on a generated rota do not write back to it. Secondary duty must fall on the week's first *fully open* weekday — enforced in `routers/duty.py`'s `create_duty` against live `PracticeClosure` data, not a schema-level `model_validator` (which can't see the DB); a duty of either type on its own closed `(date, period)` is rejected the same way, mirroring Phase 0's `duty_on_closed_date` — the rejection is period-specific, so a primary duty on the open half of a partly closed day is still accepted. A duty on a date outside the named doctor's employment window is rejected there too, for the same reason and mirroring Phase 0's `duty_outside_doctor_dates`.

**Practice closures (bank-holiday weeks, and half-day closures such as a city-wide Thursday-afternoon training session).** `practice_closures`: global planning data, non-nullable `period`, unique `(date, period)`, optional `name` — entered independently of any generation run via `/closures`, since the Duty page needs to know about a closure weeks before a `RotaConfig` exists. A full-day closure is two rows sharing a date, not a distinct value on `period` — there is deliberately no "full day" sentinel in the data model, mirroring `leave_entries`' half-day granularity; the closures UI offers a "Full day" create option that fans out into two `POST`s, but the wire schema itself only ever knows AM or PM. `rota_closures`: unique `(rota_id, date, period)`, FK `generated_rotas` cascade-delete — snapshots which `(date, period)` slots fell inside a rota's range *at generation time*, the same self-contained-snapshot principle as `template_type` on `rota_sessions`. `generate.py` writes these rows in the same transaction as the rota; `grid_utils.rebuild_rota_grid()` reads from this table, not `practice_closures`, so a closure added or removed afterwards cannot change how an existing draft/committed rota renders or validates. See "Generation Engine" above for how `closed_slots` flows through Phases 0/2/5/12.

**Master template.** `master_rota_templates` / `master_rota_sessions`. **`is_active` is not schema-enforced unique** — single-active-template is app logic, and readers must (and do) resolve multiple active rows deterministically rather than assume one. Sessions: `ck_mrs_week` (week 1–4), unique `(template_id, doctor_id, week, day, period)`, `session_type` (requires_room / no_surgery / admin_time / pre_assigned / wfh), nullable `room_id`. **Row existence is itself the data**: a doctor with no row for a slot does not work that slot — Phase 2 creates no grid slot for it — so editing a working pattern means creating/deleting rows, not just updating them.

**Staging.** `rota_stagings` (header) / `rota_staging_sessions` (migration 011) — the editable, run-scoped copy of the active template's rows for a date range that sits between the master template and generation (see "Staging" below for the full feature). `rota_stagings.config_id` is unique (one staging per `RotaConfig`); `source_template_id` points at the `MasterRotaTemplate` it was copied from, resolved by id rather than `is_active` so a later template change cannot orphan an in-progress staging. `source_template_start_week` (migration 015, `server_default 1`) records the template week the copy actually started from, since `RotaConfig.template_start_week` is always persisted as 1 on a staged config and so cannot be read back for that purpose — see "Recurring notes" under Generation Engine for why this is needed. `completed_at` is nullable and is the lifecycle marker — null means active, set means completed — mirroring `generated_rotas.committed_at`/`archived_at`'s convention; "an active staging exists" is a direct query on this column, independent of whatever later happens to the `GeneratedRota` a completed staging produces. `rota_staging_sessions` mirrors `master_rota_sessions`' shape exactly (`ck_rss_week`, unique `(staging_id, doctor_id, week, day, period)`), with `staging_id` in place of `template_id` — no real date is stored on the row; week/day/period plus the parent staging's `RotaConfig.start_date` derive it, same as a generated rota's sessions relative to their run.

**Recurring notes** (migration 015). `recurring_notes` / `recurring_note_doctors` / `recurring_note_weeks` — a standalone entity, not a `MasterRotaTemplate` field, since a note recurs by day-of-week across every generation run and can name several doctors at once, which no single template cell can represent. `recurring_notes` carries `text`, `day`, `period`, `is_active`; the two child tables are an explicit doctor list (`recurring_note_doctors`, unique `(note_id, doctor_id)`) and an explicit set of template weeks 1–4 (`recurring_note_weeks`, unique `(note_id, template_week)`, checked `BETWEEN 1 AND 4`) — there is deliberately no "no rows means every week" shorthand, so "every week" is stored as all four rows. Cascade parent-to-child is ORM-level (`cascade="all, delete-orphan"`), matching every other parent/child pair in this schema. See "Recurring notes" under Generation Engine for how these are consumed at generation time.

**Generated rotas.** `rota_configs` (start date; `num_weeks IN (1,2,4)`; `template_start_week` 1–4), `generated_rotas` (`status` draft/committed; **at most one draft globally, enforced at the API layer, not the schema**), `rota_sessions`. Session rows are unique per `(rota_id, doctor_id, week, day, period)`, and the standing invariant is: a row exists iff a template entry existed for that slot at generation time — edits mutate rows but never create or delete them (the frontend pivot relies on this). `template_type` (nullable, added by migration 002) snapshots the slot's `MasterSessionType` at generation time so later template edits cannot rewrite how historical rotas read; since M4.1 the cell edit menu may manually overwrite it, so its precise meaning is "generation-time snapshot, possibly manually overridden". Null (pre-002 rows only) reads as a normal session. `is_supervising` (non-nullable boolean, default/backfill `False`, added by migration 003) is set by Phase 9C at generation time and may also be set verbatim by the session PATCH; unlike `template_type` there is no derived-value fallback — pre-migration rows simply read as unsupervised, which is correct (Phase 9C plan, Decision 7). `is_on_leave` is not stored — derived from `leave_entries` at read time. Sessions on a draft are freely mutable; "committed rotas are immutable" is an API-layer 409, not a data-layer property.

**Generation decision log.** `rota_generation_log` (migration 007): one row per `DecisionLogEntry` the engine collects during a run, FK `generated_rotas` cascade-delete, unique `(rota_id, sequence)`. Deliberately **plain nullable integers, no FK constraints**, on `doctor_id`/`related_doctor_id`/`room_id`/`related_room_id`/`clinic_type_id` — every row already carries a self-contained `message`, so an orphaned id in a historical entry (e.g. a since-deleted clinic type) is harmless, and real FKs would silently expand the delete-blocker surface on every referenced table. Rows are written once, in the same transaction as the rota, by `_write_to_db()` on a successful run, and are never mutated afterwards — `commit_rota()`/`rollback_commit()` don't touch this table, unlike the counter snapshot tables. Cleanup is via the same cascade-delete relationship pattern as `RotaClosure`.

## Counters and snapshots

`clinic_counters` (unique `(doctor_id, clinic_type_id)`) and `system_counters` (unique `(doctor_id, counter_type)`, types `room_move` / `supervision`) store **raw counts only**. The fairness metric, weighted score = `raw_count / sessions_per_week`, is computed in the engine (`CounterState`) and mirrored in the frontend (`weightedScore.ts`); it is never stored and no SQL computes it. Clinic counters are deliberately **shared-only** — one row per (doctor, clinic type) regardless of how many schedule slots the type has; an earlier per-slot design was reversed before M2 and never shipped. Counter rows are created lazily (get-or-create in the engine and swap endpoints), not seeded — only system counters are seeded.

`rota_clinic_counter_snapshots` / `rota_system_counter_snapshots` support the draft lifecycle. On generation, every existing counter row's value is snapshotted (pre-generation values) against the new rota before any counter write. While the rota is a draft, all mutations — generation increments and manual-edit adjustments — hit the live counter tables. **Commit** deletes the snapshots, making live values the new baseline. **Scrap** restores every snapshotted value, deletes counter rows created after the snapshot, and deletes the rota — so scrap-then-regenerate equals generating once from the original baseline, and any drift from incremental edit adjustments is bounded by the draft's lifetime. Snapshot rows are write-once, and since at most one draft exists, at most one rota's snapshots exist at a time.

## Seeds

`seed/run_all.py` runs five seeders in dependency order inside one transaction (commit at the end, rollback on any error):

1. `seed_rooms.py` — the 14 rooms, hardcoded.
2. `seed_doctors.py` — from `seed/data/setup.csv`. Preferred-room cells resolve to a `room_id` when they match a room code, otherwise to a `room_type` token; anything else raises. `sessions_per_week` is seeded as the 10.0 placeholder for every doctor.
3. `seed_system_counters.py` — one zero-valued `room_move` and one `supervision` row per active doctor.
4. `seed_master_rota.py` — one template ("Default", active) from `seed/data/master_rota.csv`, whose rigid format is documented in the module docstring (two rows per doctor AM/PM, four fixed week-column blocks, a closed cell vocabulary: room codes, `D?`, `No surgery`, `Admin time [room]`, `Working from home`); any unrecognised cell or structural deviation raises.
5. `seed_reception_coverage.py` — one `reception_coverage_rules` row per `(day, hour)`, hardcoded, `min_phones_staff = 3` for hours 9 and 10 and `2` for every other hour. Independent of the clinical seeders — reception has no doctors/rooms dependency — positioned last only for readability. `reception_staff` is deliberately not seeded, entered through the UI like clinic types.

The seeders are **not idempotent and have no designed rerun guard**. In practice a rerun fails immediately on `rooms.code` uniqueness and the transaction rolls back — adequate protection, but incidental, and it depends on `seed_rooms` running first (`master_rota_templates.name` has no unique constraint, so a template-only rerun would happily create a second active template).

Deliberately not seeded: **clinic types** (and their children) — entered via the frontend — and **clinic counters** (created lazily). `setup.csv` also remains in the repo as reference data. Production seeding is a manual run from a local machine against Railway's public Postgres URL; it has been run once.

## Infrastructure and request lifecycle

- **Auth seam.** `get_current_user()` is DB-backed session auth attached as a per-endpoint `Depends()` on every router handler — deliberately not middleware, so the auth model swaps out with zero changes to route handlers or business logic (this is exactly what happened when the original shared-token shim was replaced). A request must carry `Authorization: Bearer <token>`; the token is SHA-256 hashed and looked up against `sessions.token_hash`. 401s uniformly — a client cannot distinguish "no such token" from "expired" from "deactivated user" — if the header is missing, the token has no matching session, the session has expired (fixed 30-day expiry from login, no sliding renewal), or the owning user is inactive (so deactivating a user takes effect immediately, no session hunt needed). No fail-open mode: every router endpoint requires a valid session; `/health`, `/docs`, and `/openapi.json` live outside the routers and stay open. See `backend/app/api/deps.py`, `backend/app/api/routers/auth.py`, `backend/app/api/routers/users.py`.
- **Frontend SPA mount.** `mount_frontend()` mounts `frontend/dist` at `/` (path from `FRONTEND_DIST`, defaulting to a `__file__`-relative resolution, so working-directory independent), only if the directory *and its `index.html`* exist — a half-built dist never mounts. `SPAStaticFiles` falls back to `index.html` for unknown non-API paths (client-side routes survive a hard refresh) while `/api/*` 404s stay real JSON 404s; registered routes always beat the mount. No cache-control headers are set — if stale-frontend-after-deploy ever appears, look here.
- **CORS** origins come from `CORS_ORIGINS` (comma-separated; default `*` for dev). Production is same-origin, so the production value is a hardening measure, not a functional one.

## Rota lifecycle

A `GeneratedRota` is `draft` or `committed`, and **one draft exists globally** — generate returns 409 while any draft exists. All mutation endpoints are **draft-only** (409 on committed rotas).

The counter snapshot mechanism is what makes the lifecycle safe: when generation persists, it first snapshots every existing `ClinicCounter`/`SystemCounter` value into the two snapshot tables (before counters are written, so values are exactly pre-generation), then writes counters and sessions in the same transaction. **Commit** deletes the snapshots — the live values become the baseline for future generations. **Scrap** (`DELETE /rota/{id}`) restores every snapshotted value, deletes counter rows created after the snapshot, and deletes the rota, its sessions, and the snapshots, all in one transaction. Scrap therefore also undoes counter edits made by draft editing, and scrap-then-regenerate is equivalent to generating once from the original baseline — this snapshot lifecycle, not recalculation, is what prevents incremental counter updates from drifting.

A Phase 0 generation failure returns 422 with the issues; nothing is committed, so the `RotaConfig` row is discarded along with everything else. `GET /rota` lists all rotas newest first (`created_at DESC, id DESC` — the id tiebreak matters for same-second creation), metadata only; the frontend derives the active draft and committed history from it. No pagination (volume is tens per year). `GET /rota/{id}/issues` re-runs Phase 12 and works on both draft and committed rotas. `GET /rota/{id}` also carries `closed_slots` (one entry per closed `(date, period)`) — read from the `RotaClosure` snapshot, not the live `PracticeClosure` table, so it can't change after generation.

### Rollback commit (M3.7)

`POST /rota/{id}/rollback-commit` undoes a commit one step back through commit history, restoring the rota's counters from its snapshot and flipping it back to draft — the same snapshot mechanism scrap uses, but without deleting the rota. Eligibility is enforced by five checks inside `engine.generate.rollback_commit()` rather than pre-checked in the router (existence, status, a null `committed_at` — meaning this rota predates rollback support and can never be rolled back — no active draft elsewhere blocking it, and chain order): the rota being rolled back must be the **most recent commit** (greatest `(committed_at, rota_id)` among committed rotas with a non-null `committed_at`), or the call 409s naming the blocking rota. `commit_rota()` self-heals the chain by refreshing `committed_at` to now on every commit, including a re-commit after rollback, rather than preserving an original commit time. The frontend mirrors this ordering rule client-side (`isMostRecentRollbackableCommit` in `RotaDetailPage.tsx`) so the Rollback button doesn't render on a request that would 409 — advisory only, since a draft created in another tab between load and click still hits the real 409.

### Archive / unarchive (M6)

`POST /rota/{id}/archive` and `POST /rota/{id}/unarchive` toggle `GeneratedRota.archived_at` — a pure visibility flag with no engine involvement and no effect on counters, sessions, or rollback eligibility. `archive` 409s a draft or an already-archived rota (`_require_committed` plus an explicit check); `unarchive` 409s a rota that isn't currently archived, which also covers drafts since only `archive` ever sets the column. `GET /rota` returns archived rotas unfiltered — there is deliberately no query parameter or server-side filtering; the Committed/Archived split on `RotaPage` is purely client-side, and `isMostRecentRollbackableCommit` must keep scanning the full list including archived rotas, since an archived rota can still be the most recent commit and therefore still rollback-eligible. `rollback_commit()` clears `archived_at` when it flips a rota back to draft — necessary, not cosmetic, since a surviving flag would silently re-archive a freshly re-committed rota with no UI action explaining it. Legacy rotas with a null `committed_at` are archivable (archiving is the only lifecycle action left for a rota that can never be rolled back); the guard checks status, not `committed_at`. The archive/unarchive action itself lives only on `RotaDetailPage`, next to the conditional Rollback button — consistent with commit/scrap/rollback already being detail-page-only actions.

`GET /rota/{id}/log` returns the generation decision log — `rota_generation_log` rows, ordered by `sequence`. Unlike `/issues`, which persists nothing and re-runs Phase 12 via a grid rebuild on every request, `/log` reads rows written once, in the same transaction as the rota, by `_write_to_db()`, and never re-derived; there is no grid rebuild and no server-side filtering (a full 4-week run produces at most a few hundred rows, and the frontend's `GenerationLogPanel` filters client-side by phase and doctor). Works on drafts and committed rotas alike; empty for a rota that predates this feature or was created outside `generate()`.

## Editing endpoints and re-validation

Every editing endpoint follows the same contract: mutate, re-run Phase 12 (via `engine/grid_utils.py` — a fresh grid rebuilt from persisted `RotaSession` rows per request, no caching, trusting the persisted `template_type` where present), and return the fresh issues in the response. **Eligibility is deliberately not checked server-side**: a force-assignment to an ineligible doctor succeeds and comes back with warnings — apply-then-warn with undo is the frontend's job. Duty role edits never write back to `DutyAssignment` (a generation input, not an audit trail); Phase 12 reads roles from the rebuilt grid, so re-validation stays correct regardless.

- **`PATCH /rota/{id}/sessions/{session_id}`** — partial update of `is_wfh`, `notes`, and/or `is_supervising`, with field presence detected via `model_fields_set` (`notes: null` clears; an absent field is untouched; an empty body is 422). Setting `is_wfh` true also **clears `room_id`** — room freeness is derived from session rows, so WFH must actually free the room. Toggling it off does *not* restore a room; the slot warns `unresolved_room` until one is assigned. `is_supervising` is applied verbatim with no side effects in either direction — toggling `is_wfh` does not clear it (Phase 12's `supervision_on_incompatible_slot` warns instead), and it never adjusts the `SUPERVISION` system counter, which is written only at generation time. This endpoint has no `room_id` field and never displaces — its "safe partial update, no side effects on other rows" contract is why the set-room/set-role operations live on separate endpoints.
- **`POST .../swap-roles` and `.../swap-rooms`** — exchange `(role, clinic_type_id)` or `room_id` between two sessions. **One side may be empty, making the swap a move** — documented contract with tests, not an accident; both sides empty is 422. `swap-roles` adjusts `ClinicCounter` rows (get-or-create upsert, floored at 0 on decrement; a same-clinic-type swap is a counter no-op); `swap-rooms` never touches counters. A room move deliberately leaves the source warning `unresolved_room` if its slot is `REQUIRES_ROOM` — the signal to reassign. Because the field exchange is symmetric (counters included), repeating the identical call is a true inverse, which is what the frontend's undo relies on.
- **`POST .../sessions/{session_id}/set-room`** — one-sided room assign/clear with displacement. `room_id: null` clears with no displacement lookup and no `is_wfh` change. A set `room_id` displaces any same-slot holder — its room is **cleared to blank, not reverse-swapped**; the blank/`unresolved_room` state plus the returned warnings are the honest signal — and clears the target's `is_wfh` if set (the PATCH rule in reverse). Unknown rooms 404 via explicit lookup (FK errors would surface as 500s on Postgres at flush). No counter effect. Returns `{session, displaced_session, issues}`.
- **`POST .../sessions/{session_id}/set-role`** — a **verbatim `(role, clinic_type_id, template_type)` triple setter**: it always writes the given triple exactly, which is what makes every frontend undo expressible as another call to it. Displacement applies only to steal-class assignments (duty roles; `role=clinic` with a specific `clinic_type_id`) — the displaced side is cleared to `None`/`None`, one-sided. If the written triple ends as `role=None` with `template_type` in `no_surgery`/`admin_time`, the target's room is also cleared (a no-surgery session silently holding a room would block it with no warning). Counter adjustments mirror `swap-roles`, with a same-clinic-type reassignment guarded to a no-op. Same response shape as `set-room`.

## Master rota write surface

The template has no draft/committed lifecycle, so its editing endpoints are **not draft-gated and never run Phase 12** — the per-endpoint displacement rule is the only conflict-avoidance mechanism. Edits affect future generations only: `RotaSession` snapshots `template_type` at generation time, so existing drafts and committed rotas are untouched by a template edit made afterwards.

- **`GET /master-rota/active`** — the single active template with its flat session list, joined to doctor/room codes. `MasterRotaTemplate.is_active` is not schema-enforced unique, so the endpoint orders by `id` and takes the first match rather than `.scalar_one()`: a second active row resolves deterministically instead of 500ing the page.
- **`PATCH /templates/{template_id}/sessions/{session_id}`** — a verbatim `(session_type, room_id)` **pair setter** (both fields always required, not a partial update — undo replay is just another PATCH). Works on any template, active or not. A set `room_id` displaces any same-slot-same-week holder: its room clears, and a displaced `PRE_ASSIGNED` becomes `REQUIRES_ROOM` (a roomless `PRE_ASSIGNED` means nothing to Phase 2) while a displaced `ADMIN_TIME` keeps its type.
- **`POST /templates/{template_id}/sessions`** and **`DELETE .../sessions/{session_id}`** — cell *existence* is itself the data (a doctor with no row for a slot simply doesn't work it), so editing a working pattern needs row create/delete, not just the pair setter. POST shares PATCH's displacement rule and validator (`MasterSessionPairIn` base, enforcing the `session_type`/`room_id` pairing: `PRE_ASSIGNED` requires a room, `ADMIN_TIME` optionally has one, `REQUIRES_ROOM`/`NO_SURGERY`/`WFH` must not), and pre-checks the slot for a 409 rather than letting the unique constraint raise. DELETE is a hard delete returning 204 (no children, nothing to cascade). **The server is a permissive verbatim writer** — no doctor-active check server-side; the frontend gates the add-session affordance to active doctors, and the permissiveness is what keeps undo-recreate working if a doctor is deactivated mid-session. PATCH and POST share one response shape, `MasterSessionWriteOut` (`{session, displaced_session}` — no `issues` field, since Phase 12 doesn't apply here).

## Staging

The editable step between the master template and generation: during school holidays, staff often need one-off pattern changes (covering an extra session, dropping one) that shouldn't become a permanent template edit. A staging is a run-scoped copy of the active template's rows for a chosen date range; edits happen against the copy, and the existing Phase 0–12 pipeline then runs against the edited copy unchanged. The master template itself is never touched — see "Staging branch (`context.py`)" under Generation Engine above for the one place the engine is staging-aware.

**Lifecycle.** `POST /staging` copies the active template's rows for `[start_date, start_date + num_weeks)` into a new `RotaStaging` + `RotaStagingSession` rows, creating a `RotaConfig` alongside it exactly as a direct `/rota/generate` call would (`template_start_week` is applied once, at copy time, to select which template weeks get copied, then discarded — the persisted config always has `template_start_week=1`, which is also what makes staging rows keyable by *generation* week rather than template week). Requires: no active draft, no active staging, no committed-rota overlap, and exactly one active template (the engine's strict rule, not the master-rota GET's lowest-id resolution). At most one staging exists globally, mirroring the at-most-one-draft rule; `/rota/generate` itself additionally 409s while a staging is active, though it remains reachable directly (used by tests; the frontend only calls `/staging` now).

`POST /staging/{id}/complete` runs the Phase 0–12 pipeline against the staged copy's config — the same call `generate_rota` makes against a directly-submitted config — and on success sets `completed_at`, retaining the staging rows as a record of the run rather than deleting them (a snapshot of the final edited state, not a diff against the template — the template may itself have moved since). It re-checks the draft and overlap locks (a `rollback_commit` can produce a draft mid-staging even though direct generation is blocked; the create-time overlap check was fail-fast, this is the authoritative re-check). A Phase 0 failure here is a 422 with nothing committed by this request, but the staging rows and its `RotaConfig` — committed by the earlier `POST /staging` — survive; the user fixes the offending staged edit and completes again. This is a deliberate divergence from `generate_rota`, which discards the `RotaConfig` it creates in the same failed request.

`DELETE /staging/{id}` (abandon, active-only) hard-deletes the staging (`RotaStagingSession` rows cascade) and its `RotaConfig` — nothing else can reference either at that point.

**Editing.** `PATCH`/`POST`/`DELETE` on `/staging/{id}/sessions[/{session_id}]` mirror the master rota template's contract verbatim — pair setter, same-slot room displacement including the `PRE_ASSIGNED` → `REQUIRES_ROOM` demotion of a displaced roomless pre-assigned, permissive writer with no eligibility checks — reusing `MasterSessionPairIn` by subclassing so the two grids' validation cannot drift apart. One addition: session create 422s when `week` exceeds this staging's own `num_weeks` (the shared schema's 1–4 bound is necessary but not sufficient for a 1- or 2-week staging). All three 409 on a completed staging.

**What real dates add.** Unlike the dateless master template, a staging row has a calendar date (via its config's `start_date`), which surfaces two things the template editor cannot: `is_on_leave` per session, derived at read time from `leave_entries` the same way `RotaGrid` does; and `closed_slots`, read live from `PracticeClosure` for the staging's range (no snapshot exists yet — generation at complete time reads live closures regardless, so live is correct here). Rows on a closed `(date, period)` are still copied and editable; Phase 2's closed-slot skip remains the single closure authority, and the closed-header/closed-cell treatment on `StagingGrid` is display-only.

The doctor employment window is treated the *opposite* way, and deliberately so: the copy loop skips a row entirely when its doctor is out of window on that date, and skips the extra-session new-row branch for the same. A closure is a property of the date that `StagingGrid` can render as such, so a copied-but-greyed row still tells the admin something true. An out-of-window row has no such display — it would look like an ordinary editable cell that then silently vanished at Complete, since Phase 2 (still the authority) drops it either way. The skip is recorded in `covered_slots` before it fires, so a planned extra session on the same slot cannot fall through to the no-template-row branch and reinstate what the window just removed.

## Leave planning

Forward planning of annual leave and planned extra sessions together, a month at a time, with a live clinical-headcount total so the admin can see what an absence does to cover *before* saving it. `routers/leave_planning.py` owns both endpoints; `/leave` and `/extra-sessions` are untouched and remain the ad-hoc, one-off path during the year.

**`GET /leave-planning/coverage`** returns one `(date, period)` entry per weekday in the range, capped at 62 days (the grid asks for a month; the cap is what stops this being an unbounded scan). Weekends are omitted entirely rather than returned as zero — the grid has no weekend columns. Four design decisions shape the count, and none of them are obvious from the code alone:

- **Template *week 1* only.** Mapping a calendar date onto the 4-week template cycle needs a `start_week`, and the only source of one is `RotaConfig.template_start_week` — a per-run value with no calendar anchor, which the staging path pins to 1 regardless. So the endpoint reads `MasterRotaSession` rows where `week == 1` and treats that as the working pattern for every date. Sound because Partner and salaried doctors work the same sessions every week; rooms may vary, which is irrelevant to leave planning. Flattening the template from four weeks to one is a separate ticket, not a prerequisite.
- **Partner and Salaried only**, applied server-side here *and* client-side in the grid's row build, so the on-screen total always equals the sum of the visible rows. The bulk write endpoint below is deliberately **not** type-filtered — it is a generic write path with no reason to refuse a Trainee.
- **Clinical sessions only:** a doctor counts when their *effective* type is `REQUIRES_ROOM` or `PRE_ASSIGNED`. `NO_SURGERY`, `ADMIN_TIME`, `WFH` and "no template row" all count zero — exactly the set the extra-session override converts *into* `REQUIRES_ROOM`, so the two halves of the grid agree by construction.
- **The extra-session override is applied, not a flat `+1`.** Leave and extra sessions are not symmetric: leave is read live by the engine every run, while an extra session is applied once, conditionally, in the `POST /staging` copy loop, and is a no-op on a slot the doctor already worked. The endpoint imports `routers/staging.py`'s `_OVERRIDABLE_TYPES` rather than redeclaring it so the two cannot drift; it does not reproduce the copy loop's `ADMIN_TIME`-with-room → `PRE_ASSIGNED` demotion, since both outcomes count identically here. Leave wins over an extra session on the same slot, matching the copy loop.

Closures suppress coverage: a `(date, period)` in `PracticeClosure` returns `is_closed=True` with `headcount=0`, since Phase 2 creates no slot there — the grid renders that as "—", not as an uncovered slot. Everything the endpoint reads (closures, leave, extra sessions, the employment window) is read **live**; this is forward planning, not the rendering of an existing rota, so there is no snapshot to prefer. The active template is resolved the way `GET /master-rota/active` resolves it — lowest id among active rows, since `is_active` is not schema-enforced unique — and no active template at all yields zeros rather than a 404, so the grid still draws its leave cells.

**`POST /leave-planning/bulk`** applies a batch of `leave` / `extra_session` / `clear` actions in one transaction, in a fixed order — **clears, then leave, then extra sessions** — so a batch touching both sides of a slot resolves deterministically in leave's favour. The clears are flushed before any insert: SQLAlchemy emits a mapper's INSERTs before its DELETEs within one flush, so clear-then-set-leave on the same cell would otherwise collide on `uq_leave_slot`.

Nothing here 409s on a state that already matches — the grid sends the state it *wants*, so setting leave where leave already exists is a `"duplicate"` skip. An out-of-window action is likewise a skip, not a 422. Weekends and unknown doctor ids are the two things that do fail the whole batch (422 and 404): both can only be a client bug, unlike the window, which legitimately moves under a stale grid. A pre-existing `ExtraSessionEntry` the batch's leave covers is *reported* in `superseded_extra_sessions` — never deleted, never blocked — mirroring `create_leave_bulk`. `clear` removes both the `LeaveEntry` and the `ExtraSessionEntry` for the triple (both are keyed on the same `(doctor_id, date, period)`, so there is nothing to disambiguate).

`_release_draft_rooms` is imported from `routers/leave.py` and called for every leave candidate, **duplicates included** — the same deliberate over-call `create_leave_bulk` makes, so an all-duplicates save still heals stale room state. The asymmetry is preserved too: `clear` does not restore rooms, matching both `/leave/bulk-delete` and the WFH behaviour.

## Conventions

- **Transaction boundaries:** each mutating endpoint commits explicitly on success; a raised `HTTPException` leaves the session uncommitted, so partial work is discarded.
- **Duplicate detection** is via catching `IntegrityError` on commit (race-free), mapped to 409 — not pre-checking. The one exception is the master-rota session POST above, which pre-checks to produce a descriptive 409.
- **The room_id/room_type XOR** on room eligibilities and preferred rooms is enforced at the API boundary (Pydantic validators, 422) as well as by the DB check constraints.
- **Field naming:** objects embedded in lists alongside other `_id` fields use prefixed ids (`rota_id`, `session_id`, `template_id`) — a bare `id` would be ambiguous there; standalone CRUD entity schemas (`DoctorOut`, `RoomOut`, ...) use plain `id`. The frontend's types mirror wire names exactly, no client-side renaming.

## Domain: Frontend Reference Pages

Application shell, auth boundary, and the general-purpose parts of the API client are shared with the reception rota and documented under "Shared Frontend Infrastructure" in `documentation/architecture.md`. This section covers the clinical-only reference-data pages and their supporting utilities.

### Reference Data Pages

- **DoctorsPage** — active-only management table plus `DoctorFormDialog` (Zod `doctorSchema` validation; preferred-room list ordered via `reorderPreferredRooms`, order being meaningful to Phase 5/7–9A room resolution). Deactivation is the backend's soft-delete DELETE (sets `active=False`; 409 when the doctor has sessions on a committed rota). On that 409 the page surfaces a "Deactivate instead" button firing `PATCH {active: false}` — the remedy the 409 message names. There is deliberately no show-inactive toggle or reactivate path in the UI; a deactivated doctor is recoverable only via the API.
- **ClinicTypesPage** — CRUD over clinic types via `ClinicTypeFormDialog`: name, category (free text; `"duty_helper"` is the colouring convention, explained as inline help text since the form is the only place a non-technical admin would learn it), `room_required`, schedules, and doctor/room eligibilities. Updates are the PUT replace-children pattern, one nested payload per save. Zod (`clinicTypeSchema`) validates form state, not the wire shape — room-eligibility rows carry a client-only `kind` discriminant making the room/room-type XOR structurally unrepresentable; `mapValidationErrors` maps server 422s back onto form fields. **Priority is no longer a form field** — the page itself renders enabled clinic types as a `@dnd-kit/sortable` list (same `DndContext`/`useSortable` pattern as `DoctorFormDialog`'s preferred-room reordering; array position is the only source of truth for order, nothing duplicated into per-row state) with a drag handle per row, firing `PUT /clinic-types/reorder` on drop with optimistic local reorder and rollback on error. Disabled clinic types render in a separate, non-draggable section below, sorted by name — their stored priority is stale by definition, so it's never shown or relied on.
- **LeavePage** — one Timetastic-style range form (date range, edge half-day options, Add/Remove mode toggle) replacing the original three forms, plus the filterable table with per-block delete. Submissions expand via `expandLeaveRange` (below) onto `POST /leave/bulk` / `bulk-delete`, fired concurrently via `Promise.allSettled` with per-segment failure reporting — no rollback, no faked atomicity. **LeaveRangePreview** renders a read-only mini-calendar (Mon–Fri, AM/PM split cells, max 4 months) of what the pending submission will do against existing leave. The table itself renders one row per consolidated **leave block** (`collapseLeaveEntries`, below), not one row per half-day entry: block delete fires a single `bulk-delete` call over the block's own `(start_date, end_date, period)`, reusing the range form's confirm wording via a shared `describeSpan` helper; failures land in a separate `tableError` slot so they can't mix into the form's add/remove summary. The unfiltered view (no doctor selected) sorts blocks by `compareDoctorDisplayOrder` then `start_date`, so one doctor's blocks render together rather than interleaved by date. Per-entry delete (`useDeleteLeave`) has no caller left on this page — a single half-day session is still removable via the Remove-leave form above the table (single day, AM/PM only).
- **LeavePlanningPage** — the month-at-a-time planning grid (`LeavePlanningGrid`), the forward-planning counterpart to `LeavePage`'s ad-hoc range form. Rows are Partner/Salaried only, filtered by **window *overlap* with the displayed month**, not "in window today" — a doctor leaving mid-month must still show for the part of the month they worked, with the days after their `end_date` rendered inert. Cell state is never stored per cell: it is derived at render from the server's `LeaveEntry`/`ExtraSessionEntry` rows merged with a page-level pending map keyed `(doctor_id, date, period)`, so a pending edit and the row underneath it cannot disagree. Clicking cycles normal → leave → extra planned → normal and writes only to that map; a click returning a cell to its server state deletes the key rather than recording a no-op, keeping the unsaved-count badge honest. Save posts the whole batch to `POST /leave-planning/bulk` in one transaction. Two kinds of inert cell get deliberately different treatments — closed reuses `RotaGrid`'s solid `bg-gray-200` and totals as "—", out-of-window is plain absent grey — because confusing "the practice is shut" with "this doctor isn't employed yet" would mislead. Skips and superseded extra sessions in the response are surfaced as *information*, not error: the save succeeded.
- **DutyPage** — manages `DutyAssignment` rows (the pre-planned duty inputs: validated by Phase 0's `duty_on_leave`/`duty_on_incompatible_slot`/`duty_on_closed_date` checks, applied to the grid by Phase 4) through **DutyGrid**, a week-at-a-time editable grid. Week completeness (`dutyWeekSlots.ts` / `dutyWeekComplete.ts`) is computed client-side and shared with RotaPage, which shows the same incomplete-duty-week warning before generation. Closure-aware via `useClosures()` — `buildColumns` renders a closed AM/PM cell as inert (no drop target) on a per-period basis and attaches the secondary-duty pair to the week's first *fully open* weekday (both periods open) instead of always Monday, mirroring the engine's `first_open_weekday_by_week` (reimplemented in TS as `firstOpenWeekday`, not shared, so its test file carries the matching case matrix).
- **ClosuresPage** — practice closures (bank holiday weeks, and half-day closures such as a training afternoon): list, add (date + AM/PM/Full day + optional name), delete, via `useClosures`/`useCreateClosure`/`useDeleteClosure`. AM/PM/Full day is UI sugar only — there is no `/closures/full-day` endpoint or `period: "FULL"` value; picking Full day fires two `POST`s (one per period), and deleting a full-day entry from the list fires two `DELETE`s. Global planning data, independent of any generation run or rota — a closure applies automatically to any rota generated over it, so there is nothing to select on the generate form itself.
- **CountersPage** — read-only view of live `ClinicCounter`/`SystemCounter` values (committed baseline plus any in-progress draft's edits), joined with doctor/clinic names by the API. Each row also shows a client-computed weighted score (`weightedScore.ts`), mirroring the engine's `raw / sessions_per_week` allocation scoring exactly — including `sessions_per_week == 0` scoring as infinite (never preferred), kept distinct from the genuine no-data case.
- **UsersPage** — CRUD over `users` via `UserFormDialog` (Zod `userFormSchema`, parameterised by create/edit mode: password required min-8 on create, optional on edit where a blank field means "leave unchanged" and doubles as the reset-password flow). Unlike `DoctorsPage`, the list is not active-only — it shows every user, inactive ones flagged `(inactive)` (the `LeavePage` convention), since this page is the only recovery path once a user is locked out. Deactivate/reactivate is `PATCH {active}` with a confirm prompt on deactivate; the backend's 409 (refusing to deactivate the last active user) surfaces as a toast rather than a form error, since the action has no form of its own.

### Shared Utilities

- **expandLeaveRange.ts** — pure function expanding a date range plus edge options into 1–3 **disjoint contiguous segments** (`{start_date, end_date, period}` — exactly the bulk endpoint body shapes). Per-day row expansion happens server-side, not here; the client also does no weekend logic (bulk add skips and reports weekends; bulk delete does not weekday-filter). Disjointness is what makes concurrent segment submission safe, and is asserted as a property in its tests. The contradictory single-day PM+AM edge pair throws — unreachable from the UI, guarded against programmatic callers.
- **collapseLeaveEntries.ts** — the inverse of `expandLeaveRange`: groups a doctor's individual `(date, period)` `LeaveEntry` rows back into the fewest possible contiguous `LeaveBlock`s for display. A block is a maximal run of consecutive weekdays with at least one entry, per doctor; a weekend gap (Fri→Mon) doesn't break a run, but a stray weekend *entry* does, since bulk add is weekday-only and such a row can only be anomalous data — it ends the run and becomes its own single-day block. A leading single-day PM and trailing single-day AM are absorbed into an adjacent full-day run and surfaced as `half_start`/`half_end` flags rather than separate rows (the true inverse of `expandLeaveRange`'s edge segments); any other half-day shape (interior, or a multi-day half-day run — neither reachable from the form) starts its own block rather than being hidden behind a flag. The exactness property this guarantees — every weekday in a block's span has an entry, and no weekend entry can fall inside that span — is what makes a single `bulk-delete` call over a block's own `(start_date, end_date, period)` safe to attach to that block's row; asserted as a property in its tests, not just spot-checked.
- **planningMonth.ts** — the pure half of the leave planning grid, kept out of the component for two reasons that are not stylistic. First, `applyPendingToCoverage` re-applies `GET /leave-planning/coverage`'s own rules **client-side**, so the cover total updates as cells are clicked without a round trip — the two calculations have to agree exactly, which is only checkable if this one is testable alone, so its test file carries the same case matrix as `TestCoverage`. It is a *delta* against the server's baseline rather than a from-scratch recount: an unedited slot always shows the server's own number, and only edited `(doctor, slot)` pairs are adjusted, so the page can never silently diverge for a doctor it does not render. Second, `buildPlanningActions` turns the pending map into the batch — usually one action per cell, but moving *between* leave and extra planned emits a paired `clear` first. Without it the endpoint would skip the action (`leave_exists` in one direction, a surviving superseded extra session in the other) and the saved state would not match the grid; the bulk endpoint's clears-before-inserts flush exists precisely so that pairing is legal.
- **date.ts** — date-only strings are parsed by manual Y/M/D construction, never `new Date(dateString)` (which parses as UTC midnight and renders as the previous day in negative-UTC-offset timezones); `isMonday` gates generation start dates.
- **groupDoctors.ts** — the canonical doctor display order (Partner, Salaried, Trainee, AHP; alphabetical by code within type), shared by both rota grids and the reference pages.

## Frontend: Master Rota

The `/master-rota` route is the interface for viewing and editing the active master template — the fixed 4-week repeating pattern every generation run reads from. All edits persist to the backend immediately (there is no draft/committed lifecycle and no Phase 12 validation on the template); the page states "Changes apply to future generated rotas only", because generated rotas snapshot the template at generation time and are never rewritten by template edits.

### Page and grid

**`MasterRotaPage` (routes/MasterRotaPage.tsx)** fetches the active template via `useActiveMasterRota()` (404 renders a "no active template" state) and owns the undo stack (`useUndoStack<MasterUndoEntry>`), the toast, and the Undo button. It holds its own instances of the three mutation hooks, used only to execute undo replay — the same page-level/grid-level mutation split as `RotaDetailPage`/`RotaGrid`. It does not perform forward edits.

**`MasterRotaGrid` (components/MasterRotaGrid.tsx)** renders the doctor x (day, period) matrix for one week at a time, with week tabs fixed to a constant 1–4 (`MASTER_ROTA_WEEKS` in `pivotMasterRota`). The week domain is defined by backend constraints (`ck_mrs_week`, `template_start_week`), not derived from the session list — deriving it broke once create/delete existed: an empty week had no tab to click into to populate it, and deleting the last session in a week collapsed the tab out from under `activeWeek` state.

Grid rows come from `/doctors` (`useDoctors(false)`), not from the doctors present in the sessions payload: active doctors grouped by type then alphabetical by code (so a newly added doctor with zero template sessions gets a row), plus any inactive doctor who still has sessions, flagged with the same `(inactive)` badge as `RotaGrid`. Cell rendering is plain (no Q13 colour language here): `no_surgery`/`admin_time`/`wfh` get a label badge, `requires_room`/`pre_assigned` render as the room code alone (or blank).

The grid owns all forward mutations (patch/create/delete hooks) and reports each success upward via `onMutationApplied(entry, toastMessage)` with a pre-built undo entry — `previous`/`displaced` values are captured from the in-memory session objects at click time.

### Cell editing — `MasterCellEditPopover`

A sibling of `CellEditPopover`, not a generalisation of it: the two data models (`session_type` + `room_id` only vs. role/clinic type/WFH/notes/leave) share nothing but the popover shell. One component serves both modes via a nullable `session` prop:

- **Edit mode** (`session` non-null): every cell with a session is editable — there is no draft/committed gate and no leave concept to suppress the trigger.
- **Create mode** (`session: null`): absent cells on an *active* doctor's row show a faint "+" affordance opening the same popover; an inactive doctor's absent cells stay inert (you don't build a new working pattern for a leaver). Slot coordinates (`week`/`day`/`period`) are explicit props since create mode has no session to read them from.

The menu is five mutually exclusive `session_type` options — Normal clinic, Pre-assigned room, Admin time, No surgery, WFH — with deliberately no WFH toggle: a five-value enum has no defined "off" state for a checkbox. Pre-assigned room and Admin time open a room submenu; Admin time's alone gets a "No room" entry, since roomless `ADMIN_TIME` is valid, real data.

**Confirm-before-steal:** picking a room already held by another session in the same `(week, day, period)` shows a confirm view before applying. Detection is client-side and advisory via `findMasterRoomHolder` in `slotConflict.ts` — a deliberately separate function from the rota-side `findRoomHolder` (same sibling-not-generalisation reasoning as the popover); the server's own displacement lookup remains the source of truth. Its `excludeSessionId` is nullable for create mode, matching the backend POST's `exclude_id=None`.

**"Remove session"** (edit mode only) is a destructive-styled entry at the bottom of the menu, applied directly with no confirm dialog — a deliberate departure from the steal pattern: confirmation is reserved for steal-class actions, and removal is fully undoable.

**Drag-and-drop was considered and deliberately cut** — the popover covers every operation, swap semantics on a template are unclear, and DnD's cost (context wiring, a `resolveMasterDrag`, a backend swap endpoint) was the largest item for the least value. Revisit only if actually missed.

### API layer and cache — `api/masterRota.ts`

`useActiveMasterRota()` fetches `GET /master-rota/active` into the `masterRotaKeys.active()` cache. Three mutation hooks wrap the write endpoints, all following the splice-in-place/no-invalidate pattern (`setQueryData`, never a refetch — same convention as the rota side's `updateRotaCache`):

- **`useUpdateMasterSession`** (PATCH, a verbatim `(session_type, room_id)` pair setter) splices the response `session` and any `displaced_session` into the cached list, matched by `session_id`.
- **`useCreateMasterSession`** (POST) *appends* the created session (no existing row to match) and still splices any `displaced_session` in place.
- **`useDeleteMasterSession`** (DELETE) filters the cached list by `session_id`.

PATCH and POST share one `{session, displaced_session}` response shape (`MasterSessionWriteOut` server-side).

### Pivot — `pivotMasterRota.ts`

`pivotMasterRota(sessions, doctors)` transforms the backend's flat session list into `{rows, cells, weeks}`: rows built from the doctors list as described above (mirroring `pivotRota`'s `GridRow` shape, including `inactiveWithSessions`), cells keyed by `(doctor_id, week, day, period)` for O(1) lookup via `getMasterRotaCell`, and `weeks` the exported constant `MASTER_ROTA_WEEKS = [1, 2, 3, 4]`.

### Undo — `lib/masterUndo.ts` + the shared `lib/undoStack.ts`

Undo is **replay of inverse API calls against live server state** — nothing is staged client-side, since every forward edit persists immediately. There is no redo. `MasterUndoEntry` is a three-way discriminated union (`kind: "patch" | "create" | "delete"`), deliberately **not** folded into the rota `UndoEntry` union and not routed through `replayUndo.ts` — `buildReplayRequest` is rota-scoped (every branch takes a `rotaId` and builds `RotaSession`-shaped payloads), and the template's write surface shares no branching logic with it. The generic `useUndoStack<T>` is the shared piece.

`buildMasterReplaySteps` preserves displaced-first ordering across all three kinds — restore whatever was stolen before undoing the action that stole it:

- **Undo a patch:** 1–2 PATCHes — restore the displaced session's previous pair first (this may re-displace the target server-side, harmless because the next call overwrites the target with its own exact previous pair), then the target's.
- **Undo a create:** restore any displaced session via PATCH, then DELETE the created row (a re-displacement from the restore is immaterial — the row is deleted next regardless).
- **Undo a delete:** a single POST recreating the row at its original slot with its previous pair. The recreated row gets a new `session_id` (nothing in the client references the old one after the cache filter ran); if another session has since taken the room, the server's ordinary displacement fires as it would for any fresh create — accepted under the single-admin-user assumption. Remove itself never displaces, so there is no displaced side to restore first.

A failed replay re-pushes the consumed entry (undo stays retryable) and shows an "Undo failed" toast. Success toasts are plain descriptions of what changed ("AB Monday AM set to Pre-assigned D1") — there is no issue-count delta here, since Phase 12 never runs on the template.

## Frontend: Staging

The `/staging` route is the interface for the editable holiday-cover step described under "Staging" above. `RotaPage`'s generate form no longer generates directly: submitting it calls `useCreateStaging()` and navigates to `/staging`, where the one-off edits happen before `StagingPage`'s "Complete and generate" action actually runs the pipeline. `RotaPage` renders one of three states in its top slot, in priority order: the active-draft banner (unchanged), an active-staging "resume" banner (`useActiveStaging()`, only rendered when there is no draft — a `rollback_commit` can produce a draft mid-staging, and the draft is the more immediately actionable state), or the generate/start-staging form.

**`StagingPage` (routes/StagingPage.tsx)** takes no id — at most one staging exists globally, so it always operates on `GET /staging/active` (404 renders a "no staging in progress" state with a link back to `/rota`). It owns the toast and the Complete/Abandon actions: **Complete** calls `useCompleteStaging()` and navigates to `/rota/{rota_id}` on success, rendering `GenerateErrorMessage` on a 422/409 exactly as the old direct-generate flow did; **Abandon** confirms via `window.confirm` (matching the commit/scrap pattern) before calling `useAbandonStaging()` and navigating back to `/rota`.

**`GenerateErrorMessage` (components/GenerateErrorMessage.tsx)** was extracted out of `RotaPage.tsx` so both the staging-create form and `StagingPage`'s complete action can render the same three failure shapes (plain-string 409, Phase 0 `ValidationIssue[]` 422, or a raw FastAPI request-validation 422) without duplicating the type guards.

**`StagingGrid` (components/StagingGrid.tsx)** is a clone of `MasterRotaGrid`, not a generalisation of it — kept separate to avoid destabilising the existing component and its tests. It reuses `MasterCellEditPopover` unchanged (the popover is hook-agnostic, and `StagingSession` is a structural superset of `MasterRotaSession`), swapping in the three staging mutation hooks (`useUpdateStagingSession`/`useCreateStagingSession`/`useDeleteStagingSession`) in place of the master-rota ones. Three differences from `MasterRotaGrid`:

- **Week tabs are derived from the staging's own `num_weeks` (1, 2, or 4), not a fixed 1–4.** This required a sibling pivot, `pivotStaging.ts`, rather than reusing `pivotMasterRota.ts` as originally planned — `pivotMasterRota`'s `weeks` is the hardcoded `MASTER_ROTA_WEEKS` constant (correct there, since the template always has all four week slots defined), which would render two or three permanently empty, unusable tabs on a 1- or 2-week staging.
- **Day headers show the real calendar date** (via `weekDates.ts` against the staging's `start_date`) and grey out on a date in `staging.closed_slots` that is *fully* closed; a partly closed date (one period only) keeps the header ungreyed with a qualified label (`closed (PM)`), and greys only that period's cells — copying `RotaGrid`'s header/cell treatment (Task 5) — the master template has no real dates to show.
- **A session with `is_on_leave` gets a small "Leave" badge**, informational only — the popover stays available, since arranging cover for that exact leave is the common case staging exists for.

There is no undo plumbing on this grid (unlike `MasterRotaGrid`/`MasterRotaPage`): mutation results go straight to a plain success/error toast passed down from `StagingPage`, rather than building a `MasterUndoEntry`. The v1 recovery path for a bad edit is abandon-and-restart; the master grid's undo pattern can be cloned later if session-level undo on staging proves necessary.

## Frontend: Generated Rota Grid & Editing

The interactive surface for reviewing and hand-editing a generated rota before commit. `RotaDetailPage` owns page-level state (undo stack, toast, commit/scrap actions); `RotaGrid` owns the grid, drag-and-drop, and cell mutations; the business rules live in pure, unit-testable modules under `src/lib/`. All editing is draft-only — the backend 409s edits on committed rotas, and the frontend renders committed rotas without edit affordances.

A committed rota's read-only view shows up to two further actions, side by side: a conditional **Roll back commit** button (rendered only when `isMostRecentRollbackableCommit` says this rota is eligible — see "Rollback commit" under "Rota lifecycle") and an **Archive**/**Unarchive** toggle keyed off `rota.archived_at`. Both follow the existing commit/scrap confirm-then-mutate pattern (`window.confirm`, static error text on failure) but neither navigates away on success — the page just re-renders from the mutation's response, same as rollback. `RotaPage`'s committed-history list is split into **Committed**/**Archived** tabs on `archived_at`, client-side only; `GET /rota` is never filtered server-side (see "Archive / unarchive" under "Rota lifecycle").

### Pivot invariant

A `RotaSession` row exists if and only if a template entry existed for that `(doctor, template_week, day, period)` at generation time — `phase2._build_grid` skips slot creation with no template entry (the part-time-doctor case) **or a closed `(date, period)` slot**, and no edit endpoint ever creates or deletes a session row. A missing key in `pivot.ts`'s lookup is therefore the real "absent" state; there is deliberately no fallback that reconstructs a cell from `/master-rota`. Grid rows come from `/doctors` (active doctors grouped by type then code, plus inactive doctors who still have sessions, badged `inactiveWithSessions`).

A fully closed day's columns get no other special cell handling as a result: every cell in that column is already the ordinary "absent" `<td>` (grey, no popover, no drop target) that a part-time doctor's gap produces. A partly closed day (one period only) is different since Task 5: the open period's cells render normally, and the closed period's cells get an explicit `bg-gray-200` closed style (`ReadOnlyGridCell`/`EditableGridCell`'s `closed` prop), distinct from the plain-absent grey, since the two must not be visually confused. The header row computes each day's calendar date via `weekDates.ts` and greys/labels a *fully* closed day against `rota.closed_slots` (the `RotaClosure` snapshot, authoritative), showing a qualified `(AM)`/`(PM)` label instead for a partly closed day, and, cosmetically, a live `useClosures()` fetch for the closure's name only (never for the closed/open determination itself).

### Cell colouring (`cellStyle.ts`)

One function, one fixed precedence: **leave > WFH > role colouring (duty / duty-helper / named clinic) > `NO_SURGERY`/`ADMIN_TIME` grey > default**. The grey branch is only reachable when no role is present — a role on an incompatible slot renders as a normal role-coloured cell, and Phase 12's `role_on_incompatible_slot` warning is what surfaces the conflict, not the cell's appearance. WFH's background is unconditionally blank regardless of role; the badge carries the signal. Font colour is derived from the assigned room's type (C = red, W = blue, D/SR = black) — it encodes room location, nothing else; unresolved rooms have no cell-level styling and surface only via the issues panel. Duty-helper colouring is a data convention, not a schema rule: `category === "duty_helper"` on the clinic type renders light blue, anything else renders as a named clinic — a mis-categorised type rendering green is the accepted failure mode for a cosmetic mapping.

### Editing model

Five mutation types, all draft-only, all returning fresh Phase 12 issues alongside the mutated session(s): `swap-roles`, `swap-rooms` (two-sided, or one-sided as a move), `set-room`, `set-role` (one-sided assigns with server-side displacement), and the session PATCH (`is_wfh`/`notes`/`is_supervising` — the last is optional in the payload type specifically so the set-room WFH-restore follow-up patch can omit it). Responses are **spliced into the TanStack Query cache** (`setQueryData`, matched by `session_id`) — never invalidate-and-refetch — so the grid and issues panel update from the response payload alone.

The philosophy is **apply-then-warn with undo**, not ask-first: the server performs any edit it's told to (no eligibility checks on edit endpoints) and returns warnings; the frontend applies immediately and surfaces the result. The single exception is **confirm-before-steal**: taking a room, duty role, or specific clinic type currently held by another session in the same slot shows a confirm view first. Steal detection is client-side against the in-memory grid (`findRoomHolder`), but the server's own displacement lookup remains authoritative for what actually happens. Direct actions (normal clinic, No surgery, Admin time, unassign, clear room) get no confirm.

Duty/clinic picks preserve the persisted `template_type` snapshot; No surgery / Admin time picks overwrite it — the accepted trade-off that weakens the M3.6 invariant to "generation-time snapshot, possibly manually overridden". The popover is not rendered at all on leave cells; it is available on WFH cells, where picking a room clears `is_wfh` (the PATCH rule in reverse).

### Drag-and-drop

`@dnd-kit/core` — deliberately the older of the two active dnd-kit generations, chosen for stability over the pre-1.0 `@dnd-kit/react` rewrite; revisit only if `core` is actually deprecated. Each cell renders up to two explicitly typed chips (role, room); the chip type determines the endpoint — nothing is inferred from the drop. Eligibility (`dragRules.ts`): same day **and** period, target present and not leave/WFH, not self. The day/period check must be explicit — only the active week's cells are mounted (making cross-week drops structurally impossible), but all ten day/period columns are mounted simultaneously, and the API would happily apply a cross-slot swap if the client didn't reject it. A chip is only draggable when its own value is present, so the backend's both-sides-empty 422 is unreachable from this UI. `resolveDrag.ts` keeps the resolution logic pure and unit-testable — real dnd-kit pointer simulation needs bounding rects jsdom doesn't provide.

### Undo

`useUndoStack<T>` is a generic stack; this page instantiates it with the rota `UndoEntry` union (`swap-roles`/`swap-rooms`, `patch`, `set-room`, `set-role`). `replayUndo.ts` builds each entry's replay as a sequence of 1–3 requests, executed serially by `RotaDetailPage`, **displaced session restored first, then the target** (a re-displacement from the first call is harmless — the next call overwrites the target exactly). Swaps and moves replay as the identical call repeated — both swap endpoints are self-inverse, including their clinic-counter increment/decrement pairs, so "repeat the call" and "move it back" are one mechanism. A `set-role` undo appends a trailing `set-room` when the forward op auto-cleared the room, decided by a `roomWasCleared` flag captured from the forward mutation's response at push time, not re-derived at replay time. A failed replay re-pushes the consumed entry (undo stays retryable) with an "Undo failed" toast. The Undo button is always rendered for drafts, disabled when the stack is empty; absent for committed rotas.

**One permanent limitation:** a room cleared by toggling `is_wfh: true` via PATCH cannot be restored by undoing that patch — the PATCH has no `room_id` field and `swap-rooms` 422s when neither side holds a room, so no API path back exists. The undo toast says so explicitly ("room could not be restored, reassign it manually") rather than overstating what happened. Whether that follow-up is needed is inspected from the PATCH replay's actual response in `RotaDetailPage.handleUndo`, not pre-built into the replay sequence. The nullable `set-room` closes this gap for the menu's own `set-room`/`set-role` entry kinds only.

### Validation feedback

The "N new warnings" toast is a **count delta, not a set diff** — `ValidationIssueOut` has no stable identity across Phase 12 re-runs, so "which warnings are new" isn't computable client-side; the issues panel always reflects true current state regardless. (A composite `check`+`week`+`day`+`period`+`message` key would give a workable diff without backend changes if this ever needs tightening.) Issues panel navigation is scroll plus a CSS flash targeting a `data-week-day-period` attribute — the panel and grid share no React state for it. Week tabs always render, even for a one-week rota.

### Counter effects of edits

Edits adjust `ClinicCounter` rows only (get-or-create upsert, floored at 0 on decrement; same-clinic-type reassignments are a no-op). System counters are written at generation time and never touched by edits. Draft-period counter drift is prevented by the snapshot lifecycle, not recalculation: scrap restores the pre-generation snapshot wholesale, commit makes live values the new baseline.
