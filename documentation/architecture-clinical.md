# Rota Generator — Clinical Rota Architecture

Covers the clinical rota only: the generation engine, its data layer, the `/api/v1` REST surface (excluding `/reception/*`), and the clinical-side React frontend. Shared infrastructure (auth, app shell, tech stack, CI, deployment) lives in `documentation/architecture.md`; the reception rota in `documentation/architecture-reception.md`; the phase-by-phase engine specification in `documentation/phase_pipeline.md`.

This document records design decisions and the reasoning behind them. It deliberately does **not** restate what the code says plainly — model constraints, endpoint signatures, component structure and prop lists are all faster to read in the files themselves, and a paraphrase here only drifts out of date. Where a fact is stated once and referenced elsewhere, the reference is the maintenance mechanism, not laziness.

## Generation Engine

`backend/app/engine/` — pure Python, no FastAPI dependency. Transforms the active master template plus reference data into a fully assigned draft rota via a strictly sequential pipeline: an immutable context in, a mutable grid through the phases, one write at the end.

```
engine/
  datatypes.py        SessionSlot, RotaGrid, CounterState, GenerationContext,
                      ValidationIssue, DecisionLog, GenerationResult
  week_map.py         generation-week <-> template-week <-> calendar-date mapping
  context.py          load_context(): one read-only snapshot of all reference data per run
  grid_utils.py       rebuild_rota_grid() / run_phase12_for_rota(): reconstruct a grid from
                      persisted rows for the edit endpoints
  rationale.py        shared decision-log formatting and the canonical stage names
  room_relocation.py  the generic "where does a displaced single-session occupant go"
                      search, shared by Phase 4 and Phase 7-9A
  phases/             phase0, phase2, phase4, phase5, phase7_9a, phase9b, phase9c, phase12
  generate.py         orchestrator + draft lifecycle (get_active_draft, commit_rota, scrap_rota)
```

Phase numbering (0, 2, 4, 5, 7–9A, 9B, 9C, 12) is inherited from the original GAS scripts; the gaps are not missing phases.

### Core data structures (`datatypes.py`)

- **`GenerationContext`** — frozen dataclass holding all reference data for one run, built once by `load_context()` and never mutated. Three load-time guarantees the phases depend on: `preferred_rooms_by_doctor` is flattened and ordered, with `room_type` preference rows expanded to concrete rooms at that preference position; `ClinicTypeInfo.schedules` is deterministically sorted, because Phase 5's counter fairness depends on a deterministic processing order; and `recurring_notes_by_slot` arrives fully resolved, so Phase 2's stamp is a plain dict lookup with no concatenation or week logic of its own.
- **`RotaGrid`** — the mutable workspace: `SessionSlot`s keyed `(doctor_id, week, day, period)`, plus two synchronised occupancy indexes (`_room_occupancy`, `_doctor_room`) giving O(1) answers to both "is this room free" and "what room does this doctor hold". The displacement logic in Phases 5 and 7–9A needs *who* occupies a room, not just whether it is free, which is why the second index exists.
- **`CounterState`** — in-memory working copy of clinic and system counters and their opening balances, also tracking which clinic keys are new this run so the final write knows INSERT from UPDATE without re-querying. Balances are read-only here: they are loaded as `float` and the increments never touch them. See "Counters and snapshots" for the weighted-score rule, what an opening balance is, and why clinic counters are shared.
- **`ValidationIssue`** — one finding from a phase. Only Phase 0 ever emits `severity="error"`; everything else is a warning.
- **`DecisionLog`** — an append-only collector of `DecisionLogEntry` records, threaded as a required parameter through the decision-making phases (4, 5, 7–9A, 9B, 9C) exactly as `CounterState` is. Sibling type to `ValidationIssue`: an entry records the normal path ("this happened"), not a finding.

  Four decisions shape it. **Verbosity is one entry per decision, not one per candidate** — the candidates live inside the entry's `rationale`, which replays the selection the phase actually performed. **A stage is narrated only if it ran**, so the log distinguishes "the tiers worked" from "the counters worked" from "it fell through to alphabetical" without the reader inferring it from who was picked; entries whose decision involved no choice leave `rationale` null. **Failed searches are logged too** — an unassignable clinic, an unresolvable room, an unsupervisable session each get an entry whose rationale lists the field that came up empty, since "why did nothing happen here" is the question the log exists to answer (the matching `ValidationIssue` still says *that* it failed; Phase 5 additionally logs each closed slot it skips). And `rationale.py` owns the shared formatting and the canonical stage names, so no two phases can describe the same tie-break differently.

  Persisted verbatim to `rota_generation_log` by `_write_to_db()` on a successful run only.

### Pipeline (`generate.py` orchestrating `phases/`)

`generate(db, config_id)` loads the context, then runs the phases in fixed order. **Only Phase 0 can stop the run**: any Phase 0 error returns `status="failed"` before a grid exists or anything is written. Phases 2–12 cannot fail — every subsequent finding is a collected warning, and the result status is `success` (no warnings) or `partial` (warnings present), both with a persisted draft.

`documentation/phase_pipeline.md` is the full per-phase specification (purpose, reads/writes, selection rules, Phase 9C's three confirmed divergences from the original GAS design). What follows is the navigational summary plus the decisions that postdate that document.

- **Phase 0 — pre-flight validation.** Hard errors abort. Beyond the checks in `phase_pipeline.md`, four duty-related errors: duty on a `NO_SURGERY`/`ADMIN_TIME` template slot, duty-on-leave, duty on a closed `(date, period)`, and duty outside the doctor's employment window. The last three share a rationale — Phase 2 builds no slot in any of those cases, so the duty has nothing to attach to, and an error here beats Phase 4's `duty_no_session_slot` warning letting the rota generate with the duty silently dropped. WFH template slots are deliberately exempt from the incompatible-slot block: a WFH slot is realistically overridable, the doctor comes in for duty. Reads `context.doctor_by_id`, not `context.doctors`, so an inactive doctor carrying a stale duty row is still reachable.
- **Phase 2 — grid and counter initialisation.** Builds the grid from the active template and loads counters (the one phase needing DB access). **Cell absence is data**: no `SessionSlot` is built for a doctor with no template entry (the part-time case), for a closed `(date, period)`, or for a `(doctor, date)` outside the employment window. The same mechanism covers all three for free, so no downstream phase needs a per-slot closed or window check, and the two gates compose rather than override — a closed period inside the window and an open one outside it both yield no slot. Also stamps `SessionSlot.notes` from the pre-resolved recurring notes; this is a default value and annotation only, so a duty or clinic role can still land on a slot carrying a note.
- **Phase 4 — pre-planned duty application.** Applies `DutyAssignment` rows as roles and resolves duty rooms, evicting single-session occupants via `room_relocation.py`'s shared search. An evicted Trainee or Locum is relocated within D rooms only, never into C/W/SR — this preserves the single D-room-eligible pool that Phase 9C's supervision selection depends on.
- **Phase 5 — clinic assignment and clinic room resolution.** Room resolution for `room_required` clinics is **preference-list-only** — no room-type fallback. It may displace a lower-priority occupant, but never one on leave, on duty, or running a higher-priority clinic, and only if that occupant can be relocated to a free room from their own preference list. A schedule slot landing on a closed `(date, period)` is skipped outright *before* eligibility runs, so a closure produces no `no_eligible_doctor` warning — closed means "not expected", not "uncovered".
- **Phases 7–9A — room resolution.** Three passes: Trainee/AHP full-day displacement, single-session displacement, then a Partner/Salaried fallback. Pass 3's forced placement deliberately includes D rooms, since it runs last, after all Trainee/AHP D-room demand is settled, and only warns if every room in the practice is occupied.
- **Phase 9B — room swap elimination.** Row 5 of the original GAS priority table was dropped as unreachable under strict first-match evaluation of rows 1–4 (user-confirmed: the scenario falls through to the same default as rows 6/7). "Preference match" means the room appears anywhere in the doctor's preference list, not top-preference-only.
- **Phase 9C — trainee supervision.** Selection is from the single D/SR-room eligible pool by lowest weighted `SUPERVISION` score, with **no SR-priority fast path** — a doctor already sitting in SR competes on the same footing as one in D. This is the one place Phase 9C writes a room assignment rather than only reading what Phase 9B left behind: once selected, a supervisor not already in SR is swapped into an occupied SR room, the displaced doctor taking the vacated one. Only `is_supervising: bool` is persisted, never the trainee count — `is_on_leave` is derived at read time and a stored count would go stale. `count_supervisable_trainees`/`is_eligible_supervisor` are exposed as shared predicates so Phase 12's supervision checks cannot drift from the assignment rule.
- **Phase 12 — validation (warnings only).** Six checks, tabulated in `phase_pipeline.md`. Two corrections to that table, both postdating it: **duty coverage** expects the secondary AM/PM pair on the generation week's first *fully open* weekday rather than always Monday (`context.first_open_weekday_by_week`, requiring **both** AM and PM open — a half-open day would expect secondary duty into a slot Phase 0 and `POST /duty` both refuse to accept; degrades to plain Monday when nothing is closed, and to "no secondary expected" for a week with no fully open weekday), and expects 0 primaries on a closed slot; and **clinic coverage** skips closed-slot schedule entries, mirroring Phase 5. `role_on_incompatible_slot` is what keeps forced edits honest, since the edit endpoints have no eligibility checks of their own and re-run Phase 12 instead.

### Staging branch (`context.py`)

`load_context()` prefers a staging copy over the live master template when one exists for the `RotaConfig` being generated (`_load_staging_or_template()`): `template_sessions` is built from `RotaStagingSession` rows, and `active_template` is loaded by `RotaStaging.source_template_id` — by id, ignoring `is_active` — rather than re-resolved, so deactivating or adding templates between staging create and generation cannot brick an in-progress staging. The branch deliberately does not check `completed_at`: it also fires when `rebuild_rota_grid()` calls `load_context()` for edit endpoints on a staging-born rota after completion, where the staged sessions remain the correct source.

The invariant that lets Phases 0–12 run against a staged copy **completely unchanged, with no staging-specific code in any phase file**: staging rows are keyed by *generation* week, and a staging's `RotaConfig` always persists `template_start_week=1`, making `template_week()` the identity.

This and the `_effective_template_start_week()` read described below are the only staging-aware code inside the engine. The copy step, the editable surface and the lifecycle all live in `routers/staging.py` — see "Staging" below.

### Recurring notes (`context.py`, `phases/phase2.py`)

A recurring note ("Partners meeting") is defined against a day, a period, a set of *template* weeks, and an explicit doctor list — independent of the master template, since a note recurs by day-of-week across every run and can name several doctors at once, which no single template cell can represent. `load_context()` pre-resolves every note into `recurring_notes_by_slot` so Phase 2 does one dict lookup per slot and the phases know nothing about the feature. Overlapping notes on the same slot concatenate (newline-joined, ascending note id) rather than colliding.

Notes are annotation only: they never affect eligibility, duty, or room resolution. The stamp is a default value, not a derived one — `rebuild_rota_grid()` reads `notes` straight off the persisted row and never re-derives it, so a note cleared on the draft grid stays cleared.

Week resolution has one subtlety: a staged run always persists `template_start_week = 1`, which taken at face value would land a fortnightly note on the wrong real-world fortnight. `load_context()` therefore resolves the *effective* start week — `RotaStaging.source_template_start_week` when a staging exists for the config, otherwise `config.template_start_week` — and maps note weeks against that.

### Transaction and persistence model

The engine **never commits** — `_write_to_db()` only flushes; the caller (the rota router) owns the transaction. This is what guarantees an uncaught exception rolls back everything, counter writes included.

`_write_to_db()` runs once, at the end of a successful pipeline, and its ordering carries two decisions worth knowing. **The counter snapshot is taken before any counter is written**, so it holds exact pre-generation values, and it covers *every* existing row rather than only those this run touched — draft-period swap edits can change counters the generation never looked at, and scrap must restore those too. And **sessions and closures are written as self-contained snapshots**: `template_type` is persisted directly on each `RotaSession` row (including template-type-only slots with no role), and one `RotaClosure` row is written per closed slot in range, rather than either being re-derived from the master template or the live closure table at read time — which would silently rewrite historical rotas when the template or the closure list is edited.

System counter updates use `.scalar_one()` deliberately: the seed guarantees a row per active doctor and counter type, and a violated guarantee should raise, not silently create rows.

### Draft lifecycle (also in `generate.py`)

At most **one draft exists globally**; `get_active_draft()` is how the API layer finds it, though the 409-on-generate enforcement itself is the router's. `commit_rota()`, `scrap_rota()` and `rollback_commit()` all operate through the counter snapshot mechanism described under "Counters and snapshots" — that snapshot lifecycle, not recalculation, is what lets the edit endpoints use incremental counter updates safely.

### Grid rebuild for edits (`grid_utils.py`)

`rebuild_rota_grid()` reconstructs a `RotaGrid` from persisted `RotaSession` rows with a fresh `GenerationContext` per request (no caching); `run_phase12_for_rota()` re-validates it. Every edit endpoint and `/issues` goes through this, on drafts and committed rotas alike.

Two rules make reconstruction faithful to generation time rather than to now:

- **`template_type`: the persisted value is trusted when present**, including a manually overridden one. Re-derivation from the active template is the fallback for a null (legacy) value only, and if the template entry no longer exists either, the slot falls back to `NO_SURGERY` — role-based checks stay accurate and the slot opts out of the unresolved-room check rather than warning against a template entry that is gone.
- **Closures are overridden from the rota's own snapshot.** `load_context()` populates `closed_slots` from the *current* `PracticeClosure` table, which is right for a fresh run and wrong for reconstruction. `rebuild_rota_grid()` therefore replaces `closed_slots` with the rota's `RotaClosure` rows via `dataclasses.replace()` immediately after `load_context()` returns, re-deriving `first_open_weekday_by_week` from the overridden value the same way `load_context()` derives it.

## Data Layer and Seeds

SQLAlchemy 2.0 models under `backend/app/models/`, Alembic migrations under `backend/alembic/versions/`, seeds under `backend/seed/`. **The models and migrations are the authoritative schema record** — column lists, unique keys, check-constraint names and nullability all live there. This section records only the decisions behind the shape, not the shape itself.

### Connectivity

`app/database.py` owns the engine, `SessionLocal` factory, and declarative `Base`. `DATABASE_URL` defaults to a local SQLite file; setting the env var switches to Postgres with no code change. Session hand-out to request handlers is the API layer's job (`deps.get_db`).

**SQLite foreign keys are enforced only in the test engines.** Both test conftests attach a connect-event listener issuing `PRAGMA foreign_keys=ON`; the dev engine does not. A local SQLite dev database therefore silently accepts FK violations that Postgres and the test suite would reject.

### Enums

All enums are Python `str` enums in `models/enums.py`, stored by **value** (`"Partner"`, `"AM"`, `"no_surgery"`), not member name. `enum_col()` wraps one for column use and **caches one shared SQLAlchemy `Enum` instance per Python enum**: on Postgres each native enum type is a `CREATE TYPE`, and a fresh instance per column would attempt to create the same named type once per table, breaking `create_all` and `alembic upgrade`. One shared instance lets `Base.metadata` deduplicate. SQLite renders VARCHAR + CHECK and is unaffected.

### Table design decisions

Everything named `reception_*` is the reception rota's independent schema — no shared table, FK or row — and is covered in `documentation/architecture-reception.md`.

**Rooms and doctors.** The room `type` letters (D/C/W/SR) mirror room codes and carry no further semantics in the data layer. `doctors.sessions_per_week` is **the divisor for weighted counter scores, not a capacity limit** enforced anywhere. `active` is deactivation, not deletion (see "Deleting a doctor"); preferred rooms are an ordered list where each row is exactly one of a concrete room or a generic room-type token.

**Deleting a doctor is permanent, and deactivating them is a different verb.** `DELETE /doctors/{id}` purges: the doctor row and every row in the seventeen tables that reference it — master template slots, sessions on every generated rota including committed ones, staging sessions, leave, leave entitlements, duty, extra sessions, blocked slots, counters and their per-rota snapshots, clinic-type eligibilities, room preferences, recurring-note pickers and their signature. It used to be a soft delete (`active=False`) that 409'd for anyone with committed sessions, which meant "deleting" a leaver removed nothing: they kept every row and went on appearing on the master rota grid flagged `(inactive)`, which is the bug this replaced. Purging is accepted rather than overlooked — `rota_sessions.doctor_id` is non-nullable, so the alternative is an orphan session with no doctor attached, and refusing to delete anyone with committed rows makes anyone who has actually worked undeletable, which is precisely the leaver case the feature exists for. A rota printed and handed out months ago will no longer match what the app shows, and the next generation's fairness balancing loses that person's counters. Informed consent in the UI (`GET /{id}/usage` returns the counts the confirm dialog shows, and it is typed-code gated) and the audit log — which records who deleted which doctor id after the rows are gone — are the mitigations.

Two guards narrow it, both copied deliberately from `DELETE /reception/staff/{id}`, so the clinical and reception staff deletes now behave identically: the endpoint needs `clinical: write` **and** `user_admin` (deactivating needs only `clinical: write` — an irreversible action should be the narrower permission), and it 409s unless the doctor is already inactive, making deletion a deliberate two-step that also removes the "deleted someone who is on this week's rota" case. Requiring deactivation first never makes anyone permanently undeletable, since deactivate is always available. Two consequences of the two-step: `DoctorsPage` now lists inactive doctors in their own section (it was active-only, which made deactivation a one-way trip and put the delete out of reach for exactly the leavers it exists for), and the frontend delete invalidates the *entire* query cache rather than a list of roots, because naming those roots would be a second copy of the purge list that goes stale the first time one is missed.

The child rows are deleted explicitly, from a `PURGED_MODELS` tuple in `routers/doctors.py`, rather than by `ondelete="CASCADE"` on the FKs: no migration, and the destruction is visible where it is decided. The cost is that a new doctor-referencing table would silently go unpurged, so a test asserts `PURGED_MODELS` plus `NULLED_TABLES` covers every FK to `doctors` in the metadata. `users.doctor_id` is the one referencing column nulled rather than purged — a user row is a login, not history of the doctor. `generated_rotas` headers are left standing even where the purge empties one, and `rota_generation_log` is untouched: its doctor ids are deliberately FK-free, its rows carry self-contained prose, and it is purged with its rota.

**The doctor employment window** (`start_date`/`end_date`, both nullable, null meaning unbounded) lets a joiner or leaver be entered ahead of time. The predicate lives in one place, `app/doctor_window.py`'s `is_within_window` — top-level under `app/` rather than under `app/api/`, since the engine imports it too and `engine/` importing from `api/` would invert the layering. It is deliberately **independent of `active`**: `active` is the soft-delete flag, the window is a real employment fact, and callers combine the two gates as they need. `start_date <= end_date` is validated in `routers/doctors.py` rather than by a check constraint or schema validator, because PATCH may supply one end of the pair and the check needs the merged post-update values.

Enforcement is at four points and no others: `POST /leave`, `POST /extra-sessions` and `POST /duty` 422; the `POST /staging` copy loop skips the row; and Phase 2 builds no slot. **Phase 2 is the authority**; the rest exist so the admin is told at entry time instead of watching cells vanish at generation. Bulk paths (`POST /leave/bulk`, `POST /leave-planning/bulk`) report an `"outside_doctor_dates"` skip instead of failing. The split between 422 and skip is by *request shape*, not by endpoint family: a single-entry POST has nothing to partially succeed at, while one stale cell must not fail the other 199.

**Clinic configuration.** `ClinicType.category` is free text; the `"duty_helper"` value the frontend colours specially is a data convention, not a constraint. **`clinic_priority` is server-managed, not client-settable** (`ClinicTypeIn` has no such field): a partial unique index enforces a contiguous 1..N sequence over enabled rows only, maintained by three router mechanisms — max+1 append, gap closing, and `PUT /clinic-types/reorder`. Two non-obvious implementation constraints: gap closing decrements per row in ascending order with a flush between rows rather than issuing a bulk `UPDATE`, because Postgres checks the non-deferrable unique index per row in visitation order; and reorder parks every affected row at a negative placeholder and flushes before any row gets its real value, so no intermediate state can collide. The disabled→enabled transition must assign the new priority *before* the `is_enabled` flip is flushed, or the flush briefly persists an enabled row still holding its old, possibly-colliding priority.

**Generation inputs.** `leave_entries` are half-day granularity; weekday-only is an API rule, not a schema one, so stray weekend rows are representable. `duty_assignments` is a **generation input only — manual duty edits on a generated rota never write back to it**. Its DB-backed rules (secondary duty on the week's first fully open weekday; no duty of either type on its own closed period) are enforced in `routers/duty.py` rather than a `model_validator`, which cannot see the DB. The closed-slot rejection is period-specific, so a primary duty on the open half of a partly closed day is still accepted.

**Duty opening balances** (`duty_opening_balances`) are the duty-side half of the opening-balance feature described under "Counters and snapshots", and the one place its shape differs. Duty has no counter table — the count is a `func.count()` over `duty_assignments` for the requested range — so the balance needs somewhere to live, and it is keyed **`(doctor_id, year)`**, the same grain as `leave_entitlements` and for the same reason: the duty count is derived per calendar year, so a balance outliving its year would keep crediting someone who is no longer a new starter, and by the next 1 January the count restarts and everyone is genuinely level again. The table is **sparse** — no row means zero, and setting a balance to zero deletes the row (taking its `notes` with it), so it holds only real deviations. `GET /duty/counts` resolves the balance from **the year of `from_date`**, returning zero when `from_date` is absent: the duty grid is the only caller and always requests a whole calendar year, so a range straddling a year boundary gets the balance of the year it starts in rather than a sum across years — a case that does not arise, and documenting the rule was judged cheaper than summing. Duty is **advisory**: nothing in the engine reads these counts, and the balance's only effect is on the grid's bolded "lowest annual weighted score" hint to whoever is planning the week by hand. It was kept in scope anyway because duty is the surface the whole problem was noticed on.

**Practice closures** (bank-holiday weeks, and half-day closures such as a city-wide Thursday-afternoon training session) are global planning data entered via `/closures`, independently of any generation run — the Duty page needs to know about a closure weeks before a `RotaConfig` exists. **A full-day closure is two rows sharing a date**, not a distinct value on `period`: there is deliberately no "full day" sentinel in the data model, mirroring `leave_entries`' half-day granularity. The closures UI offers a "Full day" option that fans out into two `POST`s, but the wire schema only ever knows AM or PM.

**`rota_closures` is the canonical statement of the per-rota snapshot principle.** It records which `(date, period)` slots fell inside a rota's range *at generation time*. `generate.py` writes these rows in the same transaction as the rota; `rebuild_rota_grid()`, `GET /rota/{id}` and the grid all read from this table, never from `practice_closures`, so **a closure added or removed afterwards cannot change how an existing rota renders or validates**. `rota_sessions.template_type` exists for the same reason, applied to the template rather than the closure list.

**Bank holidays.** `practice_closures.bank_holiday_key` tags a closure's AM+PM pair as the annual instance of one of eight fixed, system-wide named holidays in `app/models/bank_holidays.py`. Tagging rather than matching on the free-text `name` is the point — an admin can edit a name independently. The list and its keys are hardcoded, not admin-configurable. The Annual Planner shows an amber banner while **any** named holiday for the viewed year is still undated: a part-filled year leaves that page's clinical cover totals wrong on exactly the days still missing, so "some are set" is not a reason to stop warning.

**School holidays** (`schools` / `school_holidays`) are global planning data like closures but with **zero engine coupling**: `load_context()` never reads either table, nothing snapshots them per-rota, and no generation, coverage or duty check consults them. They exist purely so the admin approving leave can see a request lands in half term. Three shape decisions follow from that: **range-based, not per-slot** (one `(start_date, end_date)` row per holiday — nothing looks a school holiday up by `(date, period)` membership, so a six-week summer holiday is one row, not forty-two); **no AM/PM granularity at all**; and **weekends allowed**, unlike closures, since a holiday routinely starts, ends or spans a weekend. `School` has **no soft-delete flag** — nothing holds an FK into it and there is no per-rota snapshot — so deleting one is a hard delete cascading to its holidays, gated behind a confirm naming the holiday count.

**Master template.** **`is_active` is not schema-enforced unique** — single-active-template is app logic, and readers must (and do) resolve multiple active rows deterministically rather than assume one. **Row existence is itself the data**: a doctor with no row for a slot does not work that slot, so editing a working pattern means creating and deleting rows, not just updating them. This is the same rule Phase 2 relies on, and it propagates to `rota_sessions` and to the frontend pivot.

**Staging.** `rota_stagings.config_id` is unique (one staging per `RotaConfig`), and `source_template_id` points at the template it was copied from, resolved by id rather than `is_active` so a later template change cannot orphan an in-progress staging. `source_template_start_week` records the template week the copy actually started from, since `RotaConfig.template_start_week` is always persisted as 1 on a staged config and so cannot be read back for that purpose — see "Recurring notes" above. `completed_at` is the lifecycle marker (null = active), mirroring `committed_at`/`archived_at`'s convention, so "an active staging exists" is a direct query independent of whatever later happens to the `GeneratedRota` it produced. Session rows mirror the master template's shape exactly; no real date is stored, week/day/period plus the parent config's `start_date` derive it.

**Recurring notes** are a standalone entity rather than a template field, for the reasons under "Recurring notes" above. There is deliberately **no "no rows means every week" shorthand** in `recurring_note_weeks` — "every week" is stored as all four rows.

**Generated rotas.** At most one draft globally, **enforced at the API layer, not the schema**. The standing invariant on `rota_sessions`: a row exists iff a template entry existed for that slot at generation time — edits mutate rows but never create or delete them, which the frontend pivot relies on. `template_type`'s precise meaning is "generation-time snapshot, possibly manually overridden", since the cell edit menu may overwrite it; generation always sets it, so null is a legacy reading only and reads as a normal session. `is_supervising` has no derived-value fallback, unlike `template_type`. `is_on_leave` is not stored at all — derived from `leave_entries` at read time. "Committed rotas are immutable" is an API-layer 409, not a data-layer property.

**Generation decision log.** `rota_generation_log` deliberately uses **plain nullable integers with no FK constraints** on its doctor/room/clinic-type ids: every row already carries a self-contained `message` and `rationale`, so an orphaned id in a historical entry (a since-deleted clinic type, say) is harmless, and real FKs would silently expand the delete-blocker surface on every referenced table. Rows are written once, in the rota's transaction, and never mutated — commit and rollback don't touch this table, unlike the counter snapshots. `rationale` is prose, never parsed, and is not backfilled; the log is never re-derived, so rows written before the column existed simply have none.

**`leave_entitlements` is sparse by design** — no row means the rules apply. See "Leave entitlement" below.

### Counters and snapshots

`clinic_counters` and `system_counters` store a **raw count plus an opening balance**. The fairness metric, weighted score = `(raw_count + opening_balance) / sessions_per_week`, is computed in the engine (`CounterState`) and mirrored in the frontend (`weightedScore.ts`); it is never stored and no SQL computes it. A doctor with `sessions_per_week = 0` scores infinity and is therefore never preferred — a case kept deliberately distinct from having no data. Clinic counters are **shared**: one row per `(doctor, clinic type)` regardless of how many schedule slots the type has, with no day/period dimension. An earlier per-slot design was reversed before it shipped. Counter rows are still created lazily (get-or-create in the engine, the swap endpoints, and the opening-balance upsert); only system counters are seeded. `GET /counters/clinic` therefore returns the **full (counted doctor × clinic type) cross-product**, with `id: null` and zeros for a pair that has no row — a doctor who has never been allocated a clinic type would otherwise be unaddressable on the page, and that doctor is exactly who an opening balance exists for. Disabled clinic types are omitted unless they still carry a row.

**Opening balances** exist because a doctor who joins part-way through starts every counter at zero, which the score reads as "maximally under-loaded": the engine prefers them for clinics, moves them out of rooms first and gives them supervision first until they have absorbed a full period's work. The balance is a credit **denominated in the thing the counter counts**, not in the sessions the joiner would have worked — the levelling figure is `peer_weighted_score × their_sessions_per_week` ("start them at the group's current score"), so a 4-session joiner arriving when the group averages an unscaled 0.8 (the page shows it x10, as 8.0) is credited ~3.2 clinic sessions, not the ~48 working sessions they missed. Several properties are load-bearing. It is **additive and stored in its own column**, and **the engine never writes it** — `CounterState` reads it into `clinic_balance`/`system_balance` and `increment_*` touches only the raw count. It is therefore **not snapshotted**: `RotaClinicCounterSnapshot`/`RotaSystemCounterSnapshot` carry `value_before` for `raw_count` alone, so a balance cannot be corrupted by scrap or rollback, and **a scrap never undoes a balance edit** (folding the credit into `raw_count` instead would make it indistinguishable from work actually done, and a reset would silently destroy it). **Reset-to-zero clears the balance as well as the count**, on all four reset endpoints — after a reset everyone is level by definition, so a surviving credit would re-introduce the skew it was created to remove; combined with the previous point this means a reset during a draft is *half* undone by a scrap, which is why `CountersPage`'s draft warning distinguishes the two. Values are `Numeric(5,1)` **in sessions** (a credit derived from a peer average is fractional, and rounding it to an integer distorts a small number badly), **may be negative** (a returner, or a leaver whose count should read as already served), and are **converted to `float` at load** in `_load_counter_state` — `Decimal / float` raises `TypeError`, and the precision buys nothing in an in-memory sort key. The clinic and system balances persist until a reset clears them, matching the lifetime of the lifetime-cumulative counts they adjust; the **duty** balance is year-scoped instead — see below.

**The snapshot lifecycle is the canonical mechanism behind commit, scrap and rollback, and every other section refers back to here.** On generation, every existing counter row's value is snapshotted against the new rota before any counter is written, so the snapshot holds exact pre-generation values. While the rota is a draft, all mutations — generation increments and manual-edit adjustments alike — hit the live counter tables. Then:

- **Commit** deletes the snapshots. Live values become the baseline for future generations.
- **Scrap** restores every snapshotted value, deletes counter rows created after the snapshot, recreates any snapshotted row deleted during the draft period, and deletes the rota, its sessions and the snapshots — all in one transaction. One exception: a row absent from the snapshot but carrying an **opening balance** is kept with its raw count zeroed rather than deleted, since deleting it would destroy an admin's balance edit made during the draft — the balance is never snapshotted, so there is nothing to restore it from.
- **Rollback** restores the counters the same way scrap does, but keeps the rota and flips it back to draft.

Two consequences follow, and they are why the edit endpoints can use incremental counter updates rather than full recalculation: scrap also undoes counter drift from manual edits, so **scrap-then-regenerate is exactly equivalent to generating once from the original baseline**; and any drift is bounded by the draft's lifetime. Snapshot rows are write-once, and since at most one draft exists, at most one rota's snapshots exist at a time.

### Migrations

`alembic/env.py` targets `Base.metadata` and reuses the application's `DATABASE_URL`/engine, so `alembic upgrade head` behaves identically on SQLite (dev, `render_as_batch=True`) and Postgres (prod). CI validates an upgrade/downgrade/upgrade round trip against Postgres 16 on every push.

**`001_initial_schema.py` is a frozen pre-go-live baseline consolidated from a 28-revision chain, and migrations are additive from here** — every schema change is a new revision, never an edit to `001`. Its docstring is the authority on what it contains and why it was consolidated, including the Postgres enum-sharing rule and the models-are-source-of-truth rule; read that rather than a paraphrase. Git history is the archive for the old chain.

Three rules apply across all migrations and are stated in no single file:

- **Dropping or altering a constraint needs `op.batch_alter_table`**, since dev SQLite cannot do either in place.
- **A `server_default` means a real backfill decision, not a type-safety formality.** A nullable column whose null has a permanent meaning gets neither default nor backfill (`committed_at`, `archived_at`, `template_type` are all this shape). A non-nullable column added to a populated table is the opposite case, and its default states what the existing rows mean. **Declare such a default on the model as well as the migration** — six of them once lived only inside migrations and drifted out of the models unnoticed until the consolidation found them.
- **Deleting data can be preferable to reinterpreting it.** Where no correct automatic mapping from an old shape to a new one exists, a migration may clear the affected tables and have the data re-entered rather than guess. The pre-live chain did this twice. This is licensed by the system not being live (see `CLAUDE.md`) and is **not** a pattern to follow once it is.

Revision numbers are deliberately not cited for individual columns anywhere in this document — `git log -S` on the column name finds when something appeared, and always more reliably than a number in prose.

### Seeds

`seed/run_all.py` runs five seeders in dependency order inside one transaction: rooms, doctors, system counters, master template, reception coverage rules. `seed_doctors.py` and `seed_master_rota.py` both read CSVs from `seed/data/` whose rigid formats are documented in their own module docstrings; any unrecognised cell or structural deviation raises rather than being skipped. `seed_reception_coverage.py` is independent of the clinical seeders and is positioned last only for readability.

Deliberately not seeded: **clinic types** and their children (entered via the frontend) and **clinic counters** (created lazily). `seed/seed_users.py` is separate from `run_all.py` — see "Seeding" in `documentation/architecture.md`.

**The seeders are not idempotent and have no designed rerun guard.** In practice a rerun fails immediately on room-code uniqueness and rolls back — adequate protection, but incidental, and it depends on `seed_rooms` running first. `master_rota_templates.name` has no unique constraint, so a template-only rerun would happily create a second active template.

`seed_master_rota.py` writes every row directly with no room-conflict check, which is the one path that can produce a double-booked room in the template — see `MasterRotaConflictsPanel` under "Frontend: Master Rota".

### The authorization gate

Authentication is covered in `documentation/architecture.md`; the shape of the *authorization* gate is a clinical-side design decision worth stating here because it governs every endpoint below.

Unlike the auth seam, which is a per-endpoint `Depends()`, the permission gate is **not** per-endpoint. `require_access(area)` is a dependency *factory*: `main.py`'s `include_router` loop calls it once per router with that router's area (every clinical router here is `"clinical"`), and the returned closure reads `request.method` to tell a `read` from a `write`. That is the whole point: with ~80 non-GET endpoints across 23 routers, per-endpoint gating would be default-*open* — the next POST anyone adds would be unguarded until somebody remembered the dependency. Attached at inclusion time, a new endpoint is default-*deny*, and a new router cannot even be registered until it is classified in `main.py`'s `_AREA`. Router-level `dependencies=` on the `APIRouter` objects would not do, since every router mixes reads and writes, so the discrimination has to happen inside the dependency. `tests/test_api/test_authorization.py` proves it by sweeping every route in the OpenAPI schema against one permission set per preset. The full model — the five permissions, the two-entry shared-read allowlist, and the two endpoints needing `user_admin` on top of `clinical: write` — is in `documentation/architecture.md`.

`_UNGATED` is `(auth, users, calendar)` and should stay that size. `/auth` cannot take the gate (login has no authenticated user; logout must work for every login). `/users` gates itself per-endpoint with `require_capability("user_admin")`, because `PATCH /users/me` is a write every login must be able to make on their own row — which means that one file is default-open and a new endpoint there needs its dependency added by hand. `/calendar` holds the one unauthenticated endpoint, the `.ics` feed whose path token is the credential.

One judgement call: `POST /signatures/{doctor_id}/apply` mutates nothing but is gated as a write anyway — producing an officially signed document is not obviously a read-only action. It is moot in practice now that `signatures` is a boolean permission covering reads and writes alike, so a login either has the whole tool or none of it.

### Rota lifecycle

A `GeneratedRota` is `draft` or `committed`, **one draft exists globally** (generate returns 409 while any draft exists), and all mutation endpoints are draft-only. The counter snapshot mechanism under "Counters and snapshots" is what makes commit, scrap and rollback safe.

A Phase 0 generation failure returns 422 with the issues; nothing is committed, so the `RotaConfig` row is discarded along with everything else. `GET /rota` lists all rotas newest first (`created_at DESC, id DESC` — the id tiebreak matters for same-second creation), metadata only, unpaginated (volume is tens per year); the frontend derives the active draft and committed history from it. `GET /rota/{id}/issues` re-runs Phase 12 and works on drafts and committed rotas alike. `GET /rota/{id}` carries `closed_slots` from the `RotaClosure` snapshot, not the live table.

**Rollback commit.** `POST /rota/{id}/rollback-commit` undoes a commit one step back through commit history. Eligibility is enforced by five checks inside `engine.generate.rollback_commit()` rather than pre-checked in the router — existence, status, a null `committed_at` (meaning the rota predates rollback support and can never be rolled back), no active draft blocking it, and chain order. The rota must be the **most recent commit** (greatest `(committed_at, rota_id)` among committed rotas with a non-null `committed_at`), or the call 409s naming the blocker. `commit_rota()` self-heals the chain by refreshing `committed_at` to now on every commit, including a re-commit after rollback, rather than preserving an original commit time. The frontend mirrors this ordering rule client-side so the button doesn't render on a request that would 409 — advisory only, since a draft created in another tab between load and click still hits the real 409.

**Archive / unarchive.** `archived_at` is a pure visibility flag: no engine involvement, no effect on counters, sessions, or rollback eligibility. `GET /rota` returns archived rotas **unfiltered** — there is deliberately no query parameter and no server-side filtering, and the Committed/Archived split is purely client-side. That matters for one reason beyond simplicity: the most-recent-commit scan must keep seeing archived rotas, since an archived rota can still be the most recent commit and therefore still rollback-eligible. `rollback_commit()` clears `archived_at` when it flips a rota back to draft — necessary, not cosmetic, since a surviving flag would silently re-archive a freshly re-committed rota with no UI action explaining it. Legacy rotas with a null `committed_at` are archivable, archiving being the only lifecycle action left for a rota that can never be rolled back, so the guard checks status rather than `committed_at`.

**`GET /rota/{id}/log`** returns the persisted `rota_generation_log` rows in `sequence` order. Unlike `/issues`, which persists nothing and re-runs Phase 12 via a grid rebuild on every request, `/log` reads rows written once and never re-derived — no grid rebuild, and no server-side filtering, since a full 4-week run produces at most a few hundred rows and the frontend filters client-side. Empty for a rota that predates the feature or was created outside `generate()`.

### Editing endpoints and re-validation

Every editing endpoint follows the same contract: mutate, re-run Phase 12 via a fresh grid rebuild, and return the fresh issues in the response. **Eligibility is deliberately not checked server-side** — a force-assignment to an ineligible doctor succeeds and comes back with warnings. Apply-then-warn with undo is the frontend's job. Duty role edits never write back to `DutyAssignment`; Phase 12 reads roles from the rebuilt grid, so re-validation stays correct regardless.

The four operations are split the way they are for one reason: **the session PATCH's contract is "safe partial update, no side effects on other rows"**, which is incompatible with displacement, so anything that can displace lives on its own endpoint.

- **`PATCH .../sessions/{session_id}`** — partial update of `is_wfh`, `notes`, `is_supervising`, with field presence detected via `model_fields_set` (`notes: null` clears; an absent field is untouched; an empty body 422s). Setting `is_wfh` true also **clears `room_id`** — room freeness is derived from session rows, so WFH must actually free the room. Toggling it off does *not* restore a room; the slot warns `unresolved_room` until one is assigned. `is_supervising` is applied verbatim with no side effects in either direction, and never adjusts the `SUPERVISION` counter, which is written only at generation time.
- **`POST .../swap-roles`, `.../swap-rooms`** — exchange `(role, clinic_type_id)` or `room_id` between two sessions. **One side may be empty, making the swap a move** — a documented contract with tests, not an accident; both sides empty 422s. `swap-roles` adjusts clinic counters (get-or-create, floored at 0 on decrement, same-type swap a no-op); `swap-rooms` never touches counters. Because the exchange is symmetric *including counters*, repeating the identical call is a true inverse — which is exactly what the frontend's undo relies on. A room move deliberately leaves the source warning `unresolved_room` if its slot requires one: that is the signal to reassign.
- **`POST .../sessions/{session_id}/set-room`** — one-sided assign/clear with displacement. A displaced holder's room is **cleared to blank, not reverse-swapped** — the blank plus the returned warning is the honest signal. Clearing takes no displacement lookup and makes no `is_wfh` change; a set room clears the target's `is_wfh` (the PATCH rule in reverse). Unknown rooms 404 via explicit lookup, since FK errors would surface as 500s on Postgres at flush.
- **`POST .../sessions/{session_id}/set-role`** — a **verbatim `(role, clinic_type_id, template_type)` triple setter**: it always writes the given triple exactly, which is what makes every frontend undo expressible as another call to it. Displacement applies only to steal-class assignments (duty roles, or a clinic role with a specific type), and the displaced side is cleared one-sidedly. If the written triple ends as `role=None` with a no-surgery or admin-time `template_type`, the target's room is also cleared — a no-surgery session silently holding a room would block it with no warning.

### Master rota write surface

The template has no draft/committed lifecycle, so its editing endpoints are **not draft-gated and never run Phase 12** — the per-endpoint displacement rule is the only conflict-avoidance mechanism. Edits affect future generations only, since `RotaSession` snapshots `template_type` at generation time.

`GET /master-rota/active` orders by `id` and takes the first match rather than `.scalar_one()`, because `is_active` is not schema-enforced unique: a second active row resolves deterministically instead of 500ing the page.

The write endpoints are a **verbatim `(session_type, room_id)` pair setter** — both fields always required, not a partial update, so undo replay is just another PATCH — plus create and delete, because cell existence is itself the data. All three share one displacement rule: a set room displaces the same-slot-same-week holder, whose room clears, and a displaced `PRE_ASSIGNED` becomes `REQUIRES_ROOM` (a roomless `PRE_ASSIGNED` means nothing to Phase 2) while a displaced `ADMIN_TIME` keeps its type. POST pre-checks the slot for a descriptive 409 rather than letting the unique constraint raise.

**The server is a permissive verbatim writer** — no doctor-active check server-side. The frontend gates the add-session affordance to active doctors, and the permissiveness is what keeps undo-recreate working if a doctor is deactivated mid-session.

### Staging

The editable step between the master template and generation: during school holidays, staff often need one-off pattern changes — covering an extra session, dropping one — that shouldn't become a permanent template edit. A staging is a run-scoped copy of the active template's rows for a chosen date range; edits happen against the copy, and the existing Phase 0–12 pipeline then runs against the edited copy unchanged. The master template itself is never touched.

**Lifecycle.** `POST /staging` copies the active template's rows for the range into a new staging plus its `RotaConfig`, exactly as a direct generate call would create one. `template_start_week` is applied once, at copy time, to select which template weeks get copied, then discarded — the persisted config always has `template_start_week=1`, which is what makes staging rows keyable by *generation* week and lets the engine run unchanged (see "Staging branch"). Creation requires no active draft, no active staging, no committed-rota overlap, and **exactly one active template** — the engine's strict rule, not the master-rota GET's lowest-id resolution. At most one staging exists globally, mirroring the at-most-one-draft rule; `/rota/generate` additionally 409s while a staging is active, though it remains reachable directly (used by tests; the frontend only calls `/staging`).

`POST /staging/{id}/complete` runs the pipeline against the staged config and on success sets `completed_at`, **retaining the staging rows as a record of the run** rather than deleting them — a snapshot of the final edited state, not a diff against the template, since the template may itself have moved since. It re-checks the draft and overlap locks: a rollback can produce a draft mid-staging even though direct generation is blocked, and the create-time overlap check was fail-fast, so this is the authoritative re-check. **A Phase 0 failure here leaves the staging rows and its `RotaConfig` alive** — a deliberate divergence from direct generation, which discards the config it created in the same failed request. The user fixes the offending staged edit and completes again.

**Editing.** The session endpoints mirror the master rota's contract verbatim, reusing its validator by subclassing so the two grids' validation cannot drift apart. One addition: create 422s when `week` exceeds this staging's own `num_weeks`, since the shared schema's 1–4 bound is necessary but not sufficient for a 1- or 2-week staging. All three 409 on a completed staging.

**What real dates add.** Unlike the dateless master template, a staging row has a calendar date, which surfaces two things the template editor cannot: `is_on_leave` per session, derived at read time; and `closed_slots`, read **live** from `PracticeClosure` for the range — no snapshot exists yet, and generation at complete time reads live closures regardless, so live is correct here.

**Closures and the employment window are treated oppositely, deliberately.** Rows on a closed slot are still copied and editable — Phase 2's closed-slot skip remains the single closure authority, and the grid's closed treatment is display-only, so a copied-but-greyed row still tells the admin something true. An out-of-window row has no such display: it would look like an ordinary editable cell that then silently vanished at Complete, since Phase 2 drops it either way. So the copy loop **skips** out-of-window rows entirely, and skips the extra-session new-row branch for the same. The skip is recorded in `covered_slots` before it fires, so a planned extra session on the same slot cannot fall through to the no-template-row branch and reinstate what the window just removed.

### Leave planning

Forward planning of annual leave and planned extra sessions together, a month at a time, with a live clinical-headcount total so the admin can see what an absence does to cover *before* saving it.

**`GET /leave-planning/coverage`** returns one entry per weekday `(date, period)` in the range, capped at 62 days — the grid asks for a month, and the cap is what stops this being an unbounded scan. Weekends are omitted entirely rather than returned as zero, since the grid has no weekend columns. Four decisions shape the count, none of them obvious from the code:

- **Template *week 1* only.** Mapping a calendar date onto the 4-week cycle needs a `start_week`, and the only source of one is `RotaConfig.template_start_week` — a per-run value with no calendar anchor, which the staging path pins to 1 regardless. So the endpoint treats week 1 as the working pattern for every date. Sound because Partner, Salaried and Locum doctors work the same sessions every week; rooms may vary, which is irrelevant to leave planning. Flattening the template from four weeks to one is a separate ticket, not a prerequisite.
- **Partner, Salaried and Locum only**, applied server-side here *and* client-side in the totals recompute. The bulk write endpoint is deliberately **not** type-filtered — it is a generic write path with no reason to refuse a Trainee.

  A **"Show trainees"** toggle on the page adds Trainee rows to the grid (off by default), so an admin can see and plan trainee absence alongside everyone else. Those rows are editable and save exactly like any other, but they are *not* passed to the client-side totals recompute: the coverage baseline they would be adjusting never counted the trainee in the first place, so a delta against it would take the total below the number the server will report on the next fetch. The page says so in a line under the toolbar rather than leaving an unmoving total to be read as a bug. Row set and counted set are therefore now two lists in `LeavePlanningPage` (`doctors` and `coverageDoctors`), not one.
- **Clinical sessions only:** a doctor counts when their *effective* type is `REQUIRES_ROOM` or `PRE_ASSIGNED`. `NO_SURGERY`, `ADMIN_TIME`, `WFH` and "no template row" all count zero — exactly the set the extra-session override converts *into* `REQUIRES_ROOM`, so the two halves of the grid agree by construction.
- **The extra-session override is applied, not a flat `+1`.** Leave and extra sessions are not symmetric: leave is read live by the engine every run, while an extra session is applied once, conditionally, in the staging copy loop, and is a no-op on a slot the doctor already worked. The endpoint imports `routers/staging.py`'s `_OVERRIDABLE_TYPES` rather than redeclaring it so the two cannot drift. Leave wins over an extra session on the same slot, matching the copy loop.

Closures suppress coverage: a closed slot returns `is_closed=True` with `headcount=0`, since Phase 2 creates no slot there. Everything the endpoint reads is read **live** — this is forward planning, not the rendering of an existing rota, so there is no snapshot to prefer. No active template at all yields zeros rather than a 404, so the grid still draws its leave cells.

**`POST /leave-planning/bulk`** applies a batch of `leave` / `extra_session` / `blocked` / `clear` actions in one transaction, in a fixed order — **clears, then leave, then blocked, then extra sessions** — so a batch touching more than one side of a slot resolves deterministically along a **leave > blocked > extra_session** precedence. The clears are flushed before any insert: SQLAlchemy emits a mapper's INSERTs before its DELETEs within one flush, so clear-then-set-leave on the same cell would otherwise collide on the leave uniqueness constraint.

**Nothing here 409s on a state that already matches** — the grid sends the state it *wants*, so setting leave where leave already exists with the same note is a `"duplicate"` skip; a differing note updates the existing row in place and counts as applied. An out-of-window action is likewise a skip. Weekends and unknown doctor ids are the only two things that fail the whole batch (422 and 404): both can only be a client bug, unlike the window, which legitimately moves under a stale grid. A pre-existing extra session the batch's leave covers is *reported* in `superseded_extra_sessions` — never deleted, never blocked.

**Blocked** is a third cell state alongside leave and extra session, for things like a whole-day training session: the doctor is unavailable for clinical cover but this is deliberately **not** leave — it must not touch `leave_entries` or anything that reads them (the engine, leave balances, `/leave`), so it lives in its own table written only from this router. For coverage and for draft-room release it is treated exactly like leave, since a blocked doctor is equally not going to be there.

`_release_draft_rooms` is imported from `routers/leave.py` and called for every leave candidate, **duplicates included** — the same deliberate over-call the ad-hoc bulk path makes, so an all-duplicates save still heals stale room state. The asymmetry is preserved too: `clear` does not restore rooms, matching both bulk-delete and the WFH behaviour.

**`GET /leave/chargeable-count`** answers a different question from coverage: not "is there cover", but "was this doctor due at work" for each booked leave entry in range. The rule (`app/leave_charging.py`) shares only the week-1 template map (`app/master_template.py`) with coverage — `ADMIN_TIME` and `WFH` count as chargeable here (the doctor was due in, whatever they were doing) but as zero cover there, so the two predicates are deliberately **not** merged. Exemption checks run weekend → no-template-row → no-surgery → closure, **closure last**, so `closed` in the response means "the doctor would otherwise have worked this slot but the practice was shut" rather than merely "this slot fell on a closure". The count is computed at read time and never stored, so it moves if the template or closures change retroactively — accepted for now, since nothing yet snapshots an entitlement against it.

### Leave entitlement

What a doctor is *owed* for a leave year, against what `app/leave_charging.py` says they have *used*. The rules live in `app/leave_entitlement.py` (pure, no DB), the surface in `routers/leave_entitlement.py`, the optional stored deviations in `leave_entitlements`.

**The rules.** A partner gets 7 weeks a year, a salaried or trainee doctor 6; **AHPs and locums get none** — AHP leave is assigned by a third party and locums are engaged per session, so they are *absent from* the entitlement map rather than mapped to zero, and the rule function returns `None` rather than `0`. That distinction is load-bearing: "not entitled to leave" and "entitled to nothing this year" (a doctor who left last December) are different facts and the UI shows them differently. Everything is counted in **sessions** — the unit leave is booked in — so a week is worth the doctor's own `sessions_per_week`. The leave year is **1 January to 31 December**, which makes a bare `year` a complete key on the stored row. A doctor employed for part of the year is **pro-rated by days employed**, inclusive at both ends: days rather than weeks or months, because a day count needs no decision about a doctor who starts mid-week. Bank holidays need no modelling here at all — a closure on a slot the doctor would have worked is already exempt under the charging rule, so it never charges.

**Stored rows record deviations only, never the norm.** No row means exactly the rule figure. A row carries a nullable `entitlement_sessions` that **overrides** the rule outright, plus `carry_over_sessions` and `adjustment_sessions` that are **added** to whichever base applies. The nullability is the point: a row written purely to carry four sessions over must not also freeze the entitlement at whatever the rule happened to say that day, so it keeps tracking `sessions_per_week`. Carry-over and adjustment are separate columns rather than one signed total because they answer different questions ("brought forward" vs. "granted or docked"), and both may be negative. `PUT` is a full replace, not a patch — the four fields are read together on one screen, and a partial update that silently kept a stale override would be the surprising behaviour.

**The `sessions_per_week` / template mismatch is reported, not resolved.** Entitlement is credited from `Doctor.sessions_per_week`; leave is *charged* against the master template, where a slot counts as working unless it is `NO_SURGERY` — `ADMIN_TIME` and `WFH` are working sessions, the same definition `leave_charging` uses, and `template_sessions_per_week` must never be narrowed to the coverage endpoint's counted set. When the two disagree, a balance accrues and burns in different units. Making the template authoritative was rejected — a doctor whose template has not been populated would read zero entitlement — so `sessions_per_week` stays authoritative and `template_sessions_per_week`/`sessions_mismatch` ride along on every response for the UI to warn about. An empty template is never a "mismatch": it surfaces through the `no_template_row` exemption bucket instead.

**Read-time, and inheriting the cost.** Usage is recomputed from the live template and closure tables on every request, so editing a doctor's template moves a historical "used" figure. Whether to snapshot it remains open; the answer for now is *not yet, but the entitlement side is pinnable* — an admin who disagrees with a computed balance can freeze the entitlement half with an override rather than needing the whole thing snapshotted. Freezing usage at year close remains open.

**Which doctors appear.** The list endpoint omits doctor types with no entitlement entirely (a row of nulls for an AHP is noise on a screen whose job is spotting who is over or under), and omits inactive doctors *unless* they booked leave in the year asked for — a doctor who left is still owed an accurate figure for the year they left in, and hiding them would make that year stop adding up. The single-doctor `GET` does neither: asked about a specific AHP, the honest answer is null entitlement fields, not a 404 that reads as "no such doctor".

### Signatures and documents

`backend/app/documents/` holds the pure, framework-free document modules, called only from `routers/signatures.py` and `routers/eoi.py`. **No processed document is ever written to disk or the database**: `/apply` reads the upload, transforms it in memory, and returns the bytes. The only persisted artifact is the signature image itself. The EOI autofill below shares that posture and lives in the same package.

**`POST /apply` sniffs the uploaded bytes and branches on format**, ignoring both the file extension and the declared MIME type — browsers are inconsistent about document MIME types, and a renamed file would sail past either.

| Upload | Pipeline | Response |
|---|---|---|
| `.docx` | insert signature → insert date → apply read-only protection | `.docx`, Restrict Editing applied |
| `.rtf` (EMIS Web certificate export) | insert signature → insert date → convert via LibreOffice | `<stem>-signed.pdf` |

Anything else — a legacy `.doc`, a PDF, a stray image — is a 422 with an admin-readable message.

The RTF branch is **splice-then-convert, and the spliced RTF is never the deliverable** — only LibreOffice reads it. That lowers the bar on the generated `\pict` group to "whatever LibreOffice's RTF reader accepts" rather than Word's. It also means the read-only password has no analogue on this path and none is needed: a PDF is a stronger "do not edit this" than `w:documentProtection`.

**The two RTF anchors are not symmetric, and assuming they were is what broke this feature on every real certificate until it was fixed** — the Signature cell's label ends with an explicit `\par` while the Date cell's is terminated by `\cell` directly, so the Date anchor has to rewrite the label's run rather than simply splicing after it. `rtf_signature_insert.py` documents the exact markup. The regression risk here is the **test fixture** rather than the code: `backend/tests/fixtures/certificate_sample.rtf` is synthetic, and its first version invented the Date cell's markup by analogy with Signature, so the tests passed against a shape Word never emits. Its signature table is now copied run-for-run from a real export — read `backend/tests/fixtures/README.md` before changing it.

The alternative considered and rejected was extracting text with `striprtf` and re-rendering through an HTML template, avoiding LibreOffice entirely. The real export is the University of Oxford certificate form — 12 checkbox fields, 45 table rows, an embedded crest, section shading — and reassembling that from flattened text fails by **silently corrupting a medico-legal document** (a dropped paragraph of clinical opinion, a tick migrating from "No" to "Yes"), which no assertion can catch, because text you failed to extract is text whose absence you cannot detect.

**Every `soffice` invocation gets its own LibreOffice profile via `-env:UserInstallation`, and this is a correctness requirement, not a tuning knob.** Two concurrent conversions sharing the default profile were measured to collide, and the loser exited non-zero having *silently written no output file* — a request failing with nothing to diagnose. A private profile costs ~1.2 s and ~550 KB, removes the need for any mutex, and has a dedicated regression test. A resident `unoserver` would cut per-document conversion from ~1.5 s to well under a second but adds a long-running process to supervise, which is not worth it at a handful of certificates a day.

**Converter failures are 502, not 422** — `DocumentFormatError` means "your file is wrong", `ConversionError` means "our converter failed", and conflating them would send an admin hunting a bad upload when LibreOffice is what is broken. `subprocess.run` always carries an explicit timeout so a wedged `soffice` cannot hold a request thread open.

**Deployment depends on LibreOffice being in the image**: `nixpacks.toml` installs `libreoffice-writer` (not `libreoffice-core` — with core alone `soffice` starts fine but every conversion fails with the misleading `Error: source file could not be loaded`) plus `fonts-liberation`. CI installs the same for the backend test job. `SOFFICE_BIN` overrides the binary path.

### Study EOI autofill

A port of the `FillResearchSite` VBA macro the research lead used to paste into each NIHR Site Identification form. Eleven standard sections — roughly 80% of the form — are filled from a fixed rule set; the sponsor-specific questions at the end are untouched and stay a manual job in Word, which is why the output is a **plain editable `.docx`** rather than a protected one. `documentation/reference/FillResearchSite.bas` is the macro source the rules were transcribed from, and is the reference for any dispute about what a rule should say.

**Data flow.** Upload → open the package → snapshot every distinct table cell with its normalised text → match each rule against the snapshot → write answer paragraphs into whole cells → return the bytes. Nothing is persisted, nothing is written to disk, and there is no rule table in the database. `POST /eoi/fill` is a pure transform, the same posture as `POST /signatures/{id}/apply`.

**Whole cells are replaced, never text inside them.** The form's labels are heavily run-split by Word (`"Name and " / "R" / "ole:" / " [insert here]"`), so a find-and-replace port would have to reassemble runs before it could match anything. Replacing the whole cell sidesteps run splitting entirely — and it is what the macro does, so the port stays diffable against it. Formatting is carried over by copying the `pPr`/`rPr` of the target cell's first paragraph and run, falling back to the trigger cell's when the target is empty (the usual case, since answer cells start blank); that is the one place `eoi_fill.py` touches XML directly.

**Matching runs against a pre-write snapshot, and each target is written at most once.** This is the structural fix for a real macro bug rather than a tidiness preference: Section 9's answer text *contains* Section 9's own trigger phrase, so a macro walking the live document re-matched the cell it had just written. Snapshotting first makes that impossible by construction and, as a side effect, makes the order of the rule table irrelevant to the result — which is what you want from a table that may grow.

**Deduplication is on `id(cell._tc)`, and it is required, not defensive.** python-docx's `row.cells` returns the *same* underlying cell for every row a vertical merge spans, and the reference form has three merged label cells that rules depend on; a naive walk visits each twice and fills its target twice. It cannot be a plain `set` of cells, because `_Cell` defines no `__eq__` and two wrappers around one `tc` compare unequal. The id-based dedup is only sound while every visited proxy is kept alive — lxml frees a proxy once nothing refers to it and a later one can land on the same id — so `_snapshot` holds a `visited` list for exactly that reason. Without it the 38-cell reference form collapses to 13. VBA's `tbl.Range.Cells` enumerates distinct cells already, which is why the macro never hit this.

**Misses are reported in a response header, not a preview screen.** The user explicitly did not want a review step, but a silent miss is its own defect — the macro reported "Form has been filled in successfully!" unconditionally, including on this very form, where Section 10 matches nothing at all. So the response carries `X-EOI-Unmatched`: a comma-separated list of the *ids* of rules that found no target, always present, empty string when everything matched. Ids rather than the human labels because header values are latin-1 and comma-separated; `frontend/src/api/eoi.ts` holds the id → label map for display and **must stay in step with `eoi_rules.py`**. Zero matches is still a 200 — an unrelated `.docx` comes back unchanged with all eleven ids listed, and the frontend's warning naming them is a clearer message than a 422 could give.

**The rules are a Python constant because the repository is private, and that is the constraint holding them there.** The answer text carries practice-identifying data — named contacts and their direct details, the site address and code, CQC rating, ODP reporting dates, recruitment totals — measured against the bar `backend/tests/fixtures/README.md` sets for what may be committed. Hardcoding was chosen over a database table because the forms are identical every time and a figure change is then a one-line edit and a deploy; `EoiRule` is shaped so a later move to a table is a data-source swap rather than a rewrite. **If this repository is ever made public, the rule set has to move out of the source tree first.**

**Two macro behaviours were fixed rather than reproduced.** Section 4's rule matched a four-line cell (`Primary Care Y/N`, `Secondary Care`, `Community Care`, `Other`) and replaced the *whole* cell with `"Primary Care Y"`, destroying three lines; the `same_cell_line` target mode replaces only the matching paragraph, at the cost of collapsing that one paragraph to a single run (acceptable — the lines it targets are uniformly formatted checkboxes). And `InStr` was case-sensitive, so a sponsor writing "Research Site" for "Research site" silently got nothing; matching is now casefolded and whitespace-normalised on both sides.

**Deferred, deliberately.** The answer text is stale and internally inconsistent — a CQC rating from 2016, an ODP date from 2023, and two different non-commercial study counts between Sections 10 and 11 — and was ported **verbatim** so the table could be diffed against the macro. Correcting those figures is a follow-up. The second, larger follow-up is the one to watch for: nothing in this design stops the figures drifting again, because updating them means a developer editing a Python file. If that starts happening often, or if the research lead needs to change an answer without a deploy, the answer is an editable answer bank (a table plus a small admin UI), not more constants. Both are on `planned_updates.md`.

### Calendar Feed

Each doctor gets a private, unguessable URL returning their own sessions from committed rotas as an `.ics` file. They paste it into Google Calendar, Apple Calendar or Outlook once, and the calendar keeps itself current. We never call Google — Google comes to us. There is no OAuth, no Google Cloud project, no stored third-party credentials, and nothing Google-specific.

Writing events directly through the Google Calendar API was considered and rejected for now. It would buy near-instant updates, working per-event reminders and real free/busy blocking, none of which a subscribed calendar supports; it would cost a consent flow, encrypted refresh-token storage, a session→event-id mapping table, and full reconciliation on every edit, rollback and delete. If the missing reminders or the day-scale refresh latency turn out to be unacceptable in practice, the push model can be built later without unwinding any of this.

**The feed is identified by its token, not by who is logged in.** Any login that can read the clinical rota picks a doctor from the calendar page and copies that doctor's URL; the page defaults the picker to the user's linked doctor (see `documentation/architecture.md`) but does not restrict it, so a rota administrator can still fetch anyone's URL. The `users.doctor_id` link added later left this column working unchanged, which is what the original decision to keep them separate bought. The one thing it costs is that nothing can be sent *to* a doctor, because the system holds no email address — the doctor pulls the URL themselves, which is inherent to the feed model anyway.

**The token is the sole credential and the only protection.** A calendar client cannot present a bearer token, so the URL is public on the open internet and its security is that it is unguessable — `secrets.token_urlsafe(32)`, generated by `auth_utils.new_session_token()` so there is one definition of "unguessable token" in the codebase. The framing "the rota contains nothing sensitive" is not quite right and is not leaned on: the feed reveals a named individual's working pattern and, by absence, their leave. That is still personal data, which is why each feed carries **exactly one doctor** — a leaked URL exposes one person's schedule, not the practice's. **Rotation is the revocation path**, and the only one: issuing a new token immediately dead-ends the old URL, covering both a leaver and a link shared where it should not have been. Deactivating a doctor is *not* revocation, and a soft-deleted doctor still serves their feed. There is no constant-time comparison and no rate limiting; at 256 bits behind a unique index, guessing is not a threat worth engineering against.

**Every doctor row carries a token from creation**, the same invariant shape as the per-doctor `SystemCounter` rows and maintained in the same place, `routers/doctors.py`. Unlike the counter invariant, the backfill lives **inside migration 007 rather than a separate script**: `backfill_system_counters.py` exists because that invariant was violated in production before it was enforced, and this column has no such history. The migration adds the column nullable, generates a token per existing row in Python (no portable SQL expression yields a distinct random token per row across SQLite and Postgres), then batch-alters it to `NOT NULL` — so no database can hold a doctor without a token and the feed route needs no null branch. Rotation needs `user_admin` on top of the router's `clinical: write` rather than merely being write-gated: revoking a calendar link is user-management-shaped, and it is silently destructive, since the doctor's calendar simply stops updating with no error anywhere. It is one of only three endpoints in the app requiring two permissions at once, alongside the two staff deletes.

**Nothing is pre-generated or cached; each request recomputes the file from current database state.** This is what makes the feature cheap, and it dissolves the hardest problem in the push design. `is_on_leave` is not stored — it is derived from `leave_entries` at read time — so a doctor's rota can change after commit with no `rota_sessions` row changing at all; add rollback, force-delete and post-commit leave edits and a push model needs real reconciliation logic. A recomputed feed just tells the truth every time it is asked: a rolled-back or force-deleted rota's sessions stop appearing, and leave added after commit removes the affected sessions by itself. Only **committed** rotas are included — a draft changes constantly and publishing it would be noise — and **archived ones are included**, because `archived_at` is a pure UI visibility flag and an archived rota is still a real committed rota. The window runs from 56 days ago with no upper bound, applied to the rota range rather than per session, because a calendar nobody reads backwards should not grow without limit.

**The inclusion predicate reads the session row's own persisted `template_type`**: `REQUIRES_ROOM`, `PRE_ASSIGNED`, `ADMIN_TIME` and `WFH` are all events (the doctor is due at work either way), `NO_SURGERY` is not, and a null legacy type reads as a normal session. That is exactly `app/leave_charging.py`'s chargeable set, for the same reason — both ask "was the doctor due at work?" rather than `leave_planning`'s narrower "is a clinician available to see patients?" — and **the two are deliberately not merged into a shared predicate**, because `leave_charging` answers the question against the live week-1 master template by weekday while the feed answers it against the persisted snapshot on a real rota row. Sharing a function would force one of them onto the wrong source. Closed slots are read from the rota's own `RotaClosure` snapshot rather than the live `PracticeClosure` table, so a closure edited after commit cannot retroactively rewrite a historical feed. The filter order is closure → session type → leave, so a `NO_SURGERY` slot on a leave day produces neither a session event nor a leave event.

**Leave is emitted positively, and only where it suppressed a session.** A blank day is ambiguous — the doctor cannot tell leave from a feed that failed to refresh. Deriving leave events from suppressed sessions rather than scanning `leave_entries` is what keeps the query bounded: a part-timer's non-working day, a weekend and any date outside every committed rota all stay silent, and leave inherits the closure and session-type filters for free. Both periods of a date suppressed gives one all-day event; one period gives a timed half-day event, because a half day of leave is a real half day at work.

**Session times are practice-wide constants, not a settings table.** `Period` is `AM`/`PM` only and the system holds no clock times anywhere, but calendar events need them: AM 08:30–12:30, PM 13:30–18:00, module-level in `app/calendar_feed.py` with one environment-variable override per boundary, following the `DOC_LOCK_PASSWORD` / `SOFFICE_BIN` precedent. Changing the practice's hours is a Railway variable and a redeploy rather than a migration. All-day events for *working* sessions were considered and rejected — two all-day blobs a day read badly in every calendar app and say less than timed events; all-day is used only for a full day of leave, where it is the honest shape.

**Times are emitted as explicit UTC**, converted from `Europe/London` with the standard library's `zoneinfo`. Floating local times would be nearly correct for a single-site practice and wrong for anyone travelling; explicit UTC handles BST correctly, needs no `VTIMEZONE` block and adds no dependency, with `X-WR-TIMEZONE` riding along as a display hint.

**Event UIDs are `<session_id>@<constant domain>`.** Clients update an existing event rather than duplicating it when the UID matches, and `rota_sessions` has a standing invariant that edits mutate rows but never create or delete them, so the row id is stable across every edit a rota can undergo. The domain is **hardcoded, never the request's host**: deriving it from `request.base_url` would change every UID the day the app moves domain, or the moment someone subscribes via the Railway URL instead of the practice one, and every event in every subscriber's calendar would duplicate rather than update. A UID is a property of the data, which is what the constant makes it.

**The absolute URL is composed client-side.** `GET /doctors/{id}/calendar-feed` returns the token and the feed's app-relative *path*; `CalendarFeedPage` prepends `window.location.origin`. Building it server-side would mean reading `request.base_url`, which behind Railway's proxy reports whatever the proxy forwarded — a scheme mismatch there yields an `http://` URL that a subscriber pastes into Google and that silently fails. The browser already knows its origin correctly in dev (Vite proxy) and production (same-origin static mount) alike. One line of client code removes a whole class of deployment bug.

**Serialisation goes through the `icalendar` library rather than hand-rolled text.** The event structure is trivial; the format's rules are not — CRLF endings, folding at 75 octets, and escaping commas, semicolons and backslashes in text fields. Room codes and free-text notes contain exactly those characters, and getting it wrong produces a file Google silently refuses to parse, whose only symptom is a calendar that never appears.

### Conventions

- **Transaction boundaries:** each mutating endpoint commits explicitly on success; a raised `HTTPException` leaves the session uncommitted, so partial work is discarded.
- **Duplicate detection** is via catching `IntegrityError` on commit (race-free), mapped to 409 — not pre-checking. The one exception is the master-rota session POST, which pre-checks to produce a descriptive 409.
- **The room_id/room_type XOR** on room eligibilities and preferred rooms is enforced at the API boundary (Pydantic validators, 422) as well as by the DB check constraints.
- **Field naming:** objects embedded in lists alongside other `_id` fields use prefixed ids (`rota_id`, `session_id`, `template_id`) — a bare `id` would be ambiguous there; standalone CRUD entity schemas use plain `id`. The frontend's types mirror wire names exactly, with no client-side renaming.

## Frontend: Reference Pages

Application shell, auth boundary and the general-purpose API client are shared with the reception rota and documented under "Shared Frontend Infrastructure" in `documentation/architecture.md`. This section covers the clinical-only reference-data pages.

Five of these sit behind the left nav's **Session Management** entry as sub-tabs, and their **nav labels deliberately differ from their component names** — nothing in the code connects the two:

| Nav label | Component |
|---|---|
| Annual Planner | `LeavePlanningPage` |
| Individual Leave | `LeavePage` |
| Extra Sessions | `ExtraSessionsPage` |
| Closures | `ClosuresPage` |
| School Holidays | `SchoolHolidaysPage` |

The components, files and API routes were deliberately left alone when the labels changed — pure UI relabeling, no churn in tests or backend.

**One year for the whole strip.** `SessionManagementTabs` owns a single selected year, held in the URL as `?year=2027` (`SessionYearProvider` / `useSessionYear`), and renders the only year control — right of the tabs, above them, because a per-page control that silently changed four other tabs would read as a trap. Four of the five tabs read it: Closures (bank holidays *and* the practice-closure table), Extra Sessions, Individual Leave (entitlement, table and calendar) and the Annual Planner. **School Holidays deliberately does not, and the control hides while it is showing** — term dates straddle New Year, so a calendar-year filter would cut most holidays in half; it keeps its own "show past holidays" checkbox instead. A missing, non-numeric or out-of-range param reads as the current year (clamped to ±5 years) rather than erroring, so a hand-edited URL lands somewhere sensible. The month lives in the same provider but **not** in the URL — only the planner reads it, and keeping it in shared state means switching tabs and back returns to the month you were on. Changing the year lands on **today's month in that year**, and the planner **writes the year back** when a month step crosses a boundary (December 2027 → January 2028 moves the strip to 2028), so the strip can never claim a year the grid is not showing. `useSessionYear()` falls back to a read-only current year with a no-op setter outside the provider, which is what lets each page's tests render it standalone — the planner is the exception, since its month stepper writes through the provider and is inert without it.

Decisions worth knowing, page by page. Everything else is in the component.

- **DoctorsPage** — there is deliberately **no show-inactive toggle and no reactivate path**; a deactivated doctor is recoverable only via the API. On the backend's 409 (doctor has sessions on a committed rota) the page surfaces a "Deactivate instead" button firing the soft-delete PATCH — the remedy the 409 message names. The page reads the entitlement endpoint purely for `sessions_mismatch`, flagging inline beside the sessions/week stepper: it lives **here rather than on the leave tabs because this is the only place `sessions_per_week` is edited**, and the year is immaterial, used only to share a cache key with that tab.
- **ClinicTypesPage** — **priority is not a form field**: enabled clinic types are a drag-sortable list where array position is the only source of truth for order, firing the reorder endpoint on drop with optimistic local reorder and rollback on error. Disabled types render in a separate, non-draggable section sorted by name, because their stored priority is stale by definition and is never shown or relied on. The `"duty_helper"` category convention is explained as inline help text, since the form is the only place a non-technical admin would learn it.
- **LeavePage** — the table renders one row per consolidated **leave block** (`collapseLeaveEntries`), not one per half-day entry, and a block delete is a single bulk-delete call over the block's own span. Range submissions expand into disjoint segments fired concurrently with per-segment failure reporting — **no rollback, no faked atomicity**. Table failures land in a separate error slot so they can't mix into the form's add/remove summary. `LeaveEntitlementSummary` renders only when the doctor filter is set and only for a doctor the endpoint returns a row for — an AHP or locum gets nothing rather than a row of dashes. It shares the tab strip's year with the table and `LeaveYearCalendar` (neither has a control of its own), so a balance, the grid of leave that produced it and the rows listed beneath can never describe different years. Two consequences of year-filtering the table are worth knowing. The **preview query is deliberately left unfiltered**: `useLeave` is called twice, once for the table (on the selected year) and once for `LeaveRangePreview`'s overlap warning (year `null`), because a range running into next year overlaps entries the selected year's window would hide, and a missed overlap warning is worse than an extra fetch. And a **leave block spanning New Year splits at 31 December**: `collapseLeaveEntries` only ever sees the in-year half, so it renders a row ending 31 Dec, and the row's bulk delete removes exactly that half. Accepted rather than worked around with a fetch-with-buffer scheme — the row deletes precisely what it shows, and leave crossing New Year is rare. This replaced a full-practice entitlement table: the tab is about one doctor at a time. `no_template_row` exemptions warn here because they explain *this* screen's number; `sessions_mismatch` moved to DoctorsPage, next to the field it is about.
- **LeavePlanningPage / LeavePlanningGrid** — the forward-planning counterpart to LeavePage's ad-hoc form. The viewed `{year, month}` is the strip's shared state, not page-local: the month buttons call `shiftMonth` and hand the result back to the shared setter, which is how a step across New Year moves the year every other tab is on. Rows are filtered by **window *overlap* with the displayed month**, not "in window today", so a doctor leaving mid-month still shows for the part they worked. **Cell state is never stored per cell**: it is derived at render from server rows merged with a page-level pending map, so a pending edit and the row underneath it cannot disagree; an edit whose state *and* notes both equal the server's deletes the key rather than recording a no-op, keeping the unsaved-count badge honest.

  **Range selection is horizontal only, within one doctor's row** — a rectangle would need a separate set of window/closure decisions per row. The geometry is a pure function (`selectionCells` in `lib/planningMonth.ts`) so the highlight and the cells handed to Apply cannot disagree, and it walks the grid's own Mon–Fri dates rather than `expandLeaveRange`, which walks calendar days and would emit weekend keys to filter out. Endpoints are **normalised by date, not click order**, and the half-day edges reuse the Individual Leave tab's semantics — so a stationary click is a range of one *half*, and single-cell half-day editing falls out of the same rule rather than being a second code path. A drag **extends** through closed and out-of-window cells but those are filtered client-side before Apply: posting them would put "N skipped (doctor not employed on that date)" on the summary of every save spanning a leaver's end date.

  The grid holds **one popover root anchored at the drag's focus cell**, not one per cell. This is forced, not stylistic: a popover trigger opens on `click`, and a `click` only fires on the nearest common ancestor of mousedown/mouseup, so a drag spanning two cells produces no click and no popover, while a single-cell press produces one racing the programmatic open. Two consequences: with no trigger, focus must be restored to the cell explicitly on close; and Radix's document-level dismiss fires *before* React's `onMouseDown`, which is right for a plain click but would destroy the anchor a shift+click extends from — hence the shift-key guard.

  **Closed and out-of-window cells get deliberately different treatments** — closed reuses RotaGrid's solid closed style and totals as "—", out-of-window is plain absent grey — because confusing "the practice is shut" with "this doctor isn't employed yet" would mislead. Skips and superseded extra sessions in the response are surfaced as *information*, not error: the save succeeded. **Doctor row selection is a second, independent selection and a reading aid only** — it never affects a cell's state or what an edit writes; it drives a row tint and a balance line for the **viewed month's** year, so paging December→January swaps the balance rather than labelling next year's cells with this year's figures. The selected id survives month changes (following one doctor through the year is the point) but only counts as selected while that doctor has a row in view.
- **DutyPage / DutyGrid** — a week-at-a-time editable grid over the pre-planned duty inputs. Week completeness is computed client-side and **shared with RotaPage**, which shows the same incomplete-duty-week warning before generation. Closure-aware: a closed AM/PM cell is inert per-period, and the secondary-duty pair attaches to the week's first *fully open* weekday rather than always Monday — **reimplemented in TypeScript rather than shared with the engine**, so its test file carries the matching case matrix. `DutyGrid` takes an optional `weeks` prop so a caller can render fewer than a full duty period, which is what lets RotaPage embed it as a generate-form sidebar. The period dropdown offers one past period by default, extended to six by a **"Show previous periods" checkbox** — needed purely because an already-planned period stays worth looking at (and editing: duty rows are generation inputs, not an audit trail, so a late edit to a past period corrupts nothing). No API change was involved: `GET /duty` is already unfiltered and the grid's counter ranges are derived from whichever period start it is handed. The selected period is derived from today's date rather than indexed out of the options array, since the toggle changes how many past entries precede the current one; unticking while an out-of-range past period is selected snaps the selection forward rather than leaving the `<select>` blank.
- **ClosuresPage** — both halves of the page follow the strip's year: the bank-holiday grid (which had the only year pager before the year became shared, and has none now) and the practice-closure table below it. A closure added outside the selected year is saved and flagged inline rather than rejected — the date field is not clamped. AM/PM/Full day is **UI sugar only**: there is no full-day endpoint or period value, so picking Full day fires two POSTs and deleting a full-day entry fires two DELETEs. A closure applies automatically to any rota generated over it, so there is nothing to select on the generate form.
- **SchoolHolidaysPage** — purely informational global planning data with no engine coupling of any kind. A "Show past holidays" checkbox hides holidays that have ended; a school with only past holidays still shows, with an empty list. Delete is gated behind a confirm naming the school and its holiday count, since it cascades.
- **ExtraSessionsPage** — the list is filtered to the strip's year (it had no year concept at all before, showing every entry ever); as on Closures, a session dated outside that year still saves and says so. Reads the active staging, because an extra session only takes effect through the staging copy's override step. The weekday-only rule is mirrored client-side so the server's 422 is never the first line of defence.
- **RecurringNotesPage** — CRUD over note definitions. Purely annotation.
- **CountersPage** — live counter values, each row showing a client-computed weighted score mirroring the engine's exactly, including `sessions_per_week == 0` scoring as infinite and kept distinct from the genuine no-data case. The two writes are **reset** and **opening balance**, and they behave differently under a draft: the reset confirmations warn that a scrap restores the raw counts but *not* the balance the same reset cleared, while the balance inputs carry no draft warning at all, a balance edit never being snapshotted. Any credit is shown beside the raw count (`3 (+3.2)`) rather than folded into it, so "how much has this doctor actually done" stays answerable from that column. A row with `id: null` (no counter row yet) has its reset disabled and its balance input live — saving one creates the row.
- **UsersPage** — unlike DoctorsPage, the list is **not** active-only: inactive users are shown and flagged, since this page is the only recovery path once a user is locked out. The backend's zero-active-managers 409 surfaces as a toast rather than a form error, the action having no form of its own.
- **SignaturesPage** — admin-staff document tooling, not part of either rota, so it sits on its own top-level route rather than in the clinical nav.

### Shared utilities (`src/lib/`)

- **`expandLeaveRange.ts` / `collapseLeaveEntries.ts`** — inverses. Expand turns a range plus edge options into 1–3 **disjoint contiguous segments** matching the bulk endpoint's body shape; disjointness is what makes concurrent segment submission safe, and is asserted as a property in its tests. Collapse groups a doctor's half-day rows back into the fewest contiguous blocks: a weekend *gap* doesn't break a run, but a stray weekend *entry* does, since bulk add is weekday-only and such a row can only be anomalous. Leading PM and trailing AM halves are absorbed as flags rather than separate rows; any other half-day shape starts its own block rather than hiding behind a flag. The exactness property collapse guarantees — every weekday in a block's span has an entry, and no weekend entry falls inside it — is what makes attaching a single bulk-delete call to a block's row safe, and is asserted as a property, not spot-checked.
- **`planningMonth.ts`** — the pure half of the planning grid, kept out of the component for two non-stylistic reasons. `applyPendingToCoverage` re-applies the coverage endpoint's own rules **client-side** so the cover total updates without a round trip; the two calculations have to agree exactly, which is only checkable if this one is testable alone, so its test file carries the same case matrix as the server's. It is a **delta against the server's baseline**, not a from-scratch recount, so an unedited slot always shows the server's own number and the page can never silently diverge for a doctor it does not render. Separately, `buildPlanningActions` emits a paired `clear` first when moving *between* leave and extra planned — without it the endpoint would skip the action in either direction and the saved state would not match the grid. The bulk endpoint's clears-before-inserts flush exists precisely so that pairing is legal.
- **`closedSlots.ts`** — the shared "is this slot closed" lookup, taking either a live `Closure[]` or a rota/staging `ClosedSlot[]` snapshot, since the two are structurally compatible for this purpose. Used by every grid that renders closures, plus both exporters, so the closed/fully-closed determination exists once.
- **`date.ts`** — date-only strings are parsed by manual Y/M/D construction, **never `new Date(dateString)`**, which parses as UTC midnight and renders as the previous day in negative-UTC-offset timezones.
- **`groupDoctors.ts`** — the canonical doctor display order (Partner, Salaried, Trainee, AHP; alphabetical by code within type), shared by both rota grids and the reference pages.
- **`weightedScore.ts`** — the frontend mirror of the engine's fairness score. **`superviseeCount.ts`** is the same idea for Phase 9C's trainee count. Both are mirrors by necessity, not shared code; their docstrings name the Python function each must track.
- **`WeekTabs.tsx`** (component, not `lib/`) — the week tab strip shared by `RotaGrid` and `RoomRotaGrid` so both select from the same week state when toggled in `RotaDetailPage`.

## Frontend: Master Rota

The `/master-rota` route views and edits the active template — the fixed 4-week repeating pattern every generation run reads from. All edits persist immediately (no draft/committed lifecycle, no Phase 12), and the page states "Changes apply to future generated rotas only".

**Page/grid split.** `MasterRotaPage` owns the undo stack, the toast and the Undo button, and holds its own instances of the three mutation hooks used **only to execute undo replay**; the grid owns all forward mutations and reports each success upward with a pre-built undo entry, `previous`/`displaced` values captured from the in-memory session objects at click time. Same split as `RotaDetailPage`/`RotaGrid`.

**Week tabs are fixed to a constant 1–4, not derived from the session list.** Deriving them broke once create/delete existed: an empty week had no tab to click into to populate it, and deleting the last session in a week collapsed the tab out from under the active-week state. The week domain is defined by backend constraints, not by data.

**Grid rows come from `/doctors`, not from the doctors present in the sessions payload** — so a newly added doctor with zero template sessions still gets a row — plus any inactive doctor who still has sessions, badged.

**`MasterRotaConflictsPanel`** flags rooms double-booked within one `(week, day, period)`. Three decisions: it is **client-side with no endpoint of its own**, recomputed from the session list the page already holds and keeps current by cache splicing, so it re-checks on load and after every edit for free; it carries **no severity or check taxonomy**, unlike `IssuesPanel`, because the template has no Phase 12 pass; and it exists **because of `seed_master_rota.py`** — the live edit endpoints already prevent double-booking by displacing the existing holder, so the CSV import is the one bulk path that can create this state.

**Cell editing (`MasterCellEditPopover`)** is a **sibling of `CellEditPopover`, not a generalisation** — the two data models share nothing but the popover shell. One component serves both edit mode (every cell with a session is editable; no draft gate, no leave concept to suppress the trigger) and create mode via a nullable `session` prop: absent cells on an *active* doctor's row show a faint "+" affordance, while an inactive doctor's absent cells stay inert, since you don't build a new working pattern for a leaver.

The menu is five mutually exclusive `session_type` options with **deliberately no WFH toggle**: a five-value enum has no defined "off" state for a checkbox. Admin time's room submenu alone gets a "No room" entry, since roomless admin time is valid, real data. **Confirm-before-steal** is client-side and advisory (`findMasterRoomHolder`, again a deliberate sibling of the rota-side `findRoomHolder`); the server's own displacement lookup remains the source of truth. **"Remove session"** is applied with no confirm — a deliberate departure from the steal pattern, since confirmation is reserved for steal-class actions and removal is fully undoable.

**Drag-and-drop was considered and deliberately cut**: the popover covers every operation, swap semantics on a template are unclear, and DnD's cost was the largest item for the least value. Revisit only if actually missed.

**Undo (`lib/masterUndo.ts` + the shared `lib/undoStack.ts`)** is **replay of inverse API calls against live server state** — nothing is staged client-side, since every forward edit persists immediately. There is no redo. `MasterUndoEntry` is deliberately **not** folded into the rota `UndoEntry` union and not routed through `replayUndo.ts`: that module is rota-scoped in every branch, and the template's write surface shares no branching logic with it. The generic `useUndoStack<T>` is the shared piece.

Replay preserves **displaced-first ordering** across all three kinds — restore whatever was stolen before undoing the action that stole it. A re-displacement caused by the restore is harmless, because the next call overwrites the target with its own exact previous pair. Undoing a delete recreates the row with a new id (nothing references the old one after the cache filter ran), and if another session has since taken the room, ordinary displacement fires as it would for any fresh create — accepted under the single-admin-user assumption. A failed replay re-pushes the consumed entry so undo stays retryable. Success toasts are plain descriptions of what changed, with no issue-count delta, since Phase 12 never runs here.

**Cache (`api/masterRota.ts`)** — all three mutation hooks follow the splice-in-place/no-invalidate pattern (`setQueryData`, never a refetch), the same convention as the rota side. Create appends rather than matching, having no existing row; all three splice any `displaced_session`.

## Frontend: Staging

The `/staging` route is the interface for the editable holiday-cover step. **`RotaPage`'s generate form no longer generates directly**: submitting it creates a staging and navigates to `/staging`, where the one-off edits happen before "Complete and generate" actually runs the pipeline. `RotaPage` renders one of three states in its top slot, **in priority order**: the active-draft banner, an active-staging resume banner, or the generate form — draft first because a rollback can produce a draft mid-staging, and the draft is the more immediately actionable state.

`StagingPage` takes no id: at most one staging exists globally, so it always operates on the active-staging endpoint. `GenerateErrorMessage` was extracted out of `RotaPage` so both the staging-create form and the complete action render the same three failure shapes (plain-string 409, Phase 0 issue list 422, raw FastAPI request-validation 422) without duplicating the type guards.

When the generate form is showing, `RotaPage` renders a **duty preview sidebar** embedding `DutyGrid` for the exact weeks about to be generated, so an admin can adjust duty without navigating away first. The form's start date and week count were lifted out of the form component up into `RotaPage` purely so the sidebar can read the same values; `DutyGrid` needed no changes, already fetching its own data and owning its own DnD context.

**`StagingGrid` is a clone of `MasterRotaGrid`, not a generalisation** — kept separate to avoid destabilising the existing component and its tests. It reuses `MasterCellEditPopover` unchanged (the popover is hook-agnostic, and a staging session is a structural superset of a master session), swapping in the staging mutation hooks. Three differences:

- **Week tabs derive from the staging's own `num_weeks`.** This forced a sibling pivot rather than reusing `pivotMasterRota.ts` as originally planned: its `weeks` is the hardcoded 1–4 constant — correct for a template, which always has all four week slots — which would render two or three permanently empty, unusable tabs on a 1- or 2-week staging.
- **Day headers show the real calendar date** and follow `RotaGrid`'s closure treatment: fully closed greys the header, partly closed keeps it ungreyed with a qualified label and greys only that period's cells. The master template has no real dates to show.
- **A session on leave gets a badge**, informational only — the popover stays available, since arranging cover for that exact leave is the common case staging exists for.

**There is no undo plumbing on this grid**, unlike the master one: results go straight to a toast. The v1 recovery path for a bad edit is abandon-and-restart; the master grid's undo pattern can be cloned later if session-level undo proves necessary.

## Frontend: Generated Rota Grid & Editing

The interactive surface for reviewing and hand-editing a generated rota before commit. `RotaDetailPage` owns page-level state (undo stack, toast, lifecycle actions); `RotaGrid` owns the grid, drag-and-drop and cell mutations; the business rules live in pure, unit-testable modules under `src/lib/`. All editing is draft-only.

A committed rota's read-only view shows up to two further actions: a conditional **Roll back commit** button, rendered only when the client-side most-recent-commit check says this rota is eligible, and an **Archive**/**Unarchive** toggle. Both follow the existing confirm-then-mutate pattern but neither navigates away on success. `RotaPage`'s committed history is split into Committed/Archived tabs **client-side only** — see "Archive / unarchive".

### CommittedRotasPage — the published-rota view

`/clinical/committed` is the "where am I working this week" page: the list of committed, unarchived rotas with the one covering the current week picked out and opened by default, and its grid rendered underneath. It exists because **the clinical section's index page is a generation console** — staging form, duty-staffing preview, clinic enable checkboxes, commit history — none of which means anything to someone who cannot generate. A **clinical read-only login now lands here instead**: "Generate new rotas" became a `writeOnly` nav entry like the reference-data pages, and `CLINICAL_READER_HOME` in `App.tsx` is the redirect target for every write-only path, the section index among them. That constant must not itself be write-only, or the redirect loops.

**Deliberately not a mode of `RotaDetailPage`.** That page is the editing and lifecycle surface (commit, scrap, archive, rollback, force delete, issues panel, generation log); serving as a reader's landing page would mean conditioning most of it away. `RotaGrid` and `RoomRotaGrid` are already read-only for a committed rota — `editable` is derived from `rota.status` — so the whole page is those two components plus a picker, with no mutation callbacks passed at all. Archived rotas are excluded rather than given a second tab: archiving is precisely the action that says a rota should stop appearing in the everyday view, and `RotaPage`'s committed history still lists them.

**"Current" is a week, not a date.** `getCurrentRotaMonday` resolves Mon–Fri *backwards* to the Monday just gone — deliberately unlike `getUpcomingMondays`, whose forward roll is right for picking a generation start week but would point past the week the user is standing in — and rolls Saturday/Sunday *forwards*, the rota being Mon–Fri only so a weekend has no current week. `rotaWeekForMonday` then maps that Monday onto a rota's 1-based generation week (null if out of range), on UTC epoch values for the same DST reason `getDutyPeriodStart` uses them. That one value drives three things: which rota is selected on arrival, which week tab opens, and the "This week" / "(this week)" markers. Selection and current-week are **shown differently on purpose** — they coincide on arrival but come apart the moment the user clicks another rota, and the marker has to survive that. `WeekTabs` grew an optional `currentWeek` prop for the tab marker; no other caller passes it, since everywhere else the rota on screen is a draft for a future week.

|---|---|
| `RotaDetailPage.tsx` | Undo stack + toast, replay execution, Commit/Scrap/Rollback/Archive/Unarchive |
| `CommittedRotasPage.tsx` | Read-only published-rota view: committed-rota picker + grid, current week anchored |
| `RotaGrid.tsx` | Grid layout, week tabs, DnD context, dispatches all five mutation types |
| `CellEditPopover.tsx` | Cell edit menu: WFH/notes, Change room / Change role submenus, confirm view |
| `IssuesPanel.tsx` | Aggregated Phase 12 warnings with scroll-to-cell navigation |

Four of these carry decisions worth stating. **`RoomRotaGrid`** is a pure frontend transformation of data `useRota` already fetched — no mutations, no DnD, no popover — so it is structurally a sibling of `RotaGrid`'s read-only cell, not of its editable one, and that holds on drafts as well as committed rotas. **The two exporters are built entirely client-side from the already-fetched rota, which is why neither is gated on write access**, and `exportContent.ts` holds the cell-content logic they share so the sheets and the PDF cannot drift apart. **`GenerationLogPanel`'s filtering is a functional requirement, not a convenience** — a full 4-week run emits several hundred entries — and each `rationale` sits behind a collapsed per-entry disclosure because it is multi-line and would drown the messages inline. **`Toast`** is single-slot with no queue: one admin edits one draft at a time.

### Pivot invariant

A session row exists if and only if a template entry existed for that slot at generation time (see "Master template" under Table design decisions), and no edit endpoint ever creates or deletes one. **A missing key in the pivot lookup is therefore the real "absent" state**, and there is deliberately no fallback that reconstructs a cell from `/master-rota`.

One consequence: a fully closed day's columns need no special cell handling, since every cell in that column is already the ordinary absent `<td>` a part-time doctor's gap produces. A **partly** closed day is different — the open period's cells render normally and the closed period's get an explicit closed style, distinct from plain-absent grey, since the two must not be visually confused. The header greys and labels a fully closed day against the rota's own `closed_slots` snapshot (authoritative), showing a qualified AM/PM label for a partly closed one, and uses a live closures fetch **cosmetically, for the closure's name only** — never for the closed/open determination itself.

### Cell colouring (`cellStyle.ts`)

One function, one fixed precedence: **leave > WFH > role colouring (duty / duty-helper / named clinic) > no-surgery/admin-time grey > default**. The grey branch is only reachable when no role is present — a role on an incompatible slot renders as a normal role-coloured cell, and Phase 12's `role_on_incompatible_slot` warning is what surfaces the conflict, not the cell's appearance. WFH's background is unconditionally blank regardless of role; the badge carries the signal. **Font colour is derived from the assigned room's type and encodes room location, nothing else**; unresolved rooms have no cell-level styling and surface only via the issues panel. Duty-helper colouring is a data convention, not a schema rule — a mis-categorised type rendering as a named clinic is the accepted failure mode for a cosmetic mapping.

### Editing model

Five mutation types, all draft-only, all returning fresh Phase 12 issues alongside the mutated session(s) — see "Editing endpoints and re-validation" for their server-side contracts. Responses are **spliced into the query cache, never invalidate-and-refetch**, so the grid and issues panel update from the response payload alone.

The philosophy is **apply-then-warn with undo, not ask-first**: the server performs any edit it's told to and returns warnings; the frontend applies immediately and surfaces the result. The single exception is **confirm-before-steal** — taking a room, duty role, or specific clinic type currently held by another session in the same slot. Steal detection is client-side against the in-memory grid, but the server's displacement lookup remains authoritative for what actually happens. Direct actions (normal clinic, no surgery, admin time, unassign, clear room) get no confirm.

Duty/clinic picks preserve the persisted `template_type` snapshot; no-surgery and admin-time picks overwrite it — the accepted trade-off that weakens the snapshot's meaning to "generation-time, possibly manually overridden". The popover is **not rendered at all on leave cells**; it is available on WFH cells, where picking a room clears the WFH flag.

### Drag-and-drop

Each cell renders up to two explicitly typed chips (role, room), and **the chip type determines the endpoint — nothing is inferred from the drop**. Eligibility (`dragRules.ts`): same day **and** period, target present and not leave/WFH, not self. The day/period check **must be explicit**: only the active week's cells are mounted, making cross-week drops structurally impossible, but all ten day/period columns are mounted simultaneously and the API would happily apply a cross-slot swap if the client didn't reject it. A chip is only draggable when its own value is present, so the backend's both-sides-empty 422 is unreachable from this UI. `resolveDrag.ts` keeps resolution pure and unit-testable, because real dnd-kit pointer simulation needs bounding rects jsdom doesn't provide.

### Undo

`replayUndo.ts` builds each entry's replay as a sequence of 1–3 requests, executed serially, **displaced session restored first, then the target** — a re-displacement from the first call is harmless, since the next call overwrites the target exactly. **Swaps and moves replay as the identical call repeated**: both swap endpoints are self-inverse including their counter increment/decrement pairs, so "repeat the call" and "move it back" are one mechanism. A `set-role` undo appends a trailing `set-room` when the forward op auto-cleared the room, decided by a flag captured from the forward response **at push time, not re-derived at replay time**. A failed replay re-pushes the consumed entry. The Undo button is always rendered for drafts, disabled when the stack is empty, and absent for committed rotas.

**One permanent limitation:** a room cleared by toggling WFH on via PATCH cannot be restored by undoing that patch — the PATCH has no room field and `swap-rooms` 422s when neither side holds a room, so no API path back exists. The undo toast says so explicitly rather than overstating what happened, and whether that follow-up is needed is inspected from the PATCH replay's actual response rather than pre-built into the replay sequence. The nullable `set-room` closes this gap for the menu's own entry kinds only.

### Validation feedback

The "N new warnings" toast is a **count delta, not a set diff** — `ValidationIssueOut` has no stable identity across Phase 12 re-runs, so "which warnings are new" isn't computable client-side; the issues panel always reflects true current state regardless. A composite check/week/day/period/message key would give a workable diff without backend changes if this ever needs tightening. Issues-panel navigation is scroll plus a CSS flash targeting a data attribute — the panel and grid share no React state for it.

### Counter effects of edits

Edits adjust clinic counters only (get-or-create, floored at 0 on decrement, same-type reassignment a no-op). **System counters are written at generation time and never touched by edits.** Draft-period drift is prevented by the snapshot lifecycle, not recalculation — see "Counters and snapshots".
